## 2. 源码级复核：三条结论 + 一条更正

1. **触发源是触摸屏**（与昨夜一致）。IMU 的 Tap 引擎在电池下零事件的原因仍未确认。
2. **唤醒线极性反了。** 驱动按 `levels.interrupt ? POSEDGE : NEGEDGE` 配中断
   （`esp_lcd_touch_cst816s.c:65`；板级 `levels.interrupt = 0`，`boards/…185b.c:681`），即 INT 空闲高、触摸拉低；
   而 `muse_gpio_wake_line_add_wake_only(TP_INT, true)` 按**高电平**武装 → 空闲就满足唤醒条件 →
   IDF 拒绝进入 light sleep（`esp_hw_support/sleep_modes.c:1052-1102`，`RTC_SLEEP_REJECT_MASK` 含 GPIO 触发）。
3. **「唤醒 CPU」与「亮屏」之间原本没有接线。** 亮屏写在 LVGL 的 cover 回调（`muse_ui.c:1022-1030`
   `on_cover_event` → `muse_state_set_asleep(false)`），而电池睡着时 `update_power()` 会 pause 显示
   （`muse_input.c:491-498` → `esp_lv_adapter_pause`），LVGL 任务停走、indev 不读；
   `on_any_press` 只 `muse_state_poke()`（`muse_state.c:195-198`），不清 asleep。
4. **更正**：`docs/20261019待办.md` §1.1 的 55ms 根因对不上板上固件（那只存在于 `458d08f`；
   板上 1.2 修正版 `ASLEEP_WAIT_MS=190` 且 `s_knock_on` 无初值 → `knock_polling=false` → 等待 1 s / 10 s），
   「按键中断在轮询间隙触发 → 通知丢了」也不成立。

## 3. 现场取证：I2C 总线故障（本节是今天最硬的证据）

板子跑 1.2 修正版，用户报告「拔线等自动息屏后敲击/按键都不亮屏，插回 USB 触摸特别的卡」。
COM3 只读抓取（`dtr=False, rts=False` 打开，不复位）拿到：

```
E i2c.master: probe device timeout. Please check if xfer_timeout_ms and pull-ups are correctly set up   ×约每 2 s
W board: BQ27220 not answering at 0x55
W muse.imu: no IMU on the bus: ESP_ERR_INVALID_RESPONSE
W muse.imu: tap engine restart failed (#18)            ← 每 60 s
I link.heartbeat: hb t=1245s setup=done wifi=up ws=up raw=up ble=off …
@imu.wakes sleeps=16 line_high=0 taps=0 taps_awake=0 knocks=0 sampling=0 last_slept_ms=936 last_tick_ms=941 int1=0
W muse.imu: tap diary (console): boots=1 wakes=16 gpio=1 timer=0 other=15 line_high=0 taps=0 taps_awake=0
            knocks=0 not_ready=0 repairs=0 rearm_fail=3 drifts=0 accel=4748/4749 maxmg=804 screen_wakes=1 …
  diary[44] t=967293ms wake a=0 b=7        ← cause 7 = ESP_SLEEP_WAKEUP_GPIO：拔线后第一次真正的 light sleep 唤醒
  diary[45] t=1075396ms engine-ERR a=264 b=1   ← 264 = ESP_ERR_INVALID_RESPONSE，此后每 60 s 一次
```

判读：

- 触摸 CST816S（0x15）与故障器件**同一条 I2C**（`boards/…185b.c:101-102`：SDA=11、SCL=10，
  线上还有 ES8311/ES7210/BQ27220/IMU/RTC）→ 每次触摸读都在等超时，这就是「触摸特别的卡」。
- 任务没死：串口任务应答 `>imu`/`>batt`，输入任务每 2 s 读电量（`POWER_MS`，说明抓取时 `paused=false`）、
  每 60 s 重整 IMU。
- **级联放大（IDF 源码，已确认）**：`esp_lcd_panel_io_i2c` 的每个事务传**无限超时**
  （`components/esp_lcd/i2c/esp_lcd_panel_io_i2c.c:145`、`:147` 的 `..., -1`）。
  总线不通 → 读触摸的任务永久阻塞 → 屏幕不再重绘、背光/cover 停在暗态 → 状态被叫醒了也看不到亮屏。
- **根因未确认**：从机把 SCL/SDA 拉住，与 pad 在 light sleep 后丢配置，在日志上完全一样。
  IDF 的 i2c_master 在事务期间持 `ESP_PM_NO_LIGHT_SLEEP`（`i2c_common.c:285-312`），所以不是旧结论
  「I2C 事务被 light sleep 截断」。

## 6. 上机验证（1.3 首轮：USB 刷机 + 电池实测）

- 刷机：`Wrote 3084288 bytes`、`Hash of data verified` ×4、`=== flash end 13:56:14 exit=0 ===`。
- 台面（USB）：`@tp lines=2 touch=1 line=4 armed=0 live=1`（触摸线按低电平武装、线空闲为高，与驱动的下降沿一致）；
  `@tp.line[0] gpio=8 armed=1 live=0`；`@i2c fails=0 streak=0 resets=0 sda=1 scl=1`；`@status fw=1.3 battery=33`。
- 电池实测（用户操作：拔线等自动息屏 → 敲屏幕正面 3 次 → 按按键 3 次 → 插回 USB）：

```
@imu.wakes sleeps=96 line_high=0 btn=2 touch=0 touch_wakes=0 last_slept_ms=444 last_tick_ms=448
            int1=0 btn_level=0 touch_level=1 cause=1 btn_irqs=2
tap diary: boots=1 wakes=96 gpio=5 timer=87 other=4 btn=2 touch=0 line_high=0 screen_wakes=3
  diary[1] t=180427ms wake a=2 b=7      ← a=2 按键位、b=7 GPIO：按键把 CPU 叫醒了
  diary[4] t=361823ms wake a=2 b=1
@tp.line[1] gpio=4 armed=0 live=1 seen=1 irqs=0
```

判读（已确认）：

1. **按键链路通了**：日记里有 `wake a=2 b=7`（按键位 + GPIO 唤醒源）、`btn=2`、`screen_wakes=3`，
   用户现场确认「按键亮屏恢复了」。上一次「按键不亮」的出口就在 §3 的 I2C 级联（UI 被冻住），这次总线没复发（`fails=0`）。
2. **极性修正生效**：light sleep 真的在睡（`timer=87` 次定时唤醒、`last_slept_ms=444`），不再是被拒绝的忙等。
3. **触摸仍不亮，但原因找到了**：5 次 GPIO 唤醒里 2 次读到按键按下，其余 3 次读到三条线**全部无断言**
   （`touch=0 touch_level=1`）——那 3 次正是 3 次敲击。即 **CST816S 的 INT 是脉冲，不是保持到被读走的电平**；
   1.3 的判定只看「读取瞬间的电平」，所以每次敲击都被漏掉。

### 6.1 针对「脉冲」的修法（1.3c，待上机）

- 判据换成**唤醒原因本身**：`cause == GPIO` 且按键未按下、IMU 线未拉高 ⇒ 只可能是触摸线
  （睡着时只武装了这三条），直接 `set_asleep(false, "touch")`；「读取时电平为低」保留为快速路径。
- 修掉自己写出的 latch bug：线回到高时无论醒睡都要解锁，否则「亮屏时的一次触摸」会把之后所有敲击锁死。
- 新增 `muse_gpio_wake_was_line()`（`muse_board.c/.h`），供输入任务判定唤醒来源。

- **COM3 只读抓取**：pyserial 打开前 `dtr=False, rts=False` 再 `open()`，读取与写命令都不复位板子；
  命令之间留 3–5 s，输出带时间戳（`t=…`），便于把「每 2 s 的报错」和「人工动作」对齐。

## 9. 电量计电池模型写回 + 界面图标（2026-10-19 晚，同为 1.3 发版内容）

起因：界面电量恒显 33%。根因是电量计数据内存里是 3000 mAh 的模型（本板电芯 500 mAh），SoC 按错误容量算。

做法（按"复用现成模块、不自己写寄存器访问"）：引入官方组件 `espressif/bq27220`（连带 `espressif/i2c_bus`），
I2C 改由 `i2c_bus_create()` 建总线、其余设备取内层 `i2c_master_bus_handle_t`；
开机由 `bq27220_create()` 写入本板 CEDV 模型（幂等，写入后回读校验 25 个字段）；
`read_power()` 改为**以电量计为准**，电压折算仅作最后兜底。

上机证据（COM3 串口，1.3 固件）：

| 项 | 结果 |
|---|---|
| 组件日志 | `bq27220: Firmware Version 2002` / `Hardware Version 0004` / `Battery profile readback verified (25 fields, learned_capacity=excluded)` / `Skip battery profile update: verification=full` |
| `0x3C DesignCapacity` | 500 mAh（写入前为 3000） |
| `0x12 FullChargeCapacity` | 500 mAh（写入前为 3000） |
| `0x10 RemainingCapacity` | 500 mAh |
