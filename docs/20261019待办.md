## 1. P0：按键唤醒回归修复

### 1.1 根因

`458d08f` 把睡着时的 `wait_buttons` 等待从 10s/1s 改成 55ms：

```c
// muse_input.c 约 719 行
muse_board->wait_buttons(knock_polling ? ASLEEP_WAIT_MS  // 55ms！
                                       : (napping ? NAP_WAIT_MS : REST_WAIT_MS));
// knock_polling = asleep && s_knock_on，s_knock_on 默认 true
```

后果：
1. 主循环 55ms 空转一次（每秒 18 次 I2C），不是休眠
2. I2C 每次拿 `ESP_PM_NO_LIGHT_SLEEP` 锁，锁几乎常占，CPU 进不了真睡
3. 按键中断在 I2C 轮询间隙触发时，`xTaskNotifyGive(s_waiter)` 发出去没人收
   （task 不在 `ulTaskNotifyTake` 里）→ 通知丢了 → 按键按死都没反应
4. 最坏：I2C 在 55ms 窗口内没做完 → 锁互等 → CPU 卡死 → 必须强行关机

### 1.2 立刻验证（不用改代码）

```
>knock=0
```
关软件采样，等待回到 10s/1s，看按键唤醒是否恢复。
- 恢复了 → 实锤，往 1.3 修
- 没恢复 → 另查（报我，查 `0beb8ba` 的 touch INT 改动）

### 1.3 正式修复（二选一）

**方案 A：独立采样任务（推荐，干净）**

敲击采样从主循环剥离，单独 FreeRTOS 任务 60ms 周期跑。
主循环的 `wait_buttons` 恢复 10s/1s 长等待。

```c
// 新任务 knock_task，每 60ms：
while (1) {
    if (muse_state_asleep() && s_knock_on) {
        int mg = muse_imu_tap_bump_mg();  // 读加速度计，算偏离重力的 mg 数
        if (mg > KNOCK_THRESHOLD_MG) {
            // 去抖：连续 2 次超阈值才算（防误触）
            if (++s_knock_hits >= 2) {
                set_asleep(false, "knock");
                s_knock_hits = 0;
            }
        } else {
            s_knock_hits = 0;
        }
    }
    vTaskDelay(pdMS_TO_TICKS(60));
}
```

要点：
- 任务栈放 PSRAM（参考 OTA 任务的做法），优先级低于 input task
- I2C 复用现有的 `bus_lock` + PM 锁，不要另起一套
- `set_asleep` 本来就是线程安全的（里面有 `xTaskNotifyGive(s_input)`）
- `>knock=0/1` 开关保留，控制这个任务跑不跑

**方案 B：条件降级（改动小，妥协）**

只在确认硬件引擎已死时才开 55ms 轮询：

```c
// 引擎活着（taps>0 或刚启动）→ 长等待，让硬件引擎干活
// 引擎已死（连续 5 分钟 taps=0 且 drifts=0）→ 55ms 轮询，软件顶上
bool engine_dead = (now_ms - s_last_tap_ms > 5*60*1000) && s_engine_checked;
muse_board->wait_buttons(engine_dead ? ASLEEP_WAIT_MS : (napping ? NAP_WAIT_MS : REST_WAIT_MS));
```

缺点：55ms 轮询本身还是有竞态风险，只是触发概率低了。

**建议选 A**。B 是裱糊，A 才是把"采样"和"休眠"两个职责分开。

### 1.4 验证标准

- [ ] `>knock=0` 下：电池息屏 → 按键 → 亮屏，3/3
- [ ] `>knock=1` 下（修完后）：同上 3/3，且静置 10 分钟不误唤醒
- [ ] 功耗：电池下息屏电流回到之前水平（55ms 空转时电流明显偏高，可对比）

## 2. P1：电池下敲击亮屏（最终方案）

### 2.1 路线已定：软件检测为主，硬件引擎为辅

```
敲击
 ├─ 触摸屏（GPIO4）→ 已并入唤醒线 ✅（0beb8ba 已做）
 │    └─ 敲屏幕正面 → 触摸 INT 拉高 → 亮屏（USB/电池都行）
 │
 └─ 敲机身/背面 → 加速度计软件检测（方案 A 的独立任务）
      └─ 60ms 轮询 → 连续超阈值 → 亮屏
```

硬件 tap 引擎（QMI8658）：**放弃治疗**。
三次实测证明它在电池下就是不报事件，原因可能是 silicon quirk，
继续投入时间不值得。代码保留（USB 下偶尔能用），但不依赖。

### 2.2 触摸唤醒（已做，待验证）

`0beb8ba` 已把 GPIO4（触摸 INT）注册为 `wake_only` 唤醒线。
待验证：
- [ ] 电池下息屏 → 敲屏幕正面 → 亮屏
- [ ] 不影响触摸正常功能（`own_intr=false` 没动驱动的中断配置）

### 2.3 软件敲击检测（待重做，见 1.3 方案 A）

阈值建议：
- 当前 `knocks` 用的是 ≥400mg 触发过一次
- 正式阈值从 400mg 起调：太灵（放桌上被脚步震醒）就往上加，太钝就往下降
- 去抖：连续 2 次 60ms 周期超阈值（120ms 内两次冲击，符合敲击特征）

### 2.4 功耗账

| 模式 | 估算 |
|---|---|
| 长等待睡眠（10s） | 基准 |
| 60ms 软件轮询 | 每秒 16 次 I2C 读（每次 ~100μs）→ CPU 几乎不睡，**比长等待高一个数量级** |
| 折中 | 只在**深夜/长时间无操作**后降频到 200ms？或加速度变化大时才加密采样 |

先保证功能，再优化功耗。`>knock=0/1` 开关留着给用户自己选。

## 5. 2026-10-19 白天复核与 1.3 实施

> 复核方式：本机源码阅读 + IDF 源码 + 已发布资产的 sha256 比对。**全部未上机**。

### 5.1 两条结论更正

1. **§1.1 的 55ms 根因对不上板上固件。** 55ms 只存在于 `458d08f`（且当时自采样默认开）；
   板上 1.2 修正版（本地 `build-muse-waveshare-s3-touch-lcd-185b/muse-gadget.bin`，sha256
   `56e10024…` = 线上 v1.2 资产，含 `fifowatch` 串）里 `ASLEEP_WAIT_MS` 已是 190 ms，且
   `s_knock_on` 无初值（`muse_input.c:130`）→ `knock_polling=false` → 等待回到 1 s / 10 s。
   即 55 ms 那条路径在当前固件里不生效。「板上跑的就是这一版」仍属**推断**，
   一条命令坐实：`>knock` 应打 `sampling=0`。
2. **「按键中断在轮询间隙触发 → 通知丢了」不成立。** FreeRTOS 任务通知是计数锁存：
   `on_button_line` 的 `vTaskNotifyGiveFromISR` 在任务没等的时候也记着，下次
   `ulTaskNotifyTake(pdTRUE, …)` 立刻返回。按键的根因仍未确认，靠 §5.3 的计数取证。

### 5.2 触摸唤醒的两条真问题（源码级）

1. **唤醒线极性反了。** 驱动按下降沿收中断（`esp_lcd_touch_cst816s.c:65`，板级
   `levels.interrupt = 0` → `GPIO_INTR_NEGEDGE`），即 INT 空闲为高、触摸拉低；
   而唤醒线按高电平注册（`boards/board_waveshare_s3_touch_lcd_185b.c:694` → `wake_high=true`
   → `muse_board.c` 的 `GPIO_INTR_HIGH_LEVEL`）。空闲就满足唤醒条件 → IDF 拒绝进入
   light sleep（`esp_hw_support/sleep_modes.c:1052-1102`，`RTC_SLEEP_REJECT_MASK` 含 GPIO 触发）。
2. **触摸→亮屏没有代码路径。** 亮屏处理在 LVGL 的 cover 回调里（`muse_ui.c:1022-1030`
   `on_cover_event` → `muse_state_set_asleep(false)`），而电池睡着时显示被 pause
   （`muse_input.c:491-498` → `esp_lv_adapter_pause`），LVGL 任务停走 → indev 不读 →
   触摸事件进不了 UI；`on_any_press` 只 `muse_state_poke()`（`muse_state.c:195`），
   不清 asleep。极性修对也不亮屏，缺的是这一步。

### 5.5 现场实测（2026-10-19 上午，板子跑 1.2 修正版，COM3 只读抓取）

拔线跑一段再插回 USB 之后，**整条 I2C 总线是坏的**（不是触摸屏单点问题）：

```
E i2c.master: probe device timeout. Please check if xfer_timeout_ms and pull-ups are correctly set up   ×每 ~2 s
W board: BQ27220 not answering at 0x55
W muse.imu: no IMU on the bus: ESP_ERR_INVALID_RESPONSE
W muse.imu: tap engine restart failed (#18)      ← 每 60 s 一次
```

- 触摸 CST816S（0x15）与它们**同一条总线**（`I2C_SDA=11 / SCL=10`，线上还有 ES8311/ES7210/RTC）
  → 每次触摸读都在等超时 → 用户感觉到的「触摸特别的卡」。
- 任务都活着：串口任务正常应答（`>imu`、`>batt`），输入任务每 2 s 读电量、每 60 s 重整 IMU
  （`paused=false` 的节奏，说明抓取时它不在休眠态）。
- RTC 日记：`boots=1 wakes=16 gpio=1 timer=0 other=15 line_high=0 taps=0 knocks=0 screen_wakes=1`，
  事件环最后一条是 `wake a=0 b=7`（t=967 s，cause 7 = **GPIO 唤醒**，即拔线后第一次真正的 light sleep 唤醒），
  之后 8 分钟无 wake 事件；`engine-ERR a=264`（264 = `ESP_ERR_INVALID_RESPONSE`）从 t=1075 s 起每 60 s 一次。
  → 推断：**总线是在电池态第一次真睡/醒之后坏的**。IDF 的 i2c_master 在事务期间持 `ESP_PM_NO_LIGHT_SLEEP`
  锁，所以不是旧结论「I2C 事务被 light sleep 截断」。
- **原因未确认**：从机把 SCL/SDA 拉住，与 pad 在 light sleep 后丢配置，两者都会表现为探测超时。
- 级联放大（已确认，IDF 源码）：`esp_lcd_panel_io_i2c` 的每个事务传的是**无限超时**
  （`components/esp_lcd/i2c/esp_lcd_panel_io_i2c.c:145` 的 `i2c_master_transmit_receive(..., -1)`），
  所以总线一旦不通，**读触摸的那个任务会永久阻塞**：屏幕不再重绘（背光/cover 停在暗态，
  按键把状态叫醒了也看不到亮屏），触摸也再不响应。这解释了「触摸卡 → 死」「按键不亮屏」这一组现象。
  缓解方向（未做）：给触摸自己实现一个有界超时的 panel_io，或让 UI 任务带看门狗。
