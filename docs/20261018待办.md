## 1. 电池下敲击不亮屏（USB 正常）

### 1.0 前提：硬件与代码位置

- 板子：Waveshare ESP32-S3-Touch-LCD-1.85B；IMU：QMI8658A，I2C 地址 `0x6B`。
- 接线（原理图 Rev1.1）：INT1(pin4) → R51(0R) → **GPIO8**；INT2 = NC。
- 唤醒机制：`muse_gpio_wake_line_add(GPIO8, true)`（电平 HIGH），并入
  `muse_gpio_buttons_wait()` 的 light-sleep 唤醒集合。
- 仓库：`blacksamuraiiii/muse-esp32-s3-touch-lcd-1.85b`，分支 main。

| 文件 | 内容 |
|---|---|
| `esp32/components/muse/muse_imu_tap.c` / `.h` | tap 引擎驱动：500 Hz accel、tap 参数、INT1；`muse_imu_tap_tapped()` 读 STATUS1.bit1 |
| `esp32/components/muse/muse_input.c` | 睡着时每 200 ms 轮询 tap，命中 → `set_asleep(false, "tap")` |
| `esp32/components/muse/muse_board.c` | `muse_gpio_wake_line_add()`、`muse_gpio_buttons_wait()`（`:151-172` 每轮重武装 GPIO8） |
| `esp32/components/muse/boards/board_waveshare_s3_touch_lcd_185b.c` | init 建 0x6B i2c device、调 tap init、注册 GPIO8 |

### 1.1 症状（2026-10-18 用户实测）

| 现象 | 结果 |
|---|---|
| USB 供电 + 敲击 | 正常（`waking (tap)`） |
| 电池供电 + 敲击 | 失效 |
| 电池下 tap 引擎配置 | 正常（`>imu`：`CTRL7=0x21` `CTRL8=0xc1`，`recoveries=0`） |
| 电池下按键唤醒 | 正常 |

结论：不是配置漂移；不是初版那条 `s_ready` bug（0eadb51 已修）；是只在真电池那条路出现。

### 1.1b 实测把「tick 停走」这条根因证伪（2026-10-18 夜）

带串口强制复现电池态时抓到的原文（`>pmlow=1` + `>nap`）：

```
I muse_input: slept 10000 ms (tick 10000 ms), line low     ×10
```

墙钟 10000 ms 与 FreeRTOS tick 10000 ms 相等 → light sleep 之后 tick 由 tickless 补偿正常推进，
「tick 停走 → 轮询被跳过」**不成立**；`>pmlow=1` 下敲击能亮屏也说明该路径本身可工作。

另一组硬数字（`muse_input.c:66-67`）：`REST_WAIT_MS=1000`、`NAP_WAIT_MS=10000`。
息屏后即便唤醒线完全失效，最多 1 秒（Wi-Fi 小睡时 10 秒）也会返回一次并读 STATUS1。
所以真电池下「敲击完全不亮」只剩两种可能：

1. **引擎在电池态没有锁存 STATUS1**（芯片侧没报事件）；
2. **读到 tap 时状态判定不是 asleep** —— 亮屏条件是 `tapped && muse_state_asleep()`，
   此时那一次 tap 会被静默消费掉。

带串口的复现**不代表**电池态：USB 主机在时固件根本不进 light sleep，`>pmlow=1` 虽能强制，
但 USB-Serial/JTAG 随之掉线（`ClearCommError … PermissionError(13)`，之后端口列得出、打不开）。
取证只能落到设备里再插回 USB 回读 —— 这就是 `muse_imu_tap.c` 里 RTC 常驻「敲击日记」的用途：
开机与 `>imu` 打印 `wakes/gpio/timer/other/line_high/taps/not_ready/repairs/rearm_fail`
以及 16 条事件环。判读表：

| 日记读数 | 结论 |
|---|---|
| `wakes>0, line_high=0, taps=0` | 引擎没报（芯片侧）→ 查电池态下的配置/供电，或依赖敲击兜底 |
| `taps>0` 但屏幕没亮 | 状态判定（`asleep`）或亮屏路径 |
| `gpio=0`、`timer` 占多数 | 线唤醒没生效，走的是定时返回兜底 |
| `not_ready>0` / `repairs>0` | 引擎配置死路（本版已能自愈） |

### 1.1d 结论：触发源是触摸屏，不是 IMU（2026-10-19 凌晨）

用户敲的是**屏幕正面**。USB 下敲三下能亮屏，但同一时刻日记里
`taps=0 taps_awake=0 knocks=0 screen_wakes=0`——亮屏与 IMU 无关，是触摸控制器报的事件。
于是这一项的走向改为：**把触摸 INT（GPIO4）并入 light-sleep 唤醒线**（已实施，电池实测待做）。
完整时间线、被证伪的假设、难点与遗留项见 `docs/20261018进展记录.md` §11
（原 `docs/20261019进展记录.md` 已并入该文件，分册已删除）。

### 1.1c 第三次、第四次电池实测（2026-10-18 23:1x–23:2x）

第三次固件的日记（电池段）：

```
@imu.wakes … taps=0 taps_awake=0 knocks=1
tap diary: wakes=51 gpio=0 timer=49 line_high=0 taps=0 knocks=1 drifts=0 repairs=0 starts=7
事件环：9× wake a=0 b=4(TIMER) → engine-on + rearm(t=109s) → … → engine-on + rearm(t=119s, 129s)
```

- `rearms=6` → 10 秒一次把引擎整颗重启，**重启期间用户敲了，引擎仍一个事件都不报**，INT1 一次没高。
- `drifts=0` → CTRL1/CTRL2/CTRL7/CTRL8/CAL 回读全对，配置侧无痕。
- `knocks=1` → 加速度读数至少动过一次（≥400 mg），但那一下没有亮屏；这一步也可能是插回 USB 的手碰。
- 结论：**「引擎事件在电池态不出现」已三次复现，靠重启引擎救不回来。**

第四次固件（本文件对应的最后一版）改为不再依赖引擎：

| 改动 | 目的 |
|---|---|
| 息屏时轮询间隔 200 ms → 60 ms，`wait_buttons` 等待 1 s/10 s → 55 ms | 自己按 500 Hz 芯片里的最新样本判敲击，不经过 tap 引擎与 INT1 |
| `>knock=0/1` 开关 | 关掉采样即回到长等待，用来量这套检测的耗电代价 |
| 日记加 `accel=<变化数>/<读取数>`、`maxmg`、`screen_wakes` | 一次分清三段：芯片在不在采样（活性）／有没有检出（检测）／检出后屏幕有没有真的亮（亮屏路径） |
| CTRL1/CTRL2 纳入校验、睡醒立即校验 | 加速度 ODR 若在睡眠边界被改坏，引擎会「看着配好却没有样本」 |

判读表（电池实测后按这四条读）：

| 日记读数 | 结论 | 下一步 |
|---|---|---|
| `accel` 变化率 ≈100% | 芯片在采样，坏的是引擎与 INT1 | 软件检测即解，调阈值/频率 |
| `accel` 变化率 ≈0% | 读数冻住，芯片/供电侧 | 软件检测无效，转硬件或换唤醒源 |
| `knocks>0`、`screen_wakes=0` | 检出但状态没切 | 查 `asleep` 判定 |
| `knocks>0`、`screen_wakes>0` 而未亮 | 检测与状态都对，坏在亮屏路径 | 查背光/面板在电池下的上电 |

### 1.2 为什么 USB 与电池不同

`muse_input.c` 的 `update_power()`（约 452 行）：

```c
bool pause = muse_board->display_pause && muse_state_on_battery() && muse_state_asleep()
             && muse_ui_dark() && muse_voice_resting();
bool want_low = pause && (s_force_low || !muse_console_host());
```

- USB：`muse_console_host()` 为真 → `want_low=false` → 不进 light sleep，200 ms 轮询每拍都跑。
- 电池：`want_low=true` → 进 light sleep，靠 GPIO8 或定时器叫醒。
- 链路：`muse_console_host()` = `usb_serial_jtag_is_connected()`（`components/muse/muse_console.c:42`）；
  `set_cpu_low()` 只在 `want_low` 为真时把 `light_sleep_enable` 设为 `low`（`muse_input.c:367`）。

### 1.3 初版根因假设：tick 在 light sleep 期间不走（§1.1b 已证伪，留档）

主循环（约 595 行）：

```c
TickType_t now = xTaskGetTickCount();
if (now - s_tap_checked >= pdMS_TO_TICKS(IMU_TAP_POLL_MS)) {   // 200 ms
    s_tap_checked = now;
    bool tapped = muse_imu_tap_tapped();   // 读 STATUS1，读即清
    ...
}
...
if (paused && muse_board->wait_buttons) {
    muse_board->wait_buttons(10000);       // light sleep 最长 10 s
}
```

死亡序列：

1. 轮询跑完，`s_tap_checked = T`。
2. `wait_buttons` 进 light sleep，FreeRTOS tick 停走（tickless idle）。
3. 敲击 → QMI8658 INT1 拉高 → GPIO8 叫醒 CPU。
4. 回到循环顶部，`now` 仍约等于 `T`（tick 没走）。
5. `now - s_tap_checked < 200 ms` → 轮询被跳过，STATUS1 没人读。
6. INT1 一直 HIGH → 引擎锁存不再报新敲击 → 下次睡时 GPIO8 已 HIGH，唤醒配 HIGH 等于没配 → 彻底睡死。

USB 下 tick 一直走，第 5 步永远不成立，所以 USB 正常。

### 1.5 已实施：计时器换 wall clock（防御性；非根因，但语义更准）

`esp_timer_get_time()` 基于 RTC，light sleep 期间照走。5 个计时器的语义都是「真实流逝时间」
（重臂注释原话 "the window counts from the last wake"），没有一处需要「CPU 醒着的时间」。

头文件（约 32 行附近）加：

```c
#include "esp_timer.h"
```

变量声明（约 116-120 行）改：

```c
static int64_t s_tap_checked_ms;  /* last tap-status poll, ms wall clock */
static int64_t s_tap_verified_ms; /* last CTRL7/CTRL8 comparison, ms wall clock */
static int64_t s_tap_full_ms;     /* last tap-parameter comparison, ms wall clock */
static int64_t s_tap_rearmed_ms;  /* last engine restart, counted from the last wake */
static int64_t s_bump_logged_ms;  /* last knock that made it into the log */
```

主循环（约 595-630 行）改：

```c

int64_t now_ms = esp_timer_get_time() / 1000;  // wall clock，跨睡眠不断
...

    s_tap_checked_ms = now_ms;
    ...

        if (full) {
            s_tap_full_ms = now_ms;

```

### 1.7 为什么这两条不影响正常休眠

| 改动 | 休眠状态机 | 结论 |
|---|---|---|
| 换 wall clock | `update_power()` / `wait_buttons()` 一行没动 | 只修计时准不准，不碰睡不睡 |
| 叫醒后清零 | `wait_buttons` 返回时 CPU 已醒 | 多一次 I2C 读（微秒级），之后该睡继续睡 |

- 叫醒后 STATUS1 无残留 bit 则不会误唤醒（`tapped=false` 直接过）；有残留 bit 说明之前漏读，唤醒一次正是应该的。
- 功耗增量：每次 `wait_buttons` 返回多一轮 I2C 读，可忽略。

### 1.7b 已实施：三条死路修复 + 与引擎无关的敲击兜底

| 改动 | 位置 | 为什么 |
|---|---|---|
| `tapped()` 不再因 `s_ready` 为假直接返回假 | `muse_imu_tap.c` | 读 STATUS1 本身就是清锁存、把 INT1 放低的动作；旧写法让「配置未知」等于「永远读不到」 |
| `check()` 在 `s_ready` 为假时改为尝试修复 | `muse_imu_tap.c` | 旧写法直接 return false，等于这种状态下没有看门狗 |
| 1 Hz 看门狗不再被 `muse_imu_tap_ready()` 门住 | `muse_input.c` | 三条合起来：一次失败的初次 init 会让敲击**永久失效到重启** |
| 加速度脉冲 ≥400 mg 且息屏即亮屏 | `muse_input.c`（`IMU_KNOCK_WAKE_MG`） | 这条读数是轮询本来就要做的；引擎是 500 Hz 采样而轮询 200 ms，会漏短脉冲，所以阈值取高。它让「引擎不报」不再等于「敲不亮」 |

## 2. 敲击亮屏：已闭环的三条根因

分册一按 H1/H2/H3 假设排查，最终确认为三个独立机制叠加，三条修复都在 1.2 里。

### 2.1 根因与修法

| # | 根因 | 机制 | 修法 |
|---|---|---|---|
| 1 | I2C 事务被 light sleep 截断 | 半截写入被 QMI8658 解析成寄存器写，`CTRL8.bit0 (Tap_EN)` 被改写；加速度计不受影响 | 每个 I2C 事务持 `ESP_PM_NO_LIGHT_SLEEP` 锁（`muse_imu_tap.c`） |
| 2 | STATUS1 锁存没人清 | 亮屏时敲击无人读，位一直置着，引擎不再报新事件 | `muse_input.c` 每 200 ms 读一次 STATUS1，不分亮屏息屏 |
| 3 | 引擎状态机自锁 | 配置全对、引擎不检测，无可读痕迹 | `muse_imu_tap_rearm()`：睡下时每 60 s 重臂 |

排查路径（分册一的决策树，留档）：先读回 `CTRL8`/`CAL`——漂了做配置看门狗；没漂做「亮屏也读 STATUS1」；
仍死则考虑 silicon bug，退到定期软复位 tap 引擎（`CTRL8.bit0` 先清后置）。抓毛刺时间点（看配置丢失是否
落在 light sleep 进出 ±500 ms 内）只在确认漂移后才做。

遗留小项：`read_power()` 走 BQ27220 的 I2C 没有 PM 锁（`boards/board_waveshare_s3_touch_lcd_185b.c:800`），
而 tap 的 I2C 已持锁（`muse_imu_tap.c:140/152`）。顺手补同一把锁，代价小。

### 2.2 溯源手段（保留）

| 命令 | 作用 |
|---|---|
| `>imu` | 一行 WARN 打 `CTRL1/2/7/8/9`、`STATUSINT`、`STATUS1`、`TAP_STATUS`、`CAL1..4`、期望值、自愈次数 |
| `>imu.check` | 强制全量校验（含 CAL），漂了立刻重配 |
| `>imu.rearm` | 强制重臂一次 |

正常值：`CTRL7=0x21(want 0x21) CTRL8=0xc1(want 0xc1) cal=08 20 20 03 90 01 00 20`。
出现 `config drift: …` + `tap re-initialised (#1)` 说明根因 1/2 发生过，自愈生效。

### 2.3 软件复位（wupsbr 可抄项一）

`muse_imu_tap_init()` 在 WHO_AM_I 校验后、写 CTRL1 前先复位芯片：

```c
#define REG_RESET 0x60   /* Datasheet Rev A：写 0xB0 触发软件复位 */
#define RESET_CMD 0xB0
err = write_reg(REG_RESET, RESET_CMD);
if (err != ESP_OK) return err;
vTaskDelay(pdMS_TO_TICKS(20));   /* datasheet 标 15 ms */
```

已落地：`components/muse/muse_imu_tap.c:61-62`、`:261`。复位清全部寄存器，必须在所有配置之前；
复位后 WHO_AM_I 不变（0x05），不需重校验。

### 2.4 混合方案（跳过）

wupsbr 不用硬件 tap 引擎，1 kHz 轮询加速度计做软件检测（`muse_imu_poll_shake()`），
代价是 CPU 必须醒着。本板靠 light sleep 唤醒，混合方案要「INT1 只当门铃、醒来软件确认」，
但若引擎永久死亡到 INT1 都不跳，仍救不了，只能退到定时唤醒轮询（每 200 ms 醒一次，功耗上升）。

判断：§1 的 tick 根因已能解释电池下全部现象，先修 §1；混合方案与定时轮询留作保底，不实施。
wupsbr 软件检测逻辑（`s_gravity` 一阶低通 alpha=0.06、`d=a-gravity`、3 次反向 swing 判 shake）
记在此处备查；敲击可简化为单次 `g > 0.5g` 脉冲。

### 2.5 已排除项（留档，避免重复排查）

- 芯片复位/掉电：加速度计配置一直在。
- I2C 挂死：读写正常。
- `DRDY_DIS` 屏蔽 tap 中断：datasheet 确认只影响 INT2 引脚。
- Wi-Fi nap 直接动 IMU：`muse_wifi_nap()` 只断 Wi-Fi。
- GitHub 同类案例：QMI8658 的 75 个仓库、esphome issue 全查过，无同症状。

## 4. 电量、电源灯、OTA、TTS 坏包

### 4.1 电量恒显 100%（已完成）

原假设「电量计没配 Data Flash」被真机推翻。根因是寄存器地址读错：`0x1C` 是 StandbyTimeToEmpty，

### 4.2 红色电源灯常亮（已定论，硬件）

`LED2`：`3V3 → R1(10K) → LED → GND`，通电就亮。无 GPIO、无寄存器、无配置项。
耗电 (3.3−2)/10K ≈ 130 µA，可忽略。想灭只能黑胶带或拆 R1/LED2。

## 9. 电量计电池模型（1.3 已写入数据内存；1.4 剩余：GPCCEDV 标定 + 组件未覆盖的 DF 项）

背景（实测）：BQ27220 的 `0x12 FullChargeCapacity` 与 `0x3C DesignCapacity` 都读 3000 mAh（本板电芯 500 mAh）、
`0x2A CycleCount` 0、`0x0C Current` 恒 0 mA，而 `0x08 Voltage` 4.165 V → `0x2C StateOfCharge` 恒定 33%（30 分钟不动）。
10-18 上午该表还正常（`0x2C=59%`，RC/FCC = 292/500 = 58.4% 对得上），说明是**学习值/配置被复位**，不是从未配过。

已实现（2026-10-19 晚，1.3）：`read_power()` **以电量计读数为准**，电压折算曲线只作最后兜底（电量计读数越界或组件句柄缺失时才用，不再用它推翻电量计）。
开机时由 `espressif/bq27220` 的 `bq27220_create()` 把本板电池模型写进电量计数据内存（幂等：先校验、一致则跳过）。
实测写入后：`0x10 RemainingCapacity` / `0x12 FullChargeCapacity` / `0x3C DesignCapacity` 均 500 mAh，`0x2C StateOfCharge` 100%（`0x08 Voltage` 4159 mV，自洽），
组件日志 `Battery profile readback verified (25 fields, learned_capacity=excluded)` → `Skip battery profile update: verification=full`。
冷启动首次 MAC 读（设备号 0x0001）曾返回 `0xcf0d` 被组件拒绝（`Invalid Device Number`），下一次开机即通过，故 create 加了一次重试。

模型来源说明：容量项（`full_charge_cap`/`design_cap`/`near_full`）按本板 500 mAh 电芯设定；电压/温度项（`EDV0-2`/`EMF`/`C0`/`R0`/`T0`/`R1`/`TC`/`C1`/`DOD0..DOD100`）取自组件自带参考电芯
（`test_apps/main/bq27220_test.c` 的 `default_cedv`），描述的是电芯特性而非包容量。**这是可用的起始模型，不是 GPCCEDV 标定过的模型。**

组件未覆盖的 DF 项（仍待 1.4）：`DesignEnergy`（约 1850 mWh）、`Taper Current`（约 50 mA，DF 类 "Charge Termination" 地址 `0x9201`）、化学体系 profile ID。
这些不在 `parameter_cedv_t`/`gauging_config_t` 里，要单独走 `bq27220_set_parameter_u16()`（组件要求调用方自行进入 CFGUPDATE，而其控制字写接口为 static，未公开）——留给 1.4 决定是本地覆盖组件还是上游提 issue。

3. 模型恢复：先跑 `sample-data-app` 拿一轮充放电 CSV → GPCCEDV 出参数 → 用 `bq27220_create()`/`set_parameter_u16()` 写回；写前读、写后回读，并把「写前后 FCC/RC/SoC」记进 `>batt`。

先做的判据（便宜实验，仍建议先跑）：

| 步骤 | 动作 | 判据 |
|---|---|---|
| ① | USB 充电、电池放电各读一次 | `Current` 是否随充放电变号、量级合理（现见 `0x0C=0` 与 `0x14=150 mA` 自相矛盾）→ 电流测量是否还活着 |
| ② | 用 `get_design_capacity` / `set_parameter_u16` 试写 design capacity = 500 | FCC 跟着变 500、SoC 跳到 ~96% → 只差一个数；FCC 仍 3000、SoC 仍 33% → 走第 3 步的成套参数 |

注意：BQ27220 是 **CEDV** 电量计（datasheet 标题 «Single-Cell CEDV Fuel Gauge»），模型是一整套参数
（TRM §2.7.9 CEDV Configuration、EDV 放电率/温度补偿、老化因子、平滑），`DesignCapacity` 只是其中一项。
SoC 的分母是否为 `FullChargeCapacity` 而非 `DesignCapacity` **尚未逐字核实**（TI 惯例是前者），故本项不预设「改一个数就能好」。
