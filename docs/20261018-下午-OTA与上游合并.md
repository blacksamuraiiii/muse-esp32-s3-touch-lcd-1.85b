## 2. OTA 第一个坑：任务栈要不到（真机日志）

用户看到 `failed: could not start ota task`。这行字符串在仓库里只有一处——
`esp32/main/ota.c` 的 `xTaskCreate(ota_task, "ota", 16384, ...) != pdPASS` 分支，
也就是说**根本没走到网络**。

真机日志（1.2，UI 起着时按 `>ota`）：

```
I link.ota: ota start: int free 18315 largest 8704 | psram free 4095040 largest 4063232
W link.ota: no 16384-byte internal stack for the ota task
W link.ota: no 12288-byte internal stack for the ota task
W link.ota: no 10240-byte internal stack for the ota task
I link.ota: ota task up (8192-byte internal stack)
I link.ota: Writing to <ota_1> partition at offset 0x420000
```

**PSRAM 空着 4 MB，内部最大块只剩 8.7 KB**，16 KB 必然失败。修法见上表。
关键点：OTA 任务栈**必须**在内部 RAM——`esp_https_ota` 写 flash 时 cache 是关的，
PSRAM 栈那时候不可访问，直接崩。降到 8 KB 后完整跑通了：3 MB 下载 + 验签 + 安装。

## 3. OTA 第二个坑：装完又被静默回滚（这个更隐蔽）

第一次 OTA 的完整时间线：

```
I ota.github: manifest: version=1.3
I ota.github: updating 1.2 -> 1.3
I link.ota: ota task up (8192-byte internal stack)
I esp_https_ota: Writing to <ota_1> partition at offset 0x420000
I link.ota: incoming version=1.3
I link.ota: applied 1.2 -> 1.3, rebooting
……重启后……
I link.app:   Version:  1.3          ← 看着是成功的
```

**但几分钟后再抓启动日志，又变回 `Loaded app from partition at offset 0x20000` / `Version: 1.2`。**

根因在 `app.c` 的 `ota_verify_task()`：它只在 `noise_ctrl_is_connected()`
（Home Link 控制 WebSocket）为真时才调用 `esp_ota_mark_app_valid_cancel_rollback()`，
否则等 `OTA_VERIFY_TIMEOUT_US`(300 s) 超时就直接
`esp_ota_mark_app_invalid_rollback_and_reboot()`。
这块板没有 SDK token（启动日志 `SDK token: (none)`），`link.vm_api` 一直
`ESP_ERR_HTTP_CONNECT`，控制 WS 永远连不上 → **300 s 后必然回滚**。

修法：保留 WS 快速路径，新增宽限——镜像连续运行 30 s 就标记有效。
理由：会崩的镜像活不到 30 s，那种情况 bootloader 自己会回滚，不需要用云端通道判断镜像好坏。
宽限只在 `s_ota_pending_verify` 为真时执行：从 factory 分区启动时
`esp_ota_mark_app_valid_cancel_rollback()` 返回 `ESP_FAIL`（IDF 的 `Running firmware is factory`
分支），无条件调用会让每次普通开机多打一条错误日志。

**这个坑的验收行**（下次 OTA 时应该看到）：
```
I app: running a PENDING_VERIFY OTA image; awaiting health check
I app: OTA image validated after 30 s without the control WS (this build runs without it)
```

## 4. 电池：真机把原来的结论推翻了

1.2 那版我判断"BQ27220 没按电芯配过 Data Flash，SoC 天然 100%"，
还加了电压兜底。**真机 `>batt` 一打，这个判断是错的。**

真机原始值（1.2，插 USB 充电中）：

| 寄存器 | 值 | 正确含义（TRM Table 2-1） |
|---|---|---|
| 0x08 | 4136 | Voltage 4136 mV |
| 0x0C | 474 | Current +474 mA（正 = 充电） |
| 0x10 | 497 | RemainingCapacity 497 mAh |
| 0x12 | 500 | FullChargeCapacity 500 mAh |
| 0x18 | -1 | TimeToFull 无效 |
| 0x1C | 3313 | **StandbyTimeToEmpty** ← 老代码把它当 SoC 读，被 `<=100` 夹成 100 |
| 0x28 | 3064 | InternalTemperature 306.4 K = 33.3 ℃ |
| 0x2A | 2 | CycleCount 2（新机） |
| **0x2C** | **100** | **StateOfCharge 100%**（充满后） |
| 0x2E | 100 | StateOfHealth 100% |

上午那次抓到的另一组（未充满时）`0x1C=1947 0x2C=59`，且 RC/FCC = 292/500 = 58.4%，
与 SoC 59% 完全对上——**交叉验证成立，电量计本来就是配好的**，不需要写 Data Flash。

修法：SoC 改读 `0x2C`；越界才回落到电压估算。`charging` 用 BatteryStatus(0x0A) bit0
（DSG，1=放电）取反。`>batt` 现在按 TRM 名称打印 18 个标准命令 + DesignCapacity(0x3C)。

**教训：先 dump 再推理。** 任何"恒为某个值"的传感器读数，先怀疑地址/单位/缩放，
不要急着给它编一个物理原因。`0x1C` 读出 1947 这种明显不像百分比的值，本身就是最强的线索。

## 5. 上游合并（facebookincubator/muse-gadget-sdk）

落后 26 个提交 / 领先 13 个，merge base 是 `4268880`。已全部合入（提交 `5ed7ee8`）。

对本板有意义的改动：
- `sdk_token_console.c`：串口 `>sdk_token` 设置 SDK token 并记住配对用的那个
- 设置页：VM ID 行显示 VM、真实设备 token 状态
- `muse_input`：console hook（main 可挂自己的串口命令）、触摸当 talk 键
- `muse_board.h`：`no_ring`（方屏底部进度条）、`touch_talk`、`power_off` 可为 NULL
- 新板型：LCD-1.28 / 1.85C / EchoEar-2ST / ESP-Mosaico（不影响本板）

冲突处理里有一个值得记的：`idf_component.yml` 上游给 `esp_lcd_st77916` / `esp_lcd_touch_cst816s`
加了 185C/1.28 的条目，和本板条目**同名重复**，而 idf-component-manager 对重复 key 报的是
`Cannot parse the manifest file ... / ERROR: Manifest is not valid`——**报错信息完全指不到真正的原因**，
我一开始还去查 YAML 语法。合并成一条、规则列表里加上 `waveshare_s3_touch_lcd_185b` 才对。

## 7. 还差用户动手的部分

插上之后按顺序做：

```bash
# 1) 触发 OTA（板子现在跑 1.2，manifest 已是 1.3）
python esp32/tools/board_serial.py 200 COM3 --cmd ">ota"

# 2) 期望看到的序列
#    I link.ota: ota start: int free ... largest ...
#    I link.ota: ota task up (8xxx-byte internal stack)

# 3) 静置 5 分钟以上，再手动复位，确认仍在 1.3（不回退）——这是第二个坑的验收

# 4) 电量：拔掉 USB 放一会儿，看百分比会不会往下走（1.2 那版永远是 100%）
python esp32/tools/board_serial.py 20 COM3 --cmd ">batt"

# 5) 敲击：等自动息屏（30 s）后敲一下，看 waking (tap)
python "C:\Users\black_samurai\AppData\Local\Temp\tap_cycles.py" 3
```

> `tap_cycles.py` 里有几轮判定；注意 `>nap` 只是 Wi-Fi 小睡**不是息屏**，

## 8. 这条链上还没解决的（如实记录）

1. **敲击的端到端没有真机证据**：`>imu` 三次回读都正常（CTRL7=0x21 CTRL8=0xc1、CAL 全对、
   recoveries=0 rearms=0），但"睡 2 分钟后敲一下能亮"必须有一次物理敲击才算数。代码侧三条根因都有对应修法。
2. **30 s 宽限标记的日志还没抓到**（第二次 OTA 时板子网络抽风，见踩坑记录 0e）。
3. **国内直连 GitHub CDN 时通时断**：板子 `esp-tls select() timeout`，而本机 curl 走代理一切正常。
   测试 OTA 要给足重试窗口，别把网络抖动当固件 bug。长期看值得给 OTA 加"失败自动重试 N 次"。
