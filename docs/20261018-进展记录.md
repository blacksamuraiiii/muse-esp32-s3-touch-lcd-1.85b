## 1. 敲击亮屏：三条根因，三处改动

现场症状（10-17 晚 + 10-18 早）是"睡两分钟后敲不醒，再往后永久死亡，按键亮屏→息屏后同样失效"，
而加速度计一直在正常采样。这不是一个 bug，是**三个独立机制**叠在一起：

### 1.1 根因

1. **I2C 事务被 light sleep 截断**（最可能，且能解释"和睡眠时长相关"）
   `CONFIG_PM_ENABLE` + 自动 light sleep 打开后，任何任务在任何时刻都可能被停钟。
   QMI8658 会把半截写入解析成一次寄存器写；`CTRL8.bit0 (Tap_EN)` 被改写 → 引擎关掉，
   而 `CTRL7/CTRL2`（加速度计）不受影响——正好是"芯片在跑、但检测不到敲击"。
   睡着时 200 ms 进出一次 light sleep，两分钟 600 次，撞上的概率接近 1。
2. **STATUS1 锁存没人清**
   `STATUS1.bit1` 是读清位。亮屏时敲一下没人读 → 位一直置着 → 引擎不再报新事件；
   下次睡下配 HIGH 电平唤醒时，电平早已满足，等于没配。这解释了"按键亮屏→息屏后再敲失效"。
3. **引擎状态机自锁**（保底）
   配置寄存器全对、引擎就是不检测，没有任何可读痕迹。这一条只能靠定期重臂兜。

### 1.2 改动

| 文件 | 改动 |
|---|---|
| `esp32/components/muse/muse_imu_tap.c` | ① 每个 I2C 事务持 `ESP_PM_NO_LIGHT_SLEEP` 锁，事务期间不睡；② 新增 `muse_imu_tap_check(full)`：回读 `CTRL7/CTRL8` 与 init 写入值比对，漂了就重跑 init（10 s 内不重复，防循环），`full` 时再比 `CAL1..CAL4`；③ 新增 `muse_imu_tap_rearm()`：停传感器 → 重写两组参数 → 重开；④ 新增 `muse_imu_tap_diag()` / `muse_imu_tap_log_diag()` 一条 WARN 打全部寄存器 |
| `esp32/components/muse/muse_input.c` | `STATUS1` 每 200 ms 读一次，**不管亮屏还是息屏**（读即清锁存），值只在睡着时用来唤醒；1 Hz 配置校验、60 s 一次全量校验、睡着时 60 s 一次重臂 |
| `esp32/components/muse/muse_imu_tap.h` | 新 API 声明 + 说明为什么亮屏也要读 STATUS1 |

**为什么重臂间隔是 60 s 而不是 10 min**：现场故障是睡下两分钟内就死，10 min 的定时器等不到它。
重臂代价是 10 来个 I2C 事务（约 3 ms），一分钟一次可以忽略；代价窗口里丢一次敲击的概率 0.017%。

### 1.3 现场取证命令（新增）

| 命令 | 作用 |
|---|---|
| `>imu` | 打一行 WARN：`CTRL1/2/7/8/9`、`STATUSINT`、`STATUS1`、`TAP_STATUS`、`CAL1..4`、期望值、自愈次数 |
| `>imu.check` | 强制做一次全量校验（含 CAL），漂了立刻重配 |
| `>imu.rearm` | 强制重臂一次 |

正常时应该是：`CTRL7=0x21(want 0x21) CTRL8=0xc1(want 0xc1) cal=08 20 20 03 90 01 00 20`。
若出现 `config drift: ...` + `tap re-initialised (#1)`，说明根因 1 或 2 确实发生过，自愈已生效。

### 1.4 真机验收口径

1. `tap_cycles.py` 跑 3 轮（每轮等自动息屏 120 s → 敲击）→ 必须 **3/3** 出现 `muse_input: waking (tap)`。
2. 长稳：睡眠 10 分钟后敲击仍能唤醒。
3. 亮屏敲击 → 等自动息屏 → 再敲 → 仍能唤醒（验证根因 2）。
4. 以上任一步失败：贴 `>imu` 输出 + 失败前后的串口日志，按 `docs/踩坑记录.md` §1 的判定表继续。

## 2. TTS 首音时延

### 2.1 先量再改（本机 → eastasia 直连 Azure）

| 场景 | 首音 |
|---|---|
| 冷连接，60 字 | 1.20–1.39 s |
| **同一连接复用，60 字** | **0.45–0.53 s** |
| 冷连接，5 字 | 1.17–1.26 s |
| `style=friendly` 开 / 关（60 字） | 1.43 / 1.29 s |
| 16k/32k vs 24k/48k | 1.39 / 1.43 s（无差别） |
| 去掉标点 `<break>` | 无差别 |

两个结论直接否掉了两个"看起来该做"的优化：
- **首音几乎不随文本长度变化**（5 字 1.17 s vs 60 字 1.39 s）→ "把首句切出来先合成"收益极小，
  反而会因为多一次请求引入接缝，不做。
- 格式和 break 都不是瓶颈，不动。
- 真正的瓶颈是**每次请求都重新握手 TLS**，复用连接省 0.7–0.9 s。

### 2.2 服务端改动（`tts-server/tts_server.py`）

| 改动 | 说明 |
|---|---|
| Azure 连接池 | 全局 LIFO 池（`TTS_AZURE_POOL`，默认 6）。读完整个 body 才归还；半读的连接直接丢弃，不污染下一次；池化连接失效时自动重连一次并重试 |
| 启动预热 | `_prewarm()` 合成一个"嗯"，把首个请求的握手也省掉 |
| 首包阈值 | `STREAM_HEAD_BYTES` 1024 → 512，`waitress send_bytes` 1024 → 512（`TTS_STREAM_HEAD` / `TTS_SEND_BYTES` 可调） |
| 坏包钩子 | `TTS_TEST_HOOKS=1` 时：`?text=BADPACKET` 回 200 + HTML，`?text=BADSTATUS` 回 500 + HTML；`TTS_FORCE_BAD=1` 让**每条**回复都变 200 + HTML |
| `/health` | 增加 `stream_head` / `send_bytes` / `test_hooks` / `azure_pool_idle` / `azure_pool_open` |

**踩坑**：第一版用 `threading.local()` 存连接，**完全没效果**（还是 1.3 s/次）——
流式 worker 是每个请求新 `threading.Thread` 起的，线程本地变量永远是空的。必须用显式池。

### 2.3 固件侧为什么不用改

`muse_tts.c` 已经是"边收边送"：`gate_feed()` 只扣前 8 字节判 MP3 头，通过后立刻进 ring；
上层 `muse_chat_session.cpp` 的 `MP3_BUF` 有 512 KB，`pump_tts()` 一有空位就搬，下一段请求在当前段
读完立刻发出。所以不存在"ring 满导致下一段延迟"的问题，也没有可省的固件侧等待。

### 2.4 实测结果（本地起服务，端口 5051）

| 场景 | 首音 | 说明 |
|---|---|---|
| 冷启动首个请求（未预热） | 1.84 s | 基线 |
| 预热后首个请求 | **0.58 s** | `_prewarm()` 生效 |
| 之后连续请求 | **0.47 / 0.48 / 0.49 / 0.55 s** | 连接池生效，跨 waitress 线程也复用 |
| `/health` | `azure_pool_idle=1, azure_pool_open=1` | 池里确实留着一个热连接 |

### 2.5 部署（需要你在本机执行，密码不在仓库里）

```bash
cd tts-server
MUSE_HOST_PASSWORD='<10.168.2.7 的 root 密码>' \
  python deploy.py
# 镜像 muse-tts:1.5，容器名 muse-tts，端口 5050
curl -s http://10.168.2.7:5050/health
# 期望 "azure_pool_idle": 1，"stream_head": 512
```

部署后板端应看到 `first byte` 从 ~3100 ms 掉到 1500 ms 上下。

### 2.6 坏包丢弃验证（板端）

原理（已实现，v1.1 就有）：前 8 字节攒齐才判断，`0xFF`（MPEG 帧同步）或 `ID3` 才放行；
不通过 → `s_payload_bad=true`、`s_abort=true`，整段丢弃，不重试，回复只留文字。

步骤：
1. 服务端 .env 加 `TTS_TEST_HOOKS=1` 和 `TTS_FORCE_BAD=1`，重新部署。
2. 对板子说一句话。
3. 串口期望：
   ```
   W muse.tts: muse.tts: bad MP3 payload len=41 first=0x3c
   ```
   （`0x3c` 就是 `<`，HTML 的首字节）——字幕正常显示，无杂音、无崩溃、无重试风暴。
4. 把 `TTS_FORCE_BAD` 去掉重新部署，再问一句：应恢复 `first byte=0xFF`/`ID3` 并正常出声，
   说明闸门状态已复位。

## 3. 电池校准

### 3.1 现状与根因

`read_power()` 读 BQ27220 `StateOfCharge (0x1C)` 恒 100%。原理图已核过（J1 → VBAT_IN → 0.01 Ω →
VBAT，SRP/SRN 跨电阻），硬件没问题。根因是**电量计从没按实际电芯配过**：
BQ27220 上电时 `RemainingCapacity == DesignCapacity`（TI 默认值），SoC 天然 100%；
固件里只读 0x1C/0x08，从没写过 Data Flash，也没跑过学习周期。

### 3.2 改动

| 改动 | 说明 |
|---|---|
| `pct_from_mv()` | 单节 Li-ion 开路电压 → 百分比（20 点表，底部故意给宽一点） |
| `read_power()` 兜底 | 当 `gauge >= 95%` 而电压折算 `<= 80%` 时改用电压估算，并 WARN 一次说明原因。限定"gauge 接近满"是为了避免带载压降被误判成快没电 |
| `>batt` 命令 | 把 0x08..0x2E 的标准命令字按字（小端）全量打印，同时打 `int16` 解释；值像电压/电流的自己就能认出来，不猜地址 |
| `muse_board_t.power_debug` | 新增可选回调，别的板子不实现就不出现 |

### 3.3 真机取证

```
>batt
```
期望：能看到电压 3.6–4.2 V 区间、放电时有几十 mA 的电流字（`int16` 为负）。
把这段原始输出贴回来，就能确定 Data Flash 该写什么。

### 3.4 彻底修法（需要你给一个数）

需要**电池标称容量（mAh）**和化学体系（一般是 LiCoO2 / 4.2 V 截止）。拿到之后：
1. 按标称值写 Data Flash 的 `DesignCapacity` / `DesignEnergy`；
2. 做一次学习周期：充满 → 拔线用到自动关机 → 再充满。

在此之前，电压兜底能保证界面上的百分比会动、方向是对的（精度 ±10% 量级）。
