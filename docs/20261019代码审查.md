# 20261019 代码审查：Muse Gadget SDK × 微雪 ESP32-S3-Touch-LCD-1.85B

> 审查对象：本仓库 `esp32/`（v1.3 + 工作区未提交改动），重点在 1.85B 板级支持与休眠/唤醒链路。
> 方法：源码通读 + 与厂商 BSP / 官方例程逐条对照 + 上游 `facebookincubator/muse-gadget-sdk` diff + IDF v6.0.1 源码核对。
> 结论按 P0 / P1 / P2 排；每条给「位置 → 现象/根因 → 修法 → 验收」。
> 确定性标注：`【已确认】`有源码/日志依据，`【高概率】`同类故障常见根因，`【待验证】`需上机测量。

---

## 0. 结论先行

1. **没有发现会砖机、丢数据或烧屏的 P0 级缺陷。** 引脚、面板初始化表、I2C 设备地址与厂商 BSP 逐条一致（见 §1），这部分可以放心。
2. 真正该排期的两条：**关机（deep sleep）前没有把面板/功放/触摸关掉，关机后大概率仍在 mA 级耗电**；**电量计迁移处于半完成状态，`bq27220_create()` 在这台机器上失败，而用来定位它的那段诊断代码读错了寄存器，所以永远查不出来**。
3. 其余是显示链路缺超时（一次 DMA 不回调就永久冻屏）、IMU 加速度平方 int32 溢出（强敲击算成 0）、屏幕只跑了厂商一半的时钟、息屏后前 2 分钟每秒唤醒一次。

## 2. P0

### P0-1 关机后仍在耗电：deep sleep 前没关面板/功放/触摸，BOOT 脚也没上拉

**位置**：`boards/board_waveshare_s3_touch_lcd_185b.c:1133-1143`（`power_off()`）

```c
static esp_err_t power_off(void)
{
    set_brightness(0);
    muse_lcd_bands_run(send_disp_off, NULL);      /* 只发了 DISPOFF(0x28) */
    while (gpio_get_level(TALK_GPIO) == 0) { ... }
    ESP_RETURN_ON_ERROR(esp_sleep_enable_ext0_wakeup(TALK_GPIO, 0), ...);
    esp_deep_sleep_start();
}
```

**现象/根因**【已确认代码路径，功耗数值待测】：

1. **面板只发了 DISPOFF，没发 SLPIN**。`DISPOFF(0x28)` 只是把画面关掉，ST77916 的 charge pump / 偏压仍在工作；本仓库已经有 `panel_sleep(true)`（走 `esp_lcd_panel_disp_sleep` → SLPIN 0x10），但关机路径没用它。
2. **功放没有显式拉低**。PA_EN(GPIO9) 由 `esp_codec_dev` 在 close 时拉低；正常"息屏休息"时 `muse_voice` 会 `muse_audio_power(false)`，但如果用户在**播放回复的瞬间**从菜单关机，PA 仍是高电平。
3. **触摸控制器没进低功耗**。CST816S 的 `0xFE DisAutoSleep` 开机只读不写（见 `touch_report_config()`），若出厂为 1，芯片永不自动休眠。
4. **BOOT 脚没做 RTC 上拉**。`esp_sleep_enable_ext0_wakeup(GPIO0, 0)` 在深睡里用的是 RTC IO，数字域的上拉已经掉了；同仓库的 `board_espressif_box_3.c:135` 就补了 `rtc_gpio_pullup_en()`，1.85B 没补。若这批板的 BOOT 没有外部 10 k 上拉，脚会浮空 → **关机后自己开机**。

**修法**（`power_off()` 改成）：

```c
#include "driver/rtc_io.h"

static esp_err_t power_off(void)
{
    set_brightness(0);
    /* SLPIN, not just DISPOFF: DISPOFF blanks the picture and leaves the
     * panel's charge pump and bias running. GRAM is lost either way and the
     * next boot re-inits the panel. */
    bool sleep = true;
    muse_lcd_bands_run(send_panel_sleep, &sleep);
    muse_lcd_bands_run(send_disp_off, NULL);
    /* The amp must not be left enabled: PA_EN high is tens of mA in "off". */
    gpio_set_direction(PA_EN, GPIO_MODE_OUTPUT);
    gpio_set_level(PA_EN, 0);
    /* ext0 reads the pin through the RTC domain, where the digital pull-up is
     * gone. Without this a floating BOOT wakes the chip the moment it sleeps. */
    rtc_gpio_pullup_en(TALK_GPIO);
    rtc_gpio_pulldown_dis(TALK_GPIO);
    while (gpio_get_level(TALK_GPIO) == 0) {
        vTaskDelay(pdMS_TO_TICKS(20));
    }
    ESP_RETURN_ON_ERROR(esp_sleep_enable_ext0_wakeup(TALK_GPIO, 0), TAG, "wake button");
    esp_deep_sleep_start();
    return ESP_FAIL;
}
```

可选第二步（先量再决定）：`esp_sleep_pd_config(ESP_PD_DOMAIN_VDDSDIO, ESP_PD_OPTION_OFF)` 把 VDD_SPI（8 MB PSRAM + flash 供电）也切掉。S3 没有 `ESP_PD_DOMAIN_PSRAM`，只有 `VDDSDIO`；切了以后唤醒由 bootloader 重新初始化 PSRAM，**必须实测唤醒是否正常**再合入。

**验收**：
- 万用表串在电池上，菜单关机后 30 s 读数 **< 100 µA**（含 PSRAM 供电）；改前先测一次作为基线。
- 关机放置 12 h，开机后 `>batt` 的 SoC 下降 < 3 点。
- 关机后静置 10 min 不发生自发重启（`boots` 计数不变）。

## 3. P1

### P1-1 电量计迁移半完成：`bq27220_create()` 失败，而定位它的诊断读错了寄存器

**位置**：`board_waveshare_s3_touch_lcd_185b.c:590-597`（create）、`:606-626`（TEMP 诊断）、`:1042-1072`（read_power）

**现状**【已确认，代码自述 + 组件源码】：

1. 板级注释写明 `bq27220_create()` 因 Device Number 读回 `0xcf0d`（≠ `0x0220`）而拒绝写模型 → `s_gauge == NULL` → **整条组件路径（模型写入 + getter）现在都没生效**，`read_power()` 实际跑的是 `bq27220_read_word(0x2c)` 兜底分支。
2. 用来查这件事的 TEMP 诊断有两个错：
   - 写完控制字后读的是 **`0x00`**（`const uint8_t mac = 0x00;`），而 BQ27220 的 MAC 数据在 **`0x40`**（组件 `bq27220_reg.h:38 COMMAND_MAC_DATA 0x40`）。读 0x00 只会拿回 Control 寄存器本身。
   - 控制字写成大端 `{0x00, 0x01}`，组件用的是 `(uint8_t *)&control`（小端 `01 00`）。两种写法测的不是同一个东西。
3. `read_power()` 里 `int pct = soc <= 100 ? (int)soc : -1;`：组件的 getter 在 I2C 失败时**返回 0 而不是报错**（`bq27220.c:71-77`），所以一旦 create 修好、走到组件分支，**一次总线抖动就会把电量显示成 0%**，而不是保持上一次的值。
4. 文档 `docs/20261018待办.md` 里写的"与电压折算比对，偏差超 ±20 点改用电压值"在当前代码里**不存在**，只剩 `soc > 100` 才兜底。也就是说：gauge 给出一个"合法但错误"的 SoC 时没有任何拦截——这正是 1.3 之前"恒 33%"的故障形态。

**修法**：

```c
/* 诊断段：读 MAC 数据寄存器 0x40，两种控制字字节序各试一次 */
static void dump_device_number(void)
{
    static const uint8_t ctl_le[2] = { 0x01, 0x00 };   /* 0x0001, LSB first */
    static const uint8_t ctl_be[2] = { 0x00, 0x01 };
    const uint8_t reg = 0x40;                          /* MACData */
    for (int i = 0; i < 2; i++) {
        const uint8_t *ctl = i ? ctl_be : ctl_le;
        uint8_t rd[2] = { 0 };
        if (i2c_master_transmit(s_bq, ctl, 2, 50) == ESP_OK) {
            vTaskDelay(pdMS_TO_TICKS(20));
            if (i2c_master_transmit_receive(s_bq, &reg, 1, rd, 2, 50) == ESP_OK) {
                ESP_LOGW(TAG, "MAC 0x0001 (%s) -> %02x %02x", i ? "be" : "le", rd[0], rd[1]);
            }
        }
    }
}
```

`read_power()` 加两道闸：

```c
/* 两个读数都为 0 只可能是总线没通（真 0% 的电池电压也不会是 0 mV）。 */
if (soc == 0 && mv == 0) {
    return ESP_ERR_INVALID_RESPONSE;   /* 保留上一次有效值，不写 0% */
}
/* gauge 说 80%，电压折算说 40%：以电压为准并留痕（1.3 的行为）。 */
int from_mv = pct_from_mv((int)mv);
if (mv > 3000 && abs((int)soc - from_mv) > 20) {
    ESP_LOGW(TAG, "gauge %u%% vs %d mV (~%d%%): using the voltage",
             soc, (int)mv, from_mv);
    soc = (uint16_t)from_mv;
}
```

**验收**：
- 串口出现 `MAC 0x0001 (le) -> 20 02`（或 `02 20`），据此确认字节序 → 再决定是给组件提 issue 还是在板级绕过。
- 拔插电池/`>i2c.reset` 后连续 10 次 `>batt`，SoC 不为 0，且与电压折算差 < 15 点。
- `bq27220_create()` 成功时日志出现 `Skip battery profile update: verification=full`。

### P1-2 显示发送链路没有超时：一次 DMA 不回调就永久冻屏

**位置**：`boards/muse_lcd_bands.c:135`（`xSemaphoreTake(s_chunk_free, portMAX_DELAY)`）、`:198`（`s_call_done`）、`:106-109`（`wait_band` 死等 `s_band_busy`）

**现象/根因**【高概率】：整条链路依赖 `on_chunk_sent` 这一个 ISR 回调。若 `esp_lcd_panel_draw_bitmap()` 内部 `spi_device_queue_trans` 失败（总线错误、DMA 描述符耗尽），回调不会来 → `s_chunk_free` 永不归还 → 发送任务永久阻塞；同时 `s_band_busy` 永远为 true，LVGL 任务的 `wait_band()` 也永久自旋。**症状与 1.3 修过的"冻屏"完全一样，但这次没有任何自愈路径**，只能拔电池。

另外两处同源隐患：
- `:129` `int rows = s_chunk_bytes / row & ~1;` —— 若面板宽度使 `row > s_chunk_bytes`，`rows == 0`，`for (y += 0)` 死循环。当前 360 px（720 B < 5760 B）安全，但这个文件被 1.75C/2.16/185C/Mosaico 共用。
- `:137-145` 错误分支里直接调 `lv_display_flush_ready()`，而正常路径走 `esp_lv_adapter_display_notify_color_trans_done_from_isr()`，两条通知路径混用可能让适配器的 flush 计数对不上。

**修法**：

```c
/* 每个等待都给上限；超时不是"再等等"，是链路已经坏了，要留痕并让上层能恢复 */
if (xSemaphoreTake(s_chunk_free, pdMS_TO_TICKS(500)) != pdTRUE) {
    s_stalls++;
    ESP_LOGE(TAG, "chunk %d never completed (%u stalls)", k, s_stalls);
    /* 归还一个缓冲继续跑：宁可花屏一帧，也不要冻住整机 */
    xSemaphoreGive(s_chunk_free);
}
```

`wait_band()` 同理加最大迭代次数（如 50 × 100 ms = 5 s），超时后强制 `s_band_busy = false` 并 `lv_display_flush_ready()`，让 UI 继续走。`rows` 加 `if (rows <= 0) rows = 1;` 兜底。错误分支统一改成调用适配器的 notify。

**验收**：人为制造一次失败（例如把 `LCD_CHUNK_BYTES` 临时设成 0 让 `draw_bitmap` 返回错误），确认串口有 `never completed` 且 UI 仍能滑动/亮屏，而不是整机无响应。

### P1-3 IMU 加速度平方在 ±2g 满量程下 int32 溢出：最强的那一下敲击会被算成 0 mg

**位置**：`muse_imu_tap.c:598-605`（`muse_imu_tap_bump_mg`）、`:780-789`（`fifo_peak_mg`）

```c
int32_t sq = (int32_t)ax * ax + (int32_t)ay * ay + (int32_t)az * az;
int32_t rest = (int32_t)ACC_LSB_PER_G * ACC_LSB_PER_G;
if (sq <= rest) return 0;          /* 溢出成负数时，这里直接判成"没有运动" */
```

**根因**【已确认】：`CTRL2_ODR_500HZ_2G` 是 ±2g 满量程，单轴满量程 32767。三轴同时打满时 `3 × 32767² ≈ 3.2e9 > INT32_MAX`，**有符号溢出是 UB**；实际表现是 `sq` 变成负数 → `sq <= rest` → 返回 0。也就是说**敲得越狠，越可能被当成没动**。厂商 BSP 用 ±8g（`qmi8658_set_accel_range(..., QMI8658_ACCEL_RANGE_8G)`），本仓库用 ±2g，更容易打满。

当前 `s_knock_on` 默认关（`muse_input.c:130`），所以只影响 `bump` 日志与 `>knock=1` 的软件敲击检测；**一旦按 `docs/20261019待办.md` 的方案 A 把软件敲击设成默认**，这条就是 P0。

**修法**：

```c
int64_t sq = (int64_t)ax * ax + (int64_t)ay * ay + (int64_t)az * az;
const int64_t rest = (int64_t)ACC_LSB_PER_G * ACC_LSB_PER_G;
if (sq <= rest) return 0;
int bump = (int)((sq - rest) * 1000 / (2 * (int64_t)ACC_LSB_PER_G * ACC_LSB_PER_G));
```

顺带建议把 `aFS` 改到 ±4g（`CTRL2 = 0x05`，ODR 500 Hz / FS 4g），阈值 400 mg 不用重标（仍是绝对量），但敲击不再削顶。

**验收**：用力敲机身，日志 `imu bump` 数值随力度单调增长、不为 0；`>imu` 的 `maxmg` 从 66 升到 1000+。

### P1-4 息屏后前 2 分钟每 1 秒醒一次，而这 1 秒在默认配置下没有任何用途

**位置**：`muse_input.c:66-67`（`REST_WAIT_MS 1000` / `NAP_WAIT_MS 10000`）、`:786-787`、`:587-588`（nap 需 `s_cpu_low` 持续 2 min）

**根因**【已确认】：电池态息屏后，`wait_buttons()` 用的是 `REST_WAIT_MS = 1 s`，只有进入 Wi-Fi nap（需先低功耗满 2 分钟）才切到 10 s。而 1 s 的短睡在默认 `s_knock_on = 0` 时**没有服务对象**：触摸 INT、BOOT、IMU INT1 三条线都是中断唤醒，`check_touch_line()`/tap 轮询只在 200 ms 窗口里才有意义。

代价：每秒一次唤醒 + 每次唤醒跑 4~5 次 I2C 读（`IMU_TAP_VERIFY_MS 1000` 的 4 次 CTRL 回读、`bump` 读），而 `CONFIG_PM_POWER_DOWN_CPU_IN_LIGHT_SLEEP` 没开（CPU 保持供电），单次 1 s 浅睡的收益本就有限。

**修法**：把"1 s"变成只在需要轮询时使用。

```c
int wait_ms = knock_polling ? ASLEEP_WAIT_MS
             : (napping ? NAP_WAIT_MS
                        : (muse_board->wake_lines_reliable ? NAP_WAIT_MS : REST_WAIT_MS));
```

对 1.85B 来说三条唤醒线都在，可以直接用 10 s；给 `muse_board_t` 加一个 `bool wake_lines_reliable;`（1.85B 置 true），避免影响那些靠 1 s 轮询兜底的板。

**验收**：`>imu` 里 `slept` 从 ~1000 ms 变成 ~10000 ms；息屏静置电流下降（万用表/INA219 对比 10 min 平均）。

### P1-5 屏幕只跑 40 MHz，厂商 BSP 是 80 MHz

**位置**：`board_waveshare_s3_touch_lcd_185b.c:769` `io_config.pclk_hz = 40 * 1000 * 1000;`
厂商：`esp32_s3_touch_lcd_1_85B.c:866` `io_config.pclk_hz = 80*1000*1000;`

**影响**【已确认参数差异】：QSPI 4 线，40 MHz ≈ 20 MB/s，一帧 360×360×2 = 259 KB，纯数据时间约 13 ms；40 MHz 下是 26 ms，叠加分带窗口开销后，`frame_ms = 40`（25 fps）基本贴着上限。这也是"滑动时偶发掉帧"最可能的余量问题。

**修法**：直接改 80 MHz，保持现有 chunk（5760 B）与分带不变；若出现 `DMA TX underflow` 再退回 60 MHz。注意 `max_transfer_sz` 不用改，chunk 才是单次事务上限。

**验收**：开机 30 min（Wi-Fi + BLE 同时在线）无 `DMA TX underflow` / `recycle spi transactions failed`；`>fps`（若没有就加一个）稳定 ≥ 25。

## 4. P2

### P2-1 触摸 `0xED IrqPluseWidth` 的写入与注释自相矛盾

`board_...185b.c:647-690`：注释明确写"settings are read, never poked, until a datasheet settles their meaning"，紧接着的代码却 `esp_lcd_panel_io_tx_param(s_tp_io, 0xED, &widen, 1)` 写 `0x14`，而且**每次启动都写**。上一轮"熄屏即亮"事故就是写错 `0xEE` 造成的，同一个坑。
建议：默认只读，写入改成显式命令（`>tp.widen=0x14`），并把实测依据（哪种敲击在哪个值下能唤醒）记进注释。**验收**：默认启动日志里 0xED 只出现一次 `= 0x01`，不再有 `-> 0x14`。

### P2-2 面板版本探测失败时静默选 v2

`:756-765`：`probe_err != ESP_OK` 时 `init_cmds` 保持 v2，只打一条 INFO。现场遇到"花屏"时，这条 INFO 会被当成正常。建议：失败重试 2 次（每次 20 ms），仍失败则 `ESP_LOGW("panel revision unknown, assuming v2")`，并把 `version[]` 原始值一并打出（现在只在成功时打）。

### P2-3 BQ27220 同一地址挂了两个 device handle，且总线 100k/400k 混用

`:600-605` 手工 `i2c_master_bus_add_device(0x55)`，组件内部 `bq27220_create()` 又建了一个（`bq27220.c:442`）。IDF v6 不禁止同地址重复注册（已核对 `i2c_master.c`），功能没问题，但多一份队列/RAM，且两套读法结果可能不一致。
同时 `:576` 总线 100 kHz、`:632` IMU 400 kHz、`:822` 触摸 400 kHz、BQ 100 kHz。BQ27220 支持 400 kHz Fast Mode；每 2 s 一次的 `read_power` 在 100 kHz 上占总线时间是 400 kHz 的 4 倍，与触摸共线时更容易撞车。建议 BQ 也设 400 kHz，或注释清楚为什么留 100 kHz。

### P2-4 IMU 地址注释写反了

`:114` `#define QMI8658_ADDR 0x6B /* IMU, 7-bit; SDO tied low on this board */`
0x6B 是 **SDO 拉高**的地址（0x6A 才是拉低）；厂商 BSP 用的就是 `QMI8658_ADDRESS_HIGH`。地址本身对，注释错，容易误导后来人。

### P2-5 16 MB flash 只用了 8.1 MB，而镜像已经占掉 4 MB 槽的 73.5%

`partitions_muse.csv`：`ota_0` 0x20000–0x420000、`ota_1` 0x420000–0x820000，之后到 0x1000000 **空着约 7.9 MB**。当前 `muse-gadget.bin` = 3,084,288 B（73.5%）。
风险：再加一套 CJK 字库（850 KB）或一组头像资源就可能顶穿 4 MB，`esp_https_ota` 直接报 image too large，而这时只能靠改分区表全片重刷。
建议：下一版把两个槽各扩到 6 MB（`ota_0 0x20000/0x600000`，`ota_1 0x620000/0x600000`，`prod_data` 后移）。**注意这是一次性分区表变更，必须整片刷写，且旧的 OTA 资产不能直接升到新布局**，要和发版脚本一起改。

### P2-6 单文件过大，板级文件被初始化表淹没

- `main/app.c` 3041 行 / 117 KB，一个文件同时承担 BLE、Wi-Fi、VM 鉴权、OTA、UI 状态字符串。建议按 `app_ble.c` / `app_net.c` / `app_vm.c` / `app_ota.c` 机械拆分（先做 `static` 符号审计，再搬函数，不改逻辑）。
- `boards/board_waveshare_s3_touch_lcd_185b.c` 1185 行里 **372 行是两张 ST77916 初始化表**，真正的板级逻辑被挤在中间。把两张表移到 `boards/tables/st77916_185b.h`（`static const` 放头文件里，只有一个编译单元引用，不会重复占空间），板级文件能回到 800 行以内，改逻辑时不用滚屏。

### P2-7 RTC 与 SD 卡两个板载外设完全没接

PCF85063（0x51，INT=GPIO6）与 SDMMC 4-bit（15/14/16/17/12/13）在这块板上都有，固件里一个都没驱动。后果：断电/深睡后时间丢失（每次都要重新对时）、放音只能走网络。不是 bug，但属于"板子能力没用上"，建议要么在 1.4 里接 RTC（开机只校一次，省一次 NTP），要么在 README「已知限制」里写明。

### P2-8 `muse_lcd_bands.c` 是 fork 本地改动，上游没有

与 `facebookincubator/muse-gadget-sdk@main` diff：上游没有 `s_band_done` / `s_band_busy` / `wait_band`，LVGL 用的是自旋等待。本仓库为修"冻屏"自己加了信号量版等待——**这个改动同时作用在 1.75C / 2.16 / 185C / Mosaico 四块板上**，且不在上游测试覆盖里。建议：补一段注释说明为什么不能用上游版本，或者整理成 PR 回上游，避免以后 rebase 时被冲掉。

## 5. 回归清单（现象 → 根因 → 修法 → 验收行）

| 现象 | 根因 | 修法 | 验收 |
|---|---|---|---|
| 关机后电池仍掉电 | 只发 DISPOFF、PA 可能仍高、BOOT 无 RTC 上拉 | P0-1 | 关机电流 < 100 µA；12 h SoC 掉 < 3 点 |
| 电量显示 0% / 与电压明显不符 | 组件 getter 失败返回 0；无电压比对 | P1-1 | `>batt` 连读 10 次无 0；偏差 < 15 点 |
| 组件日志 `Invalid Device Number cf0d` | 诊断读 0x00 而非 0x40；控制字字节序相反 | P1-1 | 日志出现 `MAC 0x0001 (le) -> 20 02` |
| 偶发整机无响应（屏幕定格） | DMA 回调丢失后所有等待都是 `portMAX_DELAY` | P1-2 | 注入失败后 UI 可恢复，串口有 `never completed` |
| 用力敲机身反而没反应 | 三轴满量程平方 int32 溢出 | P1-3 | `bump` 随力度单调增长 |
| 息屏后电流偏高 | 前 2 min 每秒唤醒，默认配置下无用途 | P1-4 | `>imu` 的 `slept` ≈ 10000 ms |
| 滑动掉帧 | 40 MHz 只有厂商一半带宽 | P1-5 | 30 min 无 underflow，帧率 ≥ 25 |

## 6. 不建议做的"优化"

- **不要把 LVGL 绘制缓冲放 PSRAM 后直接交 DMA 送屏**。现有分带 + 内部 RAM 双缓冲是这块板唯一稳的组合，`LCD_CHUNK_BYTES` 再放大只会挤掉 Wi-Fi/BLE 的内部 RAM。
- **不要为了省 flash 去掉分带**，也不要用 `esp_lv_adapter_register_display()` 的默认缓冲策略。
- **不要试图读 PWR 键**（纯硬件电源键，没接到任何 GPIO）。
- **不要动 GPIO45/46**（strapping + LCD D1/D0），也不要把 GPIO0/19/20/43/44 挪作他用。
- **不要把 `frame_ms` 压到 20 ms 以下**：QSPI 带宽 + PSRAM 带宽同时被 Wi-Fi/BLE 抢，收益为负。
