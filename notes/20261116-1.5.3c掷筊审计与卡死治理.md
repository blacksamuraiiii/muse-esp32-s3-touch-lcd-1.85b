| 位置 | 错误 | 原因 | 处置 |

| `muse_jiaobei_ui.c:327` | `implicit declaration of function 'update_shake'` + `conflicting types` | `on_timer()` 在 `update_shake()` 定义（第 387 行）之前调用它，无前置声明 | 在 `on_timer` 前补 `static void update_shake(uint32_t);` |

## 二、审计：性能与卡死面

### 1. 每 50 ms 无条件重写 `transform_scale_x`（已修）

`refresh_display()` 每个 tick 都给两张筊写一次缩放样式，不看值是否变化。LVGL 9 写本地
样式会走失效重绘，100×100 的图带 transform 时每次都要重算图层 —— 这正是 1.5.2d 词卡页
「翻面卡」的同一个坑（当时改成 `s_shown[]` 比对）。现在只在缩放值变化时写。

### 2. 筊面在翻面过程中现画（已修）

`paint_cup()` 是 100×100 像素 × 2×2 超采样的浮点运算（约 16 万样本/张），原来在
「显示的筊面变了」那一刻（正是 300 ms 翻面的中点）在 LVGL 线程里跑，两张就是 32 万样本。
现在按 (筊, 面) 缓存：四种组合首次用到时画一次，之后翻面只换 `lv_image_set_src()`。
代价是 PSRAM 从 2×20 KB 升到 4×20 KB（80 KB），换掉翻面时的重绘尖峰。

### 3. IMU 轮询在 LVGL 线程，单次读最长 1 s（已加退避）

摇一摇走 `muse_imu_read_accel()`，底层 `i2c_master_transmit_receive(..., 1000)`。
本机 1.4 已出现过「LVGL 任务等 I2C 无限超时 → UI 冻住」（`notes/20261019待办.md`）。
现在记单次读耗时，连续 3 次失败或单次 >100 ms 就本页停掉摇一摇并打一条 WARN，点击照旧。

### 4. 金币行硬编码 `/100`（已修）

`金币 %u/100` 改成按 `MUSE_PET_COINS_MAX` 打印，和其它页面一致。

### 5. 第三方图标来源（待确认，未动）

`muse_fortune_art_qiantong.c` 是 135editor 的网页图形按用户 2026-11-14 决定「网上找图标
直接用」原样嵌入的。仓库是公开仓库，这类素材的商用/再分发授权需用户确认；本版未改。

## 三、「整页卡死」治理

用户现象：1.5.3b 词音已正常，但用起来容易整页卡住不动（没有说是必须重启）。

代码面能证实的阻塞路径与处置：

| # | 机制（可读代码证实） | 处置 |
|---|---|---|
| F1 | 所有界面音效都在 LVGL 线程里同步写完：单次最长 330 ms，且要 `xSemaphoreTake(s_write_lock, portMAX_DELAY)` 排队 | 加 `muse_sfx` 任务（栈在 PSRAM，优先级 3，低于语音 4 / 界面 5），`muse_audio_sfx()` 改为投递即返回；新增 `muse_audio_sfx_sync()` 保留阻塞语义给「低电量提示音」这类要看结果的调用 |
| F2 | `muse_audio_power()` 与写入路径不互斥（原设计「两个锁不嵌套」）：`esp_codec_dev_close()` 可以撞进正在 `esp_codec_dev_write()` 的任务，那块写要等满 `DEFAULT_WAIT_TIMEOUT`=1000 ms；音频是 20 ms 分块写的，卡顿逐块叠加 | 开关编解码器前先拿 `s_write_lock`，锁序固定为 `s_lock → s_write_lock`（没有任何路径反向嵌套） |
| F3 | 卡死时无法判断「线程被阻塞」还是「渲染/刷屏卡住」还是「堆耗尽」 | `frame_tick` 加断档探针：帧间隔 >150 ms 打 `muse_ui: frame gap N ms (int 空闲/最大块, psram 空闲)` |

未证实：本版**没有**定位到用户那次卡死的唯一根因。上述三条是代码里能证实的阻塞面，
外加一条把下次复现变成日志的探针。判据：刷入后复现一次，串口若有
`muse_ui: frame gap ...` 行，按行里的堆数字与间隔长短区分「被阻塞」「堆紧张」「刷屏慢」；
若卡住时**没有**断档行，说明 LVGL 线程活着、问题在渲染/刷屏侧，下一步查显示刷屏与图层分配。
