# 1.5.3c：掷筊合入的代码审计 + 「整页卡死」治理（2026-11-16）

合入 `feat/jiaobei-20261114`（掷圣杯 + 今日运势子页），版本 `1.5.3b → 1.5.3c`，
同时处理用户 2026-11-16 反馈的「1.5.3b 词音正常了，但容易卡死、整个页面卡住不动」。

## 一、审计：分支原状编不过（P0）

`feat/jiaobei-20261114` 是带着编译错误推上远端的（`build-153b-test.log` 复核），
三处：

| 位置 | 错误 | 原因 | 处置 |
|---|---|---|---|
| `muse_jiaobei_ui.c:327` | `implicit declaration of function 'update_shake'` + `conflicting types` | `on_timer()` 在 `update_shake()` 定义（第 387 行）之前调用它，无前置声明 | 在 `on_timer` 前补 `static void update_shake(uint32_t);` |
| `muse_jiaobei_ui.c:387` | `static declaration follows non-static declaration` | 上一条的连带（隐式声明成了外部符号） | 同上 |
| `muse_jiaobei_ui.c:448` | `assignment to 'const uint8_t *' from 'uint16_t *'` | `lv_image_dsc_t.data` 是 `const uint8_t *`，直接赋 `uint16_t *` | 改成 `(const uint8_t *)s_cup_buf[i][f]` |

教训：测试分支在主机侧只有 `muse_jiaobei.c` 有 harness（纯逻辑），UI 层没有任何主机侧
检查，靠「推上去再说」就漏到了远端。

## 二、审计：性能与卡死面

### 1. 每 50 ms 无条件重写 `transform_scale_x`（已修）

`refresh_display()` 每个 tick 都给两张筊写一次缩放样式，不看值是否变化。LVGL 9 写本地
样式会走失效重绘，100×100 的图带 transform 时每次都要重算图层 —— 这正是 1.5.2d 词卡页
「翻面卡」的同一个坑（当时改成 `s_shown[]` 比对）。现在只在缩放值变化时写。

### 2. 筊面在翻面过程中现画（已修）

`paint_cup()` 是 100×100 像素 × 2×2 超采样的浮点运算（约 16 万样本/张），原来在
「显示的筊面变了」那一刻（正是 300 ms 翻面的中点）在 LVGL 线程里跑，两张就是 32 万样本。
现在按 (筊, 面) 缓存：四种组合首次用到时画一次，之后翻面只换 `lv_image_set_src()`。
代价是 PSRAM 从 2×20 KB 升到 4×20 KB（80 KB），换掉翻面时的重绘尖峰。

### 3. IMU 轮询在 LVGL 线程，单次读最长 1 s（已加退避）

摇一摇走 `muse_imu_read_accel()`，底层 `i2c_master_transmit_receive(..., 1000)`。
本机 1.4 已出现过「LVGL 任务等 I2C 无限超时 → UI 冻住」（`notes/20261019待办.md`）。
现在记单次读耗时，连续 3 次失败或单次 >100 ms 就本页停掉摇一摇并打一条 WARN，点击照旧。

### 4. 金币行硬编码 `/100`（已修）

`金币 %u/100` 改成按 `MUSE_PET_COINS_MAX` 打印，和其它页面一致。

### 5. 第三方图标来源（待确认，未动）

`muse_fortune_art_qiantong.c` 是 135editor 的网页图形按用户 2026-11-14 决定「网上找图标
直接用」原样嵌入的。仓库是公开仓库，这类素材的商用/再分发授权需用户确认；本版未改。

## 三、「整页卡死」治理

用户现象：1.5.3b 词音已正常，但用起来容易整页卡住不动（没有说是必须重启）。

代码面能证实的阻塞路径与处置：

| # | 机制（可读代码证实） | 处置 |
|---|---|---|
| F1 | 所有界面音效都在 LVGL 线程里同步写完：单次最长 330 ms，且要 `xSemaphoreTake(s_write_lock, portMAX_DELAY)` 排队 | 加 `muse_sfx` 任务（栈在 PSRAM，优先级 3，低于语音 4 / 界面 5），`muse_audio_sfx()` 改为投递即返回；新增 `muse_audio_sfx_sync()` 保留阻塞语义给「低电量提示音」这类要看结果的调用 |
| F2 | `muse_audio_power()` 与写入路径不互斥（原设计「两个锁不嵌套」）：`esp_codec_dev_close()` 可以撞进正在 `esp_codec_dev_write()` 的任务，那块写要等满 `DEFAULT_WAIT_TIMEOUT`=1000 ms；音频是 20 ms 分块写的，卡顿逐块叠加 | 开关编解码器前先拿 `s_write_lock`，锁序固定为 `s_lock → s_write_lock`（没有任何路径反向嵌套） |
| F3 | 卡死时无法判断「线程被阻塞」还是「渲染/刷屏卡住」还是「堆耗尽」 | `frame_tick` 加断档探针：帧间隔 >150 ms 打 `muse_ui: frame gap N ms (int 空闲/最大块, psram 空闲)` |

未证实：本版**没有**定位到用户那次卡死的唯一根因。上述三条是代码里能证实的阻塞面，
外加一条把下次复现变成日志的探针。判据：刷入后复现一次，串口若有
`muse_ui: frame gap ...` 行，按行里的堆数字与间隔长短区分「被阻塞」「堆紧张」「刷屏慢」；
若卡住时**没有**断档行，说明 LVGL 线程活着、问题在渲染/刷屏侧，下一步查显示刷屏与图层分配。

## 六、2026-11-16 晚：真机卡死现场与字库缺字

### 6.1 卡死现场取证（1.5.3c 首刷后）

用户报「卡在这个页面了」并附两张屏摄。串口同步抓取（`serial-frozen.log`，t=229–250 s）

结论：**屏幕显示通路卡住，系统本身活着**，根因未确认。

- 画面是**多页残影拼接**：标题「今日运势」＋副标题「仅供娱乐」（运势子页）× 中部
  「学习」「小游戏」卡片（互动主页）× 底部「连续圣杯 ×3，神明应允」「金币 4/100」
  （掷筊页）。四个分带各自停在最后一次成功的写入上，说明断的是「往面板送分带」，
  不是某一页的绘制。
- 系统活着：`>status` 控制台有应答（`fw:1.5.3c`），`link.heartbeat` 每 5 s 照打。
- **没有任何 `muse_lcd_bands` 报错**（无 `band never completed`、无 `chunk never
  completed`），22 s 窗口内也没有 `frame gap` 行 —— 这两种「有超时兜底」的路径都没触发，
  指向「有调用者永久阻塞在 `portMAX_DELAY` 上」这一类。

据此加的四道防线（都已刷入，见 6.3）：

| 位置 | 原状 | 改法 |
|---|---|---|
| `queue_band()` 队列满 | 丢分带、`s_band_busy=false` 就返回，**不释放 flush** | 丢的时候补 `lv_display_flush_ready()` 并打 E 日志（否则 LVGL 永远等这一次 flush） |
| `muse_lcd_bands_run()` | 三处 `portMAX_DELAY` | 全部 2 s 超时；拿不到锁/队列满/没应答都打 WARN 放行（调用方是 UI 线程，屏保路径） |
| 心跳行 | 只有堆与时延 | 加 `ui=<帧数>/<分带数>`：UI 帧冻结＝界面线程被阻塞；帧在涨而分带不动＝送屏通路卡住 |
| 断档探针 | 每次卡顿都打 | 只报开机 15 s 之后的（开机本来就慢，避免噪声） |

下次复现的判据：串口心跳里 `ui=` 两个数哪一个不动。

### 6.1.1 更正（2026-11-16 21:5x，真因找到）

用户第二组屏摄把真因坐实：**不是分带/SPI 通路，是 `show_page()` 的隐藏清单漏了两页**。

`muse_interact_ui.c` 的 `show_page()` 用一长串 `lv_obj_add_flag(x_page, HIDDEN)` 逐个隐藏页面，
新增的 `s_fortune_sub_page`（运势子页）与 `s_jiaobei_page`（掷筊板）**没有加进这一串**。于是：

- 这两页一旦显示过就再也不隐藏，永远压在其它页之上 —— 屏摄①里运势子页的
  「仅供娱乐」＋「抽签/掷筊」卡片和掷筊板的双筊、金色留言行同时压住互动主页；
- 掷筊板整页那层透明 touch 对象也一直活着，**吞掉所有点击** —— 所以「点不动、像卡死」，
  而且「没法再次掷圣杯」（点击落到那张看不见的板上）；
- 掷筊板 50 ms 定时器在别的页也照跑，每 tick 改样式 → 一直在重绘那层浮在上面的内容，
  看上去就是整页卡住不动。

**这不是 1.5.3b 的老卡死**：本仓 6.1 里的分带判断是错的方向，四道防线是基于错误假设加的。
它们本身无害（`queue_band` 丢分带不释放 flush 是真漏洞、`ui=` 计数与 `muse_lcd_bands_run`
超时是加固），保留作保险，但真因就是上面这一条。

修法：把两页补进隐藏清单，并在注释里写明「本文件每个页面都必须在这张表里」。
核对命令：`grep -o "s_[a-z_]*_page" | sort -u` 与
`grep "lv_obj_add_flag(s_.*_page, LV_OBJ_FLAG_HIDDEN)"` 的数量必须相等（现在 18/18）。

同类第二刀：金币不足时掷筊原来是**静默返回**（2026-11-14 的决定），现在改成在留言行写
「金币不够（需 5 枚）」，与 worker 拒绝时同文案 —— 用户 2026-11-16 把「点了没反应」
当成了功能坏了。

### 6.2 字库缺「筊」

`掷圣杯` 标题与「掷筊，每次 -5 金币」里的「筊」是空白。原因：`gen_cjk_noto_font.sh` 只收
GB2312 的 6763 汉字，「筊」是 GBK 独有（U+7B4A）不在其中。改法：脚本里加一行
`EXTRA="0x7B4A"` 并入 `-r`，不手改生成文件（每次重跑都会整体重写）。

验证：`unicode_list_8[]` 从 3401 项变 3402 项，新增偏移 9829 → 码位 `0x7b4a`；
`glyph_dsc` 从 7432 变 7433；行高仍是 20/5（生成脚本里的 pin 生效）。

- 刷机：`flash_153c.ps1` exit=0，四次 `Hash of data verified.`。

  `ui=456/65`（帧约 25/s，与 40 ms 帧一致）。
