## 3. 音量按钮位置（已定稿：y = -ring_in/3，更靠腰侧）

`esp32/components/muse/muse_ui.c` `build_answer()`：

```c
spk_y = -ring_in / 3;                       // 原 -ring_in * 5 / 8，中途试过 -ring_in / 2
int d = ring_in - spk_r - 4;                // 不变（spk_r = 36）
spk_x = -(int)sqrtf((float)(d * d - spk_y * spk_y));
```

**待办里「把 -4 改成 -24」会移到中间、压在人脸上**：`d` 变小 → `|spk_x|` 变小。按钮横向位置只由纵向高度决定
（圆方程反解），所以想让它离脸更远就得往下移。

185B（ring_in=170，360 屏）实测三种高度的差别（模拟器 360 渲染 + 像素掩膜度量）：

| y | 中心 | \|x\| | 外缘距屏心 | 距最近美术像素 |
|---|---|---|---|---|
| `-5/8·ring_in` | -75,-106 | 75 | 166 | 被美术盖住（原始问题） |
| `-1/2·ring_in` | -99,-86 | 99 | 167 | 15 px |
| **`-1/3·ring_in`** | **-118,-57** | **118** | **167** | **33 px** |

外缘恒为 167（环内缘 170，仍在环内）；回复页尺寸三种高度都一样（`17 x 3 heard` / `14 x 7 read`），
所以下移不牺牲文字行数。**定稿取 -1/3：距脸净空从 15 px 翻到 33 px。**

## 4. 敲击唤醒（已完成，未上机验证）

### 引脚已核实（原理图 Rev1.1，6/9-Axis 块，U15 QMI8658A）
- INT1（pin4）→ 网络名 `QMI_INT1` → R51（0R）→ **GPIO8**
- INT2（pin9）→ **NC**
- I2C 地址 0x6B（SDO 接地）；GPIO8 另引到排针 J6 第 2 脚
- 核实方法：下载官方仓库 `hardware/ESP32-S3-Touch-LCD-1.85B Rev1.1.pdf`（URL 里 `%20` 要保留），
  用 pymupdf 按坐标取词，`QMI_INT1 / R51 / 0R / GPIO8` 四个词在同一行（x 546→584, y 387）

### 代码
| 文件 | 内容 |
|---|---|
| `esp32/components/muse/muse_imu_tap.c` / `.h` | QMI8658A tap 引擎：accel 500 Hz、单/双击、事件送 INT1；`muse_imu_tap_tapped()` 读 STATUS1.bit1 并清位 |
| `esp32/components/muse/muse_board.c` / `.h` | 新增 `muse_gpio_wake_line_add(gpio, wake_high)`：把外设中断线并入 `muse_gpio_buttons_wait()` 的 light-sleep 唤醒集合 |
| `boards/board_waveshare_s3_touch_lcd_185b.c` | init 里给 0x6B 建 i2c device、调 tap init、把 GPIO8 注册为唤醒线 |
| `esp32/components/muse/muse_input.c` | 睡着时每 200 ms 读一次 tap 状态，命中即 `set_asleep(false, "tap")` 亮屏 |

### 两条唤醒通道（都留着）
1. GPIO8 电平唤醒（INT1 推挽）→ 睡着了敲一下立刻醒，延迟 ~几十 ms；
2. STATUS1 轮询兜底（200 ms 一次）——STATUS1.bit1 是**读清**的锁存位，
   即使电平沿没抓到（INT1 可能只随 DRDY 出脉冲），下一次轮询也能补上。

### 寄存器要点（QMI8658A datasheet Rev A）
- 地址：CTRL1=0x02、CTRL2=0x03、CTRL7=0x08、**CTRL8=0x09**、**CTRL9=0x0A**、CAL1..CAL4=0x0B..0x12、
  STATUSINT=0x2D、STATUS1=0x2F、TAP_STATUS=0x59
- 配置流程（§10.3/10.4）：先 CTRL7.aEN=0 → 写两组参数（CAL4_H[7:4]=0x01/0x02 选组）→ 每次发
  CTRL9=0x0C 后等 STATUSINT.bit7 → 回写 CTRL9=0x00 应答 → CTRL8 置 bit6(送INT1)+bit0(Tap_EN) →
  CTRL2 设 500 Hz → CTRL7.aEN=1。**CTRL8.bit7=1** 让握手走 STATUSINT，配置过程不会拉 INT1
- 当前参数（datasheet 参考值，500 Hz）：PeakWindow=20、TapWindow=50、DTapWindow=250、
  Alpha=8(0.0625)、Gamma=32(0.25)、PeakMagThr=800(0.8g²)、UDMThr=400(0.4g)——真机敲不灵/太灵就调 `muse_imu_tap.c` 顶部宏

### 已修正草稿里的错
`qmi8658_tap/` 那份草稿（保留作参考，未并入构建）地址整体错位一格：
把 CTRL7 当 0x07、CTRL8 当 0x09 却又同时把命令寄存器写成 0x0A；另外
`gpio_wakeup_enable(GPIO8, GPIO_INTR_ANYEDGE)` 是非法参数（该 API 只收 HIGH/LOW 电平），
且从未写第二组参数（PeakMagThr/UDMThr 为 0 会一直误触发）。位模式基本对，地址全错。

| 场景 | 结果 |

| WSL 本机流式（35 字） | 200，首字节 1.76–2.81 s，40752 B |

**发现（影响后续选择）**：edge-tts 这条路已经不可用——实测 WSS 握手 403
（`Sec-MS-GEC` 令牌/版本漂移）。因此默认不挂回退，否则失败路径要多等约 7 秒才报 502。
要应急可 `TTS_FALLBACK=edge`。另外 **pitch 单位两边不同**（Azure 百分比 / edge-tts Hz），
已按后端分别校验，写错回落默认值、不打断朗读。

免费额度：F0 约 50 万字符/月；超限时服务返 502，板子按「非 MP3」丢弃、只留文字。

### 板子端首轮实测：没声音 → 定位到 Flask 开发服务器（已修）

板子首轮请求的症状（串口）：

    E HTTP_CLIENT: Incomplete chunked data received 0
    W muse.tts: TTS request failed: ESP_ERR_HTTP_INCOMPLETE_DATA (url 391, budget 2048)
    E HTTP_CLIENT: Incomlete data received, ret=0, 1440/51264 bytes   ← 51264 的包只收到 1440

排除法：容器日志显示服务端 `streamed 51264 bytes in 4.23s`（发满了）；WSL 用同一 URL 收满 51467 B；
再拿**裸 socket 探针**占 5050 端口回放同一份 51264 B 载荷（绕开 werkzeug），**板子完整放出来了**。
结论：责任在 Flask 开发服务器/werkzeug 这一层，与分块编码无关（Content-Length 那条路同样卡在 1440 B）。

处置与验证：服务改用 **waitress**（镜像 muse-tts:1.4，`TTS_SERVER` 默认 waitress），重新部署后板子
`I muse.tts: TTS got 13248 bytes (content-length -1, first byte 3107 ms, total 3894 ms)`，
`reply audio: 24000 Hz, 1 ch, 48 kbps`，正常出声。**板子端到端 TTS 已验证。**

## 5b. 敲击唤醒已知问题：长时间睡眠后失效（留待下次修）

真机实测（2026-10-17 晚，用户操作 + 串口实证）：

| 场景 | 结果 |
|---|---|
| 刚刷完/刚重启后敲击 | ✅ 能点亮（t=64.5s 抓到 `muse_input: waking (tap)`） |
| 长时间睡眠（约 2 分钟以上）后敲击 | ❌ 无效；连续 3 轮脚本测试 0/3 唤醒 |
| 按键点亮屏幕 → 30 秒自动息屏 → 敲击 | ✅ 正常 |

故障现场寄存器（临时诊断固件，睡时每 200 ms 打印一行）：

```
W muse.imu: poll: STATUSINT=0x00 STATUS1=0x00 TAP_STATUS=0x31 int1=0 a=-1051/-691/14670
```

- 加速度计**在正常跳动**（噪声 ±600 LSB，Z≈0.90 g）→ 芯片在跑、安装面安静（排除灵敏度与台面振动）
- `STATUS1` / `STATUSINT` 恒 0、`TAP_STATUS` 停在旧的 `0x31`（Z 轴/单击）→ 引擎没检测到新敲击
- `int1=0` → INT 线没被拉高（不是线卡死在高电平）

推论：与**睡眠时长**相关，`WIFI_NAP_MS = 2 分钟`（Wi-Fi 小睡门限）与故障时间点吻合；但加速度计仍在
转换，说明不是整片 soft reset。待查是 tap 引擎配置（CTRL8.bit0/bit6 或 CAL 参数）丢失，还是引擎停摆。

下次的验证路径（工具已备好）：

1. 在 poll 里加读 `CTRL7(0x08)`、`CTRL8(0x09)`、`CAL1..CAL4(0x0B..0x12)`，对比「短睡正常」与「长睡失效」两组值。
2. 若不一致：poll 检测到配置漂移时重跑 `muse_imu_tap_init()`（重写 tap 参数 + CTRL8/CTRL2/CTRL7）。
3. 测试脚本 `C:\Users\black_samurai\AppData\Local\Temp\tap_cycles.py`（等自动息屏 → 等敲击 → 报 OK/FAIL，可多轮）。
   注意 `>nap` 只是 Wi-Fi 小睡，**不是息屏**；息屏由无操作自动触发。
4. 诊断补丁形态（复用照抄）：新增 `muse_imu_tap_poll(bool always_log)` —— 先读 STATUSINT(0x2D)、
   再读 STATUS1(0x2F)（读即清标志）、再读 TAP_STATUS(0x59) 与 0x35 起 6 字节加速度，打一行 WARN。
