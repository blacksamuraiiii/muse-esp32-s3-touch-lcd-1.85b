## 1）屏幕触摸有时乱跳，过一会才恢复

**现状（已核对源码，修正原文档两处说法）**：

- 触摸是 `esp_lcd_touch_cst816s`，**设备级 400 kHz**：板级在 `tp_io_cfg.scl_speed_hz
  = 400000`（`board_waveshare_s3_touch_lcd_185b.c:976`）显式覆盖了总线的默认速度，
  而总线本身是 100 kHz（同文件 `:691` 的 `i2c_cfg.master.clk_speed`，整条总线由
  `espressif/i2c_bus` 统一持有）。驱动 2.0.2 的宏里自带 `.scl_speed_hz = 100000`，
  被这一行盖掉。（原文写"100 kHz，不是 400 kHz"，方向反了。）
- 不是"零滤波"。板上已经有三层针对这颗芯片的保护，改之前必须先排掉：
  1. `touch_autosleep()`：写 `0xFE DisAutoSleep`，面板亮着时控制器常扫
     （否则第一下点击会被吞）；面板灭时放它自己睡，代价是灭屏后第一下
     触摸只唤醒不落点。
  2. `check_touch_line()` 的 80 ms 入睡脉冲过滤：灭屏瞬间控制器会吐一个
     假低脉冲，`s_stat_slept_ms < 80` 直接丢掉（`muse_input.c`）。
  3. 闹钟 6 s grace 窗口（`ALARM_TOUCH_GRACE_US`）：响铃时面板唤醒会
     产生一个幻影按，talk 边沿要等面板稳定才认。
- `touch_report_config()` 只读 `0xA7/0xED/0xFA/0xFE` 四个寄存器并打日志。
  仓库家规写得很明白：**这几个寄存器只读不写**——上一轮误把 `0xEE` 当
  IrqPluseWidth 写进去，代价是灭屏立刻被唤醒，整夜亮屏。

**成因排序（可能性从高到低）**：

1. **CST816S 报跳点**：面板电源态切换、QSPI 刷屏干扰、手指悬空未落下时，
   控制器会吐跳变很大的坐标；驱动只校验范围，原样交给 LVGL。
2. **I2C 读数损坏**：触摸与 RTC(0x51)、电量计(0x55)、codec 共用一条总线，
   100 kHz 下读坏一次就出一个越界点。`muse_i2c_register()` 已经登记了
   "总线整体失联"的恢复路径，说明这事以前发生过。
3. **LVGL 侧无防抖**：一次误报就是一次 PRESSED，没有"连续两次一致才认"。

**下一步（先量，不改）**：

抓日志最小步骤——在 `poll_buttons()` 的"新按下"分支加一行临时日志
（`board_waveshare_s3_touch_lcd_185b.c`，`if (pressed && !tp_down)` 内，
`tp_on_face` 算完之后）：

```c
ESP_LOGI(TAG, "tp press %d,%d face=%d", (int)p.x, (int)p.y, (int)tp_on_face);   /* 临时：抓乱跳 */
```

然后 `idf.py -p COMx monitor`，用 `muse` 控制台或串口抓 10 分钟正常使用 +
一次复现。判读口径：

- 出现**单个坐标跳变点**、下一个采样又回来 → 驱动层误报，做软件滤波。
- 出现**越界坐标**（<0 或 >360）或 `esp_lcd_panel_io_rx_param` 报错 →
  先查 I2C，不是滤波能救的。
- 完全没有 `tp press` 却出现界面跳动 → 问题不在触摸，去看 LVGL 绘制
  缓冲（PSRAM 上做 DMA 的老坑）。

**滤波方案（确认是跳点后再上，约 20 行）**：坐标跳变超过一屏合理位移
（一帧内手指不可能移动的距离）直接丢该点；同一位置连续两次采样一致才认
按下；抬起后 100 ms 内的新按下先怀疑（灭屏脉冲窗口，与已有 80 ms 先例
同一思路）。**不要**动 `0xEE/0xFA` 寄存器，除非拿到 Rev datasheet。

**上滤波之前先做一次零成本 A/B**：`:976` 的 `tp_io_cfg.scl_speed_hz` 从
400000 改成 100000 重跑一轮。异常消失 → 主因是采样完整性，滤波只需留
"越界丢弃"；异常照旧 → 回 400000，按上面的 20 行方案做。

## 2）屏幕说话打断回复——B 方案打偏了（本项最重要）

**机制先摆清。1.85B 上有两条"屏幕说话"的路，只有一条被 1.5e 挡了：**

| 路径 | 实现 | 1.5e 是否挡住 |
|---|---|---|
| A. 点脸上的 mic 图标 | `muse_ui.c` 的 `on_touch_mic`，PRESSED/RELEASED 发 TALK_PRESS/RELEASE | ✅ 已加模式门 |
| B. 按住脸（头像）500 ms | 板级 `poll_buttons()` 的 `tp_talking`，到 500 ms 直接 `ev \|= MUSE_BTN_TALK_PRESS` | ❌ 没挡 |

**而 1.85B 上生效的是 B，不是 A**：`muse_ui.c` 里 mic 图标的点击能力挂在
`if (muse_board->touch_talk)` 下，而 `touch_talk` 的语义是"没有物理 talk
键、靠屏幕 mic 出边沿"（`muse_board.h:85`）。1.85B 有 BOOT 键，结构体里
没置这个位（全仓库只有 `board_ostb_echoear_2st.c` 和
`board_reterminal_sticky.c` 置了），所以：

- 这块板上的 mic 图标只是**提示图形**，不可点，`on_touch_mic` 永不注册；
- `314daa4` 给 `on_touch_mic` 加的门，在 1.85B 上是死代码，只对上面两块板
  有用；
- 用户报的"刷到屏幕就打断"，实际是 B 路径：按住（或倒扣贴桌、口袋里压住）
  500 ms 就开一轮对话，`talk_button()` 收到 TALK_PRESS 后只要不是睡着/菜单/
  配对确认就直接 `post(MUSE_PTT_DOWN)`，回复放到一半也被打断。

**修法（最小改动，3 行）**：在 `poll_buttons()` 的按下时刻记一次"这次按下
开始时是不是空闲"，不是空闲就整次按下都不许说话：

```c
static bool tp_blocked;   /* 这次按下开始时不空闲：整次按下都不算说话 */

    if (pressed && !tp_down) {
        lv_point_t p = { 0 };
        lv_indev_get_point(s_touch_indev, &p);
        tp_down = true;
        tp_on_face = muse_ui_face_active() && !muse_ui_face_control_at(p.x, p.y);
        tp_press_tick = xTaskGetTickCount();
        tp_talking = false;
        /* 回复/思考/录音进行中，屏幕不是打断键：打断只留给 BOOT。 */
        tp_blocked = (muse_state_mode(NULL) != MUSE_MODE_IDLE);
    } else if (pressed && tp_down && tp_on_face && !tp_talking && !tp_blocked) {
        if ((xTaskGetTickCount() - tp_press_tick) >= pdMS_TO_TICKS(TOUCH_HOLD_MS)) {
            tp_talking = true;
            ev |= MUSE_BTN_TALK_PRESS;
        }
    }
```

抬起分支已经是"只有 `tp_talking` 才发 RELEASE"，天然配对，不用改。
1.85C（`board_waveshare_s3_185c.c` 同一套 `TOUCH_HOLD_MS`）要一起改，
否则两块板行为不一致。

**备选（更彻底，但动得多）**：让 B 路径也走
`muse_input_touch_talk()`（把 touch 边沿集中到 `s_touch_talk_events`），
然后在 `muse_input.c` 的 `ev |= touch` 之前加一道统一门。好处是"屏幕说话"
只剩一个入口，将来加板不会再漏；代价是改 `muse_board` 的
`poll_buttons` 契约，所有带触摸的板都要跟着改。**当前不建议**，先把 3 行
版本刷进去验证。

**保留 1.5e 已做的 `on_touch_mic` 门**：它对那两块 `.touch_talk = true` 的
板是对的，删了反而退化。但要清楚它跟本板无关。

**残留风险（写进验收单）**：`talk_down` 在 `talk_button()` 里是 BOOT 和
触摸共用的。BOOT 按下到 `MUSE_MODE_LISTENING` 落地之间有一个轮询窗口
（`POLL_MS = 10 ms`），这个窗口里屏幕按下会被门放行，它的抬起就会发出
TALK_RELEASE，把 BOOT 正按着的对话掐断。概率低（要求 10 ms 内同时按下），
要彻底消掉得按来源分别记 `talk_down`，改动比收益大，先记着。

## 3）WiFi 在线，Muse 连接却重连 connecting

**两层要分开（原文档这里说反了，已修正）**：

- WiFi 关联（`esp32/main/wifi_mgr.c`）没断，指数退避无限重连；
- 断的是 Muse 的 Noise 会话（`muse_link` 显示 Connecting）：
  `muse_chat_session.cpp` 每 20 s 发 ping（`PING_US`），60 s 内一个字节都
  没回来就 `drop_connection("server went quiet")`（`DEAD_US`）。
- 电源档实际取值（`muse_voice.c:934`）：**USB → FULL，电池醒着空闲 →
  DOZE，息屏休息 → REST**。不是"睡醒是 REST"；另外对话进行中已经强制
  FULL（`muse_voice.c:921/976`），所以"会话活跃期用 FULL"这条其实已经
  做到了，真正的问题是**回合之间的 DOZE 撑不住 20 s ping 的往返**。
- 还有个设计内的断网：低功耗持续 10 分钟会整段关 Wi-Fi
  （`WIFI_NAP_MS`）。但那种情况下 WiFi 状态本身就是断的，与用户描述的
  "WiFi 在线"不符，可以先排除。

**成因排序**：

1. AP 对睡着的 station 老化激进 / DTIM 太长，DOZE 下 ping 包被延迟累积到
   60 s 超时。
2. 网关侧空闲超时：长待机后先关了会话，板子下次用时才发现。
3. 射频：RSSI 弱、漫游、信道干扰，WiFi 层看着连着，实际丢包。
4. **不是故障的一类，先排掉**：10 分钟空闲会主动断会话（`IDLE_CLOSE_US`，
   `muse_chat_session.cpp:117/2186`），之后 `s_auto_next_us = INT64_MAX`，
   下一轮对话才重连；UI 的 "Connecting" 来自
   `LED_STATE_WIFI_CONNECTED → MUSE_LINK_CONNECTING`（`muse_glue.c:749-754`），
   即"WiFi 好、WS 未建"就显示 Connecting。这类不动电源策略。

**下一步（日志判读口径，一句就能分开前两种）**：`drop_connection()` 的
`why` 字符串已经区分了方向——

- `ping failed`：**我方发不出去**，问题在射频/电源档，往第 1 条查；
- `server went quiet`：60 s 内**对端一个字节都没回**，往第 2 条查（也可能是
  第 1 条把回包全丢了，所以要配合 RSSI 看）。

抓法：`idf.py -p COMx monitor 2>&1 | grep -E "went quiet|ping failed|wifi|disconnect|ps="`，
复现一次后对着时间轴看掉线前 60 s 内的 RSSI 与电源档。

**候选（按代价排序，等你拍板）**：

1. 回合之间也用 DOZE 但不用 REST（当前已是），只把 ping 的**发送**时机
   从 20 s 拉到 15 s——治标，先不做；
2. 空闲态改 FULL：功耗换稳定，长待机续航会明显变差，需实测电流再定；
3. 不动。DOZE 掉线后重建会话本来就是这个 SDK 的设计预期，只要重建够快
   用户无感。**建议先测重建耗时**（日志里 `connecting` 到连上的时间差），
   小于 1 s 就不值得动电源策略。

## 4）对话过程中不允许休眠（已改，有效）

**现状核查**：`check_sleep()` 本来就有会话保护——只有 `MUSE_MODE_IDLE`
且 `idle_secs() > 睡眠设置` 才睡；对话中是 LISTENING/THINKING/SPEAKING，
睡不进去；CPU 轻睡也有 `s_awake` 锁挡着。

**真缺口在"回合刚结束那一刻"**：回复进行时没有任何 `muse_state_poke()`
（会话任务不 poke，voice 任务只在队列事件时 poke），`idle_secs` 会横跨
整轮对话一直涨；`go_idle()` 把模式置回 IDLE 的下一刻，`check_sleep()`
看到 `idle_secs > 设置` 就立刻睡——用户刚听完回复、还想继续问，屏已经黑了。

**改动**：`muse_voice.c` 的 `go_idle()` 里加一行 `muse_state_poke()`，空闲
倒计时从回合结束才算。`go_idle()` 是 voice 任务里**唯一的回合出口**
（13 处调用点全部经它，已核对），所以一处改动覆盖全部结束路径；不动睡眠
设置、不动电源锁。

**验收**：开一轮超过睡眠设置的长对话（等回复 8 s + 长回复放音），回合结束
时屏不立刻黑；之后静置到设定时间，正常睡。
