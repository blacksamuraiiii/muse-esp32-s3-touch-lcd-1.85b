## 0. 第 3 阶段已关闭的决策（用户 2026-10-25 晚拍板，照办，不再问）

### 0.1 字体：以 1.4 的 CJK 字体为准，不要 18 号

- 远端核实（分支 `docs/1.5-interaction-preview`）：
  `esp32/components/muse/fonts/` 里只有 `README.md` 与
  `muse_font_cjk_16.c`，**没有 18 号 CJK 字体文件**。
  `muse_font_cjk_16` 是 GNU Unifont 16.0.04 的 16×16 位图，
  与 unscii-16 同格，作字幕字体的 fallback，
  `CONFIG_MUSE_CJK_FONT` 门控，约 850 KB Flash；
  生成脚本 `esp32/tools/muse/gen_cjk_font.sh` 用
  `lv_font_conv --size 16`，范围 0x3000-0x30FF、0x4E00-0x9FFF、
  0xFF00-0xFFEF（脚本内已核实，SHA 校验的 Unifont 16.0.04）。
- 第 3 阶段一律以这个 16px 字体为准：运势正文与卡下小字走
  `caption_font()` / `muse_font_cjk_16` 路径渲染（第 2 阶段
  `muse_interact_ui.c` 已按此写，`LV_FONT_DECLARE(muse_font_cjk_16)`）。
  **不要凭空发明 18 号字体符号、不要为凑数字新增字体文件**。
- 设计稿里的“18 号”是用户想要的字号愿望，不是现有字体文件：
  现有字体只能做到 16px。真要 18px 字形，须另生成
  `muse_font_cjk_18` 并实测 Flash 增量（16px 版已占约 850 KB，
  18px 版只会更大，`check_sizes` 以实编译为准，不要凭感觉说
  “肯定够”），那是用户另行决定后才做的事，**不在本阶段**。

## 1. 跨日与时钟核实清单（共 10 项，全部未验证）

日公式（第 2 阶段已改，第 1 阶段 NOTES 的 localtime 待验证项已关闭）：

```c
day = (now + MUSE_PET_DAY_OFFSET_SECONDS) / 86400;  /* 偏移常量 = 0 */
```

即纯 UTC 日，不依赖 TZ 设置。后果：**每日边界在北京时间 08:00**
（UTC 午夜），不是本地午夜；以后想改成本地午夜，只改
`MUSE_PET_DAY_OFFSET_SECONDS` 为 `8*3600`，不用改逻辑。
下面每一步都写“预期现象 + 判断标准”，不要写“已通过”。

| # | 步骤（串口 + 屏上） | 预期现象 | 判断标准（算通过才打勾） |
|---|---|---|---|
| C1 | `>time=` 设一个已知 UTC 日期（如 2026-10-26 00:00:00 UTC），重启后 `>pet.status` | 占卜日 / 生活费日 / 当日上限按该 UTC 日切分 | 三个日字段一致，且与 `epoch/86400` 的手工算值相等 |
| C2 | 在北京时间 07:59 与 08:01（即 UTC 日边界前后）各看一次 `>pet.status` | 07:59 仍是旧日，08:01 已是新日 | 边界前后日字段恰好差 1，不是差 0 也不是差 2 |
| C3 | 设系统日期跨 3 天（关机期间也算），再看 `>pet.status` | 生活费按天数扣：`due = 10 × 经过天数`，扣到 0 为止不欠账 | `decay_notice = min(due, 原金币)`，金币 `max(0, 原金币 - due)` |
| C4 | SNTP 跳变：先用旧日期抽一张卡，再让时钟跳到新日期抽卡 | 跳变后按新 UTC 日抽新卡，一天内可能出现两张卡 | 这是预览版可接受行为（第 2 阶段已定），**不要当成 bug 报**，也不要因此回退 |
| C5 | 时钟回拨：把日期往回设 2 天，再看 `>pet.status` | 不补发金币、不补扣生活费、不倒退各日字段 | 金币、当日上限、日字段全部保持回拨前的值 |
| C6 | 未校准：`now < 2025-01-01 UTC`（`MUSE_PET_TIME_MIN`）时做动作 | 生活费不扣、不重置当日上限；占卜仍按当前 UTC 日抽 / 复用（第 2 阶段已删 `PET_TIME` 拒绝路径） | 生活费日与当日上限不动；占卜不返回错误 |
| C7 | 跨日后摸摸 / 喂饭 | 当日给币清零：摸摸重新从前 10 次给币，喂饭重新第一次给币 | `daily_touch_coins` / `daily_feed_coins` 在新日从 0 起算 |
| C8 | 占卜同日复用 / 次日新卡 | 同日两次同一张卡（`PET_FORTUNE_SAME`），次日抽新卡 | 两次 `>pet.fortune` 的序号相同；次日序号可能相同也可能不同（随机），但日字段必须变 |
| C9 | 生活费公告 | 扣款后第一次互动（IDLE）字幕写“毛毛这几天花了 X 金币”，只显示一次 | 第二次互动不再显示；`decay_notice` 在显示并 ACK 后清零（先显示、后 ACK，顺序反了金额就丢了） |
| C10 | 重启恢复 | 重启后 `>pet.status` 的金币 / 各日字段 / 占卜序号与重启前一致 | 不是每次开机归零；若归零，先查 NVS blob 是否被 `muse_settings_init` 的擦分区波及（设计 §4.4 已提醒：同 NVS 分区、不同 namespace） |

补充（第 2 阶段 NOTES §2.2 已记，本阶段重申）：`PET_DECAY_ACK`
不产生 feedback；若在“显示扣款”与“发送 ack”之间恰好跨过午夜，
新一轮扣款可能被这次 ack 一并清掉——窗口极小，1.5a 不做扣款序号，
实测时若撞上，记为已知局限，不要临时改模型。

### 2.1 算法（写清是算出来的，不是实测）

- 卡片：300×150，顶部 y=105（第 2 阶段 `build_fortune()`）。
- 等级：卡片内顶部内边距 12，16px 字，约占到 y=28。
- 正文：宽度 = 300 − 32 = 268px，`LV_LABEL_LONG_WRAP`，
  行距 6，顶部对齐在卡片内 y=52 处。
- 字宽：`muse_font_cjk_16` 是 16×16 位图，中文与全角标点
  每字 16px → 每行约 `floor(268 / 16) = 16` 字。
- 行高：16 + 6 = 22px；正文可用高度 = 150 − 52 = 98px →
  **最多 4 行（88px）**，第 5 行（110px）会超出卡片。
- 结论口径：下面“预计放得下”只是按上述算式得出的预判，
  **不是“已过屏”**。LVGL 的实际换行（标点处理、行尾规则）

## 4. 电池夜测规程（与 1.4d 同条件对比，不写预期数值）

铁律（测试版遥测约定，1.4d 夜测已验证过的方法论）：

- **电池测试不能插 USB 在线看日志**：插线即变 USB 供电，数据作废。
  机内攒（FAT 遥测分区）、次日串口导出；电流测量只认 FAT 遥测 +
  `powcfg`，`ptest` 读回结构没有电流字段，不要用它当电流证据。
- 重插 USB 会复位、清 RTC journal：夜测期间不要重插，
  结束导出时按 1.4d 的导出流程走，不要中途拔插。

步骤：

1. 开始：满电（100%）开始，记下开始时间与 `>pet.status`（金币 /
   各日字段），确认刷的是 1.5a + Test 构建、USB 已拔。
2. 夜里：设备放着不动，不对话、不点按、不亮屏操作；
   互动 worker 按 30 秒一轮跑，不做任何额外唤醒。
3. 结束：次日早上（建议与 1.4d 夜测相同的时长，例如 7.5 小时
   左右，具体时长以实测记录为准）记下结束时间与剩余电量，
   再插 USB、串口导出 FAT 遥测 + `powcfg`。
4. 对比指标：掉电百分点、平均电流（mA）、浅睡占比。
   **不要写预期数值当结论**：1.4d 的夜测基线（base 约 10mA、
   结构下限）是参照，不是 1.5a 必须等于的数；1.5a 的结论
   以本次实测的掉电百分点与平均电流为准，写进进展记录。
5. 若 1.5a 夜测明显高于 1.4d 同条件：先按唤醒源分布统计
   （心跳、重连、UI tick 各占多少），不要先猜是 worker 的问题；
   worker 本身 30 秒一轮、不持 lock，理论上不应是主要增量，
   但“理论上”不是证据，以遥测为准。

## 6. 手图资产缺口：未生成，只给转换方法（不要造假图）

### 6.1 状态：模板 `#error` 仍在拦截，缺口没有被“生成”闭环

- 本机没有可用的 LVGL 图片转换工具链：

  无 Inkscape、无 ImageMagick，本机 Python 也没有 cairosvg
  （上一轮会话的 cairosvg 在本机当前 Python 里不可用，
  不要假装它还在）。因此本阶段**没有生成任何手图 C 数组**，
  没有造假图、没有用占位图替换模板。
- 本阶段能确定的是 LVGL 版本（远端核实）：
  `esp32/components/muse/idf_component.yml` 里
  `lvgl/lvgl: "9.5.0"`。转换格式必须按 LVGL 9.5 来，
  不要按 LVGL 8 的 `lv_img_dsc_t` 旧格式猜。

### 6.2 转换方法（在有工具的机器上按此做，一次做对）

输入（本地已确认存在）：

- `~/workspace/gi_rock.svg`、`gi_paper.svg`、`gi_scissors.svg`
  （Game-icons 仓 `game-icons/icons`，`john-redman/` 下，
  John Redman，**CC BY 3.0**，512×512 网格，单色；
  发布 1.5a 时保留 Game-icons 署名）。

步骤：

0. **先删背景矩形（本阶段新发现，转换时最容易漏的一步）**：
   三个 SVG 各只有 2 条 path，第 1 条是满画布矩形
   `<path d="M0 0h512v512H0z"/>`（无 fill，SVG 默认填黑色），
   第 2 条才是白色手形（`fill="#fff"`）。
   转换前必须删掉第 1 条 path（或将其 fill 置为 none），
   否则渲染出来是一块黑方块、不是透明底白手；
   后续的运行时 recolor（输家变 DIM 灰）会把整块黑方块
   一起变色，而不是只变手形——那是转换错误，不是设计。
1. 整体逆时针转 90 度、手朝上：原图手朝右（手指朝 +x），
   绕画布中心 (256, 256) 做 `rotate(-90 256 256)`
   （SVG 坐标 y 向下，-90 度即视觉逆时针），转完手指朝上。
   未转的手是 bug，不是风格选择（定稿示意图 v17 就是转后版）。
2. 渲染为 PNG：透明底、白手，生成**一个母版**（如 256px），
   不要生成两套不同像素格；LVGL 在运行时缩放到
   选择页约 100px、结果页约 130px 两档（代码里选择行用
   `IC_GAME_CHOICE`、揭晓行用 `IC_GAME_RESULT`，以代码为准）。
3. 转 LVGL 9.5 C 数组：用 LVGL 9 的图片转换器
   （LVGL 9 的 `LVGLImage.py` 或官方在线转换器，选 LVGL 9 格式），
   格式为真彩 + alpha（`LV_IMAGE_CF_TRUE_COLOR_ALPHA` 一类，
   以转换器在 LVGL 9.5 下的实际输出为准，不要按 LVGL 8 猜），
   符号名必须 exactly：
   `muse_interact_hand_rock`、`muse_interact_hand_paper`、
   `muse_interact_hand_scissors`（类型 `lv_image_dsc_t`）。
   输家变暗是运行时 `lv_image_set_recolor`，不是第二张图；
   赢家边框是容器边框，不是图的一部分。
4. 替换模板：用生成文件替换 `muse_interact_hand_assets.h`，
   删掉 `#error` 那一行（只删那一行，不要动符号名），
   再编译——编译通过是“格式对了”，不是“图好看了”。
5. 实机核对（图好看的唯一标准）：选择页 100px 与结果页
   130px 下，拳头 / 张开手掌 / V 形剪刀手**各自一眼可辨**，
   不能只在三张并排时靠位置猜；输家 recolor 后仍可辨是手形、
   不是一团灰；赢家边框不遮手形。
