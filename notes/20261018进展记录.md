## 2. 敲击亮屏：三条根因，三处改动

现场症状（10-17 晚 + 10-18 早）：睡两分钟后敲不醒，再往后永久死亡，按键亮屏→息屏后同样失效，
而加速度计一直在正常采样。这不是一个 bug，是三个独立机制叠加。

### 2.1 根因

1. **I2C 事务被 light sleep 截断**（最可能，能解释「和睡眠时长相关」）
   `CONFIG_PM_ENABLE` + 自动 light sleep 打开后，任何任务在任何时刻都可能被停钟。
   QMI8658 把半截写入解析成一次寄存器写；`CTRL8.bit0 (Tap_EN)` 被改写 → 引擎关掉，
   而 `CTRL7/CTRL2`（加速度计）不受影响——正好是「芯片在跑、但检测不到敲击」。
   睡着时 200 ms 进出一次 light sleep，两分钟 600 次，撞上的概率接近 1。
2. **STATUS1 锁存没人清**
   `STATUS1.bit1` 是读清位。亮屏时敲一下没人读 → 位一直置着 → 引擎不再报新事件；
   下次睡下配 HIGH 电平唤醒时，电平早已满足，等于没配。这解释「按键亮屏→息屏后再敲失效」。
3. **引擎状态机自锁**（保底）
   配置寄存器全对、引擎就是不检测，没有任何可读痕迹。只能靠定期重臂兜。

### 2.2 改动

| 文件 | 改动 |
|---|---|
| `esp32/components/muse/muse_imu_tap.c` | ① 每个 I2C 事务持 `ESP_PM_NO_LIGHT_SLEEP` 锁；② 新增 `muse_imu_tap_check(full)`：回读 `CTRL7/CTRL8` 与 init 写入值比对，漂了就重跑 init（10 s 内不重复，防循环），`full` 时再比 `CAL1..CAL4`；③ 新增 `muse_imu_tap_rearm()`：停传感器 → 重写两组参数 → 重开；④ 新增 `muse_imu_tap_diag()` / `muse_imu_tap_log_diag()` 一条 WARN 打全部寄存器 |
| `esp32/components/muse/muse_input.c` | `STATUS1` 每 200 ms 读一次，**不管亮屏还是息屏**（读即清锁存），值只在睡着时用来唤醒；1 Hz 配置校验、60 s 一次全量校验、睡着时 60 s 一次重臂 |
| `esp32/components/muse/muse_imu_tap.h` | 新 API 声明 + 说明为什么亮屏也要读 STATUS1 |

重臂间隔定为 60 s 而非 10 min：现场故障是睡下两分钟内就死，10 min 的定时器等不到它。
重臂代价约 10 来个 I2C 事务（约 3 ms），一分钟一次可忽略；代价窗口里丢一次敲击的概率 0.017%。

### 2.3 现场取证命令

| 命令 | 作用 |
|---|---|
| `>imu` | 打一行 WARN：`CTRL1/2/7/8/9`、`STATUSINT`、`STATUS1`、`TAP_STATUS`、`CAL1..4`、期望值、自愈次数 |
| `>imu.check` | 强制全量校验（含 CAL），漂了立刻重配 |
| `>imu.rearm` | 强制重臂一次 |

正常时：`CTRL7=0x21(want 0x21) CTRL8=0xc1(want 0xc1) cal=08 20 20 03 90 01 00 20`。
出现 `config drift: …` + `tap re-initialised (#1)`，说明根因 1 或 2 发生过，自愈已生效。

### 2.4 真机验收口径

1. `tap_cycles.py` 跑 3 轮（每轮等自动息屏 120 s → 敲击）→ 必须 3/3 出现 `muse_input: waking (tap)`。
2. 长稳：睡眠 10 分钟后敲击仍能唤醒。
3. 亮屏敲击 → 等自动息屏 → 再敲 → 仍能唤醒（验证根因 2）。
4. 任一步失败：贴 `>imu` 输出 + 失败前后串口日志，按 `docs/踩坑记录.md` §1 的判定表继续。

### 2.5 结果与二次定位（2026-10-18 夜）

USB 下敲击正常；电池下失效，而 `>imu` 显示配置逐位正确、`recoveries=0`。
三条根因（I2C 截断 / 锁存没清 / 引擎自锁）已修住「配置漂移、锁存」这半边。剩下的失效最初归因于
「light sleep 期间 tick 停走」，**当夜用带串口的强制复现证伪**：

```
I muse_input: slept 10000 ms (tick 10000 ms), line low     ×10     ← 墙钟与 tick 相等
I muse_input: slept 10001 ms (tick 10000 ms), line low
```

tick 由 tickless 补偿正常推进，所以轮询不会因为睡眠被跳过。同一份日志给出另一条硬数字：
`log.muse: screen off a while; left wifi` 之后等待仍是 10 秒（`NAP_WAIT_MS`），
普通息屏则是 1 秒（`REST_WAIT_MS`）——即使唤醒线完全失效，最多这个间隔就会返回并读一次 STATUS1。
真电池下敲击仍不亮，因此只剩两种可能：引擎没锁存 STATUS1，或读到 tap 时状态不是 asleep。
这两者带串口都看不到（USB 主机不让 CPU 睡，`>pmlow=1` 又把串口弄断），
改为在设备里留 RTC 日记，插回 USB 回读。当日改动与判读表见 `docs/20261018待办.md` §1。

## 3. TTS 首音时延

### 3.1 先量再改（本机 → eastasia 直连 Azure）

| 场景 | 首音 |
|---|---|
| 冷连接，60 字 | 1.20–1.39 s |
| **同一连接复用，60 字** | **0.45–0.53 s** |
| 冷连接，5 字 | 1.17–1.26 s |
| `style=friendly` 开 / 关（60 字） | 1.43 / 1.29 s |
| 16k/32k vs 24k/48k | 1.39 / 1.43 s（无差别） |
| 去掉标点 `<break>` | 无差别 |

被数据否掉的两个「看起来该做」的优化：

- 首音几乎不随文本长度变化（5 字 1.17 s vs 60 字 1.39 s）→ 「切首句先合成」收益极小，
  还会因多一次请求引入接缝，不做。
- 格式与 break 都不是瓶颈，不动。

真正的瓶颈是每次请求都重新握手 TLS，复用连接省 0.7–0.9 s。

### 3.2 服务端改动（`tts-server/tts_server.py`）

| 改动 | 说明 |
|---|---|
| Azure 连接池 | 全局 LIFO 池（`TTS_AZURE_POOL`，默认 6）。读完整个 body 才归还；半读连接直接丢弃；池化连接失效时重连一次并重试 |
| 启动预热 | `_prewarm()` 合成一个「嗯」，省掉首个请求的握手 |
| 首包阈值 | `STREAM_HEAD_BYTES` 1024 → 512，`waitress send_bytes` 1024 → 512（`TTS_STREAM_HEAD` / `TTS_SEND_BYTES` 可调） |
| 坏包钩子 | `TTS_TEST_HOOKS=1` 时：`?text=BADPACKET` 回 200 + HTML，`?text=BADSTATUS` 回 500 + HTML；`TTS_FORCE_BAD=1` 让每条回复都变 200 + HTML |
| `/health` | 增加 `stream_head` / `send_bytes` / `test_hooks` / `azure_pool_idle` / `azure_pool_open` |

踩坑：第一版用 `threading.local()` 存连接，**完全没效果**（还是 1.3 s/次）——
流式 worker 是每请求新起 `threading.Thread`，线程本地变量永远是空的。必须用显式池。

### 3.3 固件侧为什么不用改

`muse_tts.c` 已是「边收边送」：`gate_feed()` 只扣前 8 字节判 MP3 头，通过后立刻进 ring；
上层 `muse_chat_session.cpp` 的 `MP3_BUF` 有 512 KB，`pump_tts()` 一有空位就搬，
下一段请求在当前段读完立刻发出。不存在 ring 满导致下一段延迟，也没有可省的固件侧等待。

### 3.4 实测结果（本地起服务，端口 5051）

| 场景 | 首音 | 说明 |
|---|---|---|
| 冷启动首个请求（未预热） | 1.84 s | 基线 |
| 预热后首个请求 | **0.58 s** | `_prewarm()` 生效 |
| 之后连续请求 | **0.47 / 0.48 / 0.49 / 0.55 s** | 连接池生效，跨 waitress 线程也复用 |
| `/health` | `azure_pool_idle=1, azure_pool_open=1` | 池里确实留着一个热连接 |

### 3.6 坏包丢弃（板端未验证）

原理（v1.1 起）：前 8 字节攒齐才判断，`0xFF`（MPEG 帧同步）或 `ID3` 才放行；

1. 服务端 `.env` 加 `TTS_TEST_HOOKS=1` 和 `TTS_FORCE_BAD=1`，重新部署。
2. 对板子说一句话。
3. 串口期望 `W muse.tts: muse.tts: bad MP3 payload len=41 first=0x3c`（`0x3c` 是 `<`）。
4. 去掉 `TTS_FORCE_BAD` 重新部署，再问一句：应恢复 `first byte=0xFF`/`ID3` 并正常出声。

## 5. 电池：真机把原来的结论推翻了

### 5.1 1.2 那版判断（错）

判断是「BQ27220 没按电芯配过 Data Flash，SoC 天然 100%」，并加了电压兜底 `pct_from_mv()`。
真机 `>batt` 一打，这个判断是错的。

### 5.2 真机原始值（1.2，插 USB 充电中）

| 寄存器 | 值 | 正确含义（TRM Table 2-1） |
|---|---|---|
| 0x08 | 4136 | Voltage 4136 mV |
| 0x0C | 474 | Current +474 mA（正 = 充电） |
| 0x10 | 497 | RemainingCapacity 497 mAh |
| 0x12 | 500 | FullChargeCapacity 500 mAh |
| 0x18 | -1 | TimeToFull 无效 |
| 0x1C | 3313 | **StandbyTimeToEmpty** ← 老代码把它当 SoC 读，被 `<=100` 夹成 100 |
| 0x28 | 3064 | InternalTemperature 306.4 K = 33.3 ℃ |
| 0x2A | 2 | CycleCount 2（新机） |
| **0x2C** | **100** | **StateOfCharge 100%**（充满后） |
| 0x2E | 100 | StateOfHealth 100% |

上午另一组（未充满）`0x1C=1947 0x2C=59`，且 RC/FCC = 292/500 = 58.4%，与 SoC 59% 完全对上。
交叉验证成立：**电量计本来就是配好的**，不需要写 Data Flash。

### 5.3 修法

- SoC 改读 `0x2C`；越界才回落到电压估算。
- `charging` 用 BatteryStatus(0x0A) bit0（DSG，1=放电）取反。
- `>batt` 按 TRM 名称打印 18 个标准命令 + DesignCapacity(0x3C)。
- `pct_from_mv()`（20 点单节 Li-ion 开路电压表）保留作兜底：
  仅当 `gauge >= 95%` 而电压折算 `<= 80%` 时启用，并 WARN 一次；
  限定「gauge 接近满」是为了避免带载压降被误判成快没电。
- `muse_board_t.power_debug` 新增可选回调，别的板子不实现就不出现。

### 5.4 教训

**先 dump 再推理。** 任何「恒为某个值」的传感器读数，先怀疑地址/单位/缩放，
不要急着给它编一个物理原因。`0x1C` 读出 1947 这种明显不像百分比的值，本身就是最强的线索。

真机日志（1.2，UI 起着时按 `>ota`）：

```
I link.ota: ota start: int free 18315 largest 8704 | psram free 4095040 largest 4063232
W link.ota: no 16384-byte internal stack for the ota task
W link.ota: no 12288-byte internal stack for the ota task
W link.ota: no 10240-byte internal stack for the ota task
I link.ota: ota task up (8192-byte internal stack)
I link.ota: Writing to <ota_1> partition at offset 0x420000
```

PSRAM 空着 4 MB，内部最大块只剩 8.7 KB，16 KB 必然失败。
修法：栈改 `xTaskCreateWithCaps(MALLOC_CAP_INTERNAL)`，按 16K→12K→10K→8K 逐级降。
关键点：OTA 任务栈**必须**在内部 RAM——`esp_https_ota` 写 flash 时 cache 是关的，
PSRAM 栈那时不可访问，直接崩。

### 6.2 第二个坑：装完又被静默回滚

第一次 OTA 的时间线：

```
I ota.github: manifest: version=1.3
I ota.github: updating 1.2 -> 1.3
I link.ota: ota task up (8192-byte internal stack)
I esp_https_ota: Writing to <ota_1> partition at offset 0x420000
I link.ota: incoming version=1.3
I link.ota: applied 1.2 -> 1.3, rebooting
……重启后……
I link.app:   Version:  1.3          ← 看着是成功的
```

但几分钟后再抓启动日志，又变回 `Loaded app from partition at offset 0x20000` / `Version: 1.2`。

根因在 `app.c` 的 `ota_verify_task()`：只在 `noise_ctrl_is_connected()`
（Home Link 控制 WebSocket）为真时才调 `esp_ota_mark_app_valid_cancel_rollback()`，
否则等 `OTA_VERIFY_TIMEOUT_US`(300 s) 超时就
`esp_ota_mark_app_invalid_rollback_and_reboot()`。
这块板没有 SDK token（启动日志 `SDK token: (none)`），`link.vm_api` 一直
`ESP_ERR_HTTP_CONNECT`，控制 WS 永远连不上 → 300 s 后必然回滚。

修法：保留 WS 快速路径，新增宽限——镜像连续运行 30 s 就标记有效。
理由：会崩的镜像活不到 30 s，那种情况 bootloader 自己会回滚。
宽限只在 `s_ota_pending_verify` 为真时执行：从 factory 分区启动时
`esp_ota_mark_app_valid_cancel_rollback()` 返回 `ESP_FAIL`
（IDF 的 `Running firmware is factory` 分支），无条件调用会让每次普通开机多打一条错误日志。

验收行（下次 OTA 应看到）：

```
I app: running a PENDING_VERIFY OTA image; awaiting health check
I app: OTA image validated after 30 s without the control WS (this build runs without it)
```

## 11. 敲击亮屏现场排查（10-18 22:30 – 10-19 00:15）

> 本节合并自 `20261019进展记录.md`（整合后已删除）。这段工作是 1.2 发布之后的现场排查，
> **改动都在 1.2 里，没有新版本号**；未上机验证的项目在下面逐条标明。
> 相关：`docs/20261018待办.md` §1（故障与判读表）、本文件 §2。

### 11.0 一页结论

1. **真正的触发源不是 IMU，是触摸屏。** 用户敲的是**屏幕正面** —— USB 下敲三下能亮屏，
   但 RTC 日记里 IMU 的 `taps / taps_awake / knocks / screen_wakes` **全为 0**，
   说明亮屏与 IMU 无关，是触摸控制器报的事件。此前「USB 正常、电池失效」被理解成
   「IMU 路径只在电池坏」，方向错了。
2. **电池下 IMU 的 Tap 引擎确实一个事件都不报**，三次实测一致；同时加速度在采样
   （`accel=3925/3926`，寄存器每次读都在变），配置与数据手册逐位一致（`drifts=0`）。
   即「芯片活着、配置对、引擎就是不报」——原因仍未确认。
3. **已实施的修复：把触摸控制器的 INT（GPIO4）并入 light-sleep 唤醒线**，
   电池下敲屏幕正面有望直接唤醒（**未做电池实测**）。
4. 三个被证伪的假设：tick 在 light sleep 期间停走；Tap 配置写错；加速度在电池下停采。
5. 两个我自己引入的干扰（都已回退/默认关闭）：10 秒一次的引擎重臂、睡着时读 FIFO。

### 11.2 被证伪的假设（避免以后再走一遍）

| 假设 | 证据 | 结论 |
|---|---|---|
| `xTaskGetTickCount()` 在 light sleep 期间停走，导致 200 ms 轮询被跳过 | `slept 10000 ms (tick 10000 ms)` 两者相等；本板 `CONFIG_FREERTOS_USE_TICKLESS_IDLE=y` 且 light sleep 由 idle 路径进入，tick 有补偿 | **不成立**。换 `esp_timer_get_time()` 仍然值得（语义更准），但不是根因 |
| Tap 参数/寄存器写错 | 对着 QMI8658A 数据手册逐位核对：`CTRL2=0x04`=500 Hz/±2 g、`CTRL8=0xc1`（bit7 握手 + bit6 活动中断送 INT1 + bit0 Tap_EN）、`CTRL1=0x48`、两组 CAL 参数 + CTRL9=0x0C、`STATUS1(0x2F).bit1`=Tap | **配置没问题** |
| 电池下加速度停采 | `accel=3925/3926`（读数每次都在变） | **不成立**；停采的是引擎的事件输出，不是采样 |
| 用 60 ms 轮询数据寄存器就能替掉引擎 | 一整轮电池会话 `maxmg=66`（0.066 g），敲击脉冲 10–30 ms | **不成立**；轮询式读“最新样本”抓不到脉冲，必须走 FIFO |
| USB 下亮屏说明 IMU 路径可用 | 同时 `taps=taps_awake=knocks=screen_wakes=0` | **不成立**；用户敲的是屏幕正面，亮屏来自触摸屏 |

### 11.3 难点：为什么这个问题特别难查

1. **电池态没有串口。** 固件只在无 USB 主机时进 light sleep（`want_low = pause && !muse_console_host()`），
   而 USB-Serial/JTAG 一进 light sleep 就掉线。所以「电池才犯的错」正好发生在看不到日志的状态里。
2. **`>pmlow=1` 是假复现。** 它能强制 CPU 睡，但 USB 主机在位这件事本身改变了行为，
   现场日志显示等待/唤醒形态与真电池不同；而且它一执行就把串口弄断，之后必须拔插 USB 重新枚举。
3. **每次迭代成本高**：改一处 → 编译（1–2 分钟）→ 刷机（40 秒）→ 拔插 USB → 人工敲 → 读日记，
   一轮 5–10 分钟，且必须有人在板子边上。
4. **中间件在骗人**：`esp_lcd_touch` 与 LVGL 适配器占用了 GPIO4 的中断，
   通用「唤醒线」函数若顺手 `gpio_config()` 会把中断类型清成 DISABLE（驱动跟着失效），
   所以触摸这条线只能用「只武装唤醒源、不碰中断」的变体。
5. **我自己的改动一度把现象搅混**：10 秒一次的引擎重臂让芯片每 10 秒复位重配
   （日记里几分钟内 `starts=18`），睡着时读 FIFO 又把输入任务拖到心跳空档 30 秒。
   这两条都已回退/默认关闭，教训是**排查期一次只动一处，且新增路径必须默认关闭**。

「芯片有没有采样」「引擎有没有报」「状态切没切」「屏幕亮没亮」四段分开。

### 11.5 遗留项（已转入 `docs/20261019待办.md` §2）

1. **触摸唤醒的电池实测**：拔 USB，屏幕熄灭后敲屏幕正面，看是否亮屏。
   （若仍不亮，下一步查 CST816S 在屏息期间是否被置入睡眠模式，以及 `esp_lcd_touch` 的
   中断回调在 light sleep 唤醒后能否拿到事件。）
2. **IMU Tap 引擎在电池下静默**：三次实测一致，配置与手册逐位一致，原因未确认。
   已知「重启引擎」救不回来（重启 6 次仍静默），且频繁重启有害（每 10 秒复位）。
3. **FIFO 路线**：寄存器与命令已按手册落地（`FIFO_CTRL=0x14`、`SMPL_CNT=0x15`、
   `STATUS=0x16`、`DATA=0x17`、CTRL9 `0x05` 取数、读完清 `FIFO_RD_MODE`），
   但首版一执行就把输入任务拖死，默认关闭，待用 `>fifowatch` 在台面上确认能读到峰值再启用。
4. 若最终确认只能靠触摸：把「敲外壳」这类需求改成「触摸屏点一下」。

### 11.6 方法沉淀（可复用）

- **无复位读串口**：`pyserial` 打开前置 `dtr=False, rts=False`，可只读不扰；
  反之 RTS 翻转一次就是一次干净复位，用来抓启动日志（`esp32/tools/board_serial.py`）。
- **RTC noinit 日记**：`RTC_NOINIT_ATTR` 的结构（计数器 + 16 条事件环）跨复位存活，
  电池实测后插回 USB 即读；本机实测 `boots` 从 1 递增到 4，确认保留有效。
- **诊断命令要好用**：`>imu`（寄存器 + 计数 + 日记）、`>fifo`、`>fifowatch=<秒>`、
  `>knock=0/1`、`>pmlow=0/1`；排查期新增路径一律默认关闭，避免自己制造的故障混进现象。
- **数据手册在手**：QMI8658A Rev A（Waveshare 镜像）——寄存器总表 p26–27、配置位 p31–35、
  Tap p61–63、FIFO p35 与 p48；WSL 用 `~/.venv/bin/python3` + pymupdf 抽页。
