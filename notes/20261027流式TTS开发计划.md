# 流式 TTS 开发计划（2026-10-27，分支 feat/streaming-tts-20261027，基点 main 1.5c）

## 一句话目标

网关已经是流式回消息（`delta.message_start / text_append / message_done`），
板子今天却要等整条消息 `message_done` 才开始说。改成：增量文本一到句末
标点就立刻合成播放，首音从“整段生成 + 整段合成”变成“第一句生成 + 一句
合成”。后端无关：先在现有桥上验证，之后直连 Azure 时同一套句子管线原
样复用。

## 现状（已按 1.5c 代码核实，不是推测）

- 回复到达：`muse_chat_session.cpp` 的 `on_event()` 接 `delta.text_append`，
  语音模式下 `append_text()` 把增量拼进 `s_turn.texts`（每条消息上限
  `TEXT_MAX` 1024 字节，共 `MAX_MSGS` 8 条），同时 `show_reply_start()`
  刷新开场字幕。`message_done()` 才把消息置 `TTS_QUEUED`。
- 说话触发：会话主循环在 `P_WAIT_REPLY` 时每轮跑
  `start_tts() → pump_tts() → decode()`。`start_tts()` 只挑首条
  `TTS_QUEUED` 消息，整段文本一次交给 `muse_tts_speak()`，置 `TTS_ACTIVE`。
- 音频通路已经是流式的：`muse_tts.c` 的 worker 取音频进 PSRAM ring，
  `pump_tts()` 搬进 `s_turn.mp3`（`MP3_BUF`），`decode()` 用 minimp3 解码；
  `muse_tts_drained()` 后 `mp3_ended`，解码排空该消息置 `TTS_FINISHED`，
  下一轮 `start_tts()` 推进下一条消息。`decode()` 在流未结束时扣住
  `MP3_HOLD`（1445 字节）不解最后一帧，因为 minimp3 要看到下一帧头。
- 插话已有代际保护（1.5c）：`muse_tts_cancel()`  bump `s_gen`，
  旧 fetch 的字节在 `on_http_data` 与 `gate_finish` 两处被拦，重试也被
  条件挡住；worker 的 drain 循环只在无待处理项时才清忙闲。
- 不受影响的两条路：无 `CONFIG_MUSE_TTS_URL` 时走静默 pacing（按
  `TEXT_CHARS_PER_S` 16 字/秒读字幕）；控制台模式（`s_turn.text`）本来
  就不说话。流式改动不得动这两条路的行为。
- 已知上限：单条消息文本超 1024 字节时 `strlcat` 截断（`m.len` 照计），
  这是今天就有的限制，流式不把它变好也不把它变坏，见“待定”。

## 设计

### 句子是单位，消息仍是顺序

- 每条消息加一个“已说偏移”游标（已合成并播出的文本位置），存在
  `msg_t` 里，随 turn 重置一起清零。
- `text_append` 到达后，从游标起扫描已缓冲文本，找第一个句子边界；
  有完整句子且该消息当前没有句子在播，就启动它。消息内句子严格按
  顺序播；消息之间也严格按顺序：消息 i 还有没说完的缓冲文本或还没
  `message_done`，就不启动消息 i+1。
- `message_done` 到达时把游标到文末的残段作为最后一句（组） flush，
  哪怕它没有句末标点。`message.assistant` 整条到达的老路同样走这套：
  所有句子一次性可用，逐句播，和今天整段播的听感一致，只是实现统一。

### 分句：复用，不复制

- 边界判定就是 `muse_tts.c` 里 `break_before()` 的那套：ASCII
  `.!?;:` 与全角 。！？（1.5c 刚修好逐字节比对，之前算式恒不对）。
  把它抽成会话与 TTS 共用的 helper（例如 `muse_tts_sentence_end()`），
  不许在会话侧再写一份——1.5c 已经证明两份会漂移。
- 启动阈值：第一个边界，或者无边界但已缓冲到 `TTS_TEXT_CHUNK`
  180 字节（沿用现有 URL 分块上限），先到先说。长句没有标点时首音
  仍然来得早。

### 句子怎么播：沿用现有生命周期，不另起管线

- 首选方案：句子仍走 `muse_tts_speak()`，一次一句，由主循环串联。
  一句播完（`muse_tts_drained()` 且 `decode()` 排空该句音频）的下一轮，
  若同一消息已有下一个完整句子就接着说；若消息未完且无完整句子，
  就**停住等**，不要置 `TTS_FINISHED`、不要推进下一条消息。
- 为此 `mp3_ended` 要分两层：句末（本句音频排空，解码器可释放
  `MP3_HOLD`、为下一句重建 `mp3dec` 状态）与消息末（消息已 done 且
  游标到文末）。今天 `pump_tts()` 见 `muse_tts_drained()` 就置
  `mp3_ended`，句末必须复用这个脉冲但不能让它直接结束消息。
  每个句子是一段独立 MP3，解码器状态（`mp3dec_init`、码率、
  `down_rate`）按句重建；上一句的尾帧不得留给下一句当头。
- 备选方案（只有首选被证明行不通时才考虑）：给 `muse_tts` 加
  `speak_more()` 续写接口，让一条 fetch 管线内部消化句子边界。
  改动面更大（fetch 循环、ring、代际号都要动），除非首选在解码
  边界上撞墙，否则不选。

### 字幕：不许跑在声音前面

- 播哪句，字幕就跟到哪句；等下一句时字幕停住，不许跳到未播的
  流式文本。开场字幕（`show_reply_start`）行为不变。
- 具体跟随方式（播句内的字幕推进节奏）实现时对照现有
  “spoken captions carry on from there”的代码定，不得凭空发明一套。

### 插话与取消

- 插话（`muse_tts_cancel()` + `s_gen` bump）时：丢弃该消息全部未播
  句子，游标作废；turn 重置时游标与句子状态一并清零。
  在途句子靠 1.5c 已有的代际号拦住，不新增机制。
- 取消后还没开始的排队句靠 `s_abort` 挡住（1.5c 已验证的路径），
  不得误播。

### 失败与回退

- 某句合成失败（`muse_tts_speak` 返回 false、取不到音频）：
  按今天整段失败的处理——该消息剩余文本转静默 pacing，turn 能自己
  结束，不许卡住等下一句。
- 某句音频坏包：沿用今天的严格 MP3 前缀闸门，坏包只留文字。
- 开关：新增 `CONFIG_MUSE_STREAMING_TTS`（默认 y），关掉即回到
  1.5c 行为（等 `message_done` 整段说），回滚不用改代码。

## 工作拆分与验收

1. 分句 helper 抽取 + host 单测
   - 把 `break_before` 抽成共用 helper，会话侧与 TTS 侧同调一个函数。
   - 在 `esp32/tests/` 按现有 Python 驱动 C 的模式加单测：ASCII 标点、
     全角 。！？、无边界长句（180 字节切）、边界在 UTF-8 多字节中间
     不得误切。
   - 验收：单测过；`muse_tts.c` 现有分块行为不变（跑通现有 TTS 相关测试）。
2. 消息游标与流式启动
   - `msg_t` 加已说偏移；`text_append` 后扫描边界；主循环在
     `P_WAIT_REPLY` 里按“有完整句且无句在播”启动句子。
   - `message_done` flush 残段；`message.assistant` 整条走同一路径。
   - 验收：单条多句回复，第一句音频在第一句边界到达后不久即出，
     不必等整条 done；句序与消息序不错乱。
3. 句末与消息末分层
   - `mp3_ended` 句脉冲与消息结束分离；句间重建解码器状态；
     无句可播且消息未完时停住等，不推进、不结束。
   - 验收：连续三句不断句播放无丢帧、无咔哒；中途停顿等下一句时
     不提前结束 turn；长回复播完后 turn 正常结束。
4. 字幕跟随与插话
   - 字幕跟随播句；插话丢弃未播句；turn 重置清游标。
   - 验收：字幕不超前于声音；句中插话后旧句余音不漏出来；
     下一回合从干净状态开始。
5. 失败与开关
   - 句失败转静默 pacing；`CONFIG_MUSE_STREAMING_TTS=n` 时行为与
     1.5c 一致（对照实测：等整段 done 才说）。
   - 验收：断桥（TTS URL 不可达）时 turn 能自己结束；关开关后
     与 1.5c 听感一致。

## 实机验收清单（用户侧编译实测）

- `esp32/tools/muse/board.sh build lcd185b`，看 size 行不超 4MB 槽。
- 首音时延：日志里第一条 `text_append` 到第一句音频帧的时间戳，
  对照 1.5c 的整段等待，确认明显提前。
- 三句连续回复不断句、不丢句、不串句；句中插话干净停住。
- 无标点长句（超 180 字节）能按上限切出首音。
- 多条消息的回合：前一条没播完，后一条不开口。
- 桥断开时 turn 能自己结束；关开关后回到 1.5c 行为。

## 风险与待定

- 解码器句边界是最大风险点：minimp3 的 `MP3_HOLD` 逻辑是按
  “流未结束”写的，句脉冲处理不当会在句间丢一帧或咔哒一声。
  工作项 3 必须先过，再谈别的。
- 单条 1024 字节截断：流式不改它。超长单条（约 340 汉字以上）
  今天就已经截断；要不要抬 `TEXT_MAX`（8 条 × 1024 已占 8KB，
  抬的代价是 RAM）由实测决定，不在本计划里默认改。
- 网关侧 delta 粒度：如果某网关实现把整句攒成一个 `text_append`
  才发，首音收益会打折扣——这是网关行为，板子侧测不出来时先查
  日志里的 append 粒度再下结论。
- 本计划不动：直连 Azure（下一棒）、公网 TTS 服务器、桥的
  `clean()` 进固件（直连时才需要）。

## 实施注记（2026-10-28，2/5–4/5 落地时记）

- 句界集以“句子”为语义，不以 `break_before` 为准：`break_before`
  含空格、逗号、换行，只用于 URL 分块；`muse_sentence_next_unit`
  只认 ASCII `. ! ? ; :` 与全角 `。！？`，逗号不断句。
- 2/5 与 3/5 同批落地：无句末分层就无句始，拆不开。句末
  分层只动 `decode()` 收尾：句末释槽（`tts_msg = -1`，消息保持
  ACTIVE）、消息末才 FINISHED；`pcm_frames` 句中不动，字幕保持
  时间 pacing，不跑到声音前面。
- 字幕钳制（4/5）：`muse_hatch_turn_caption` 里 `at` 不超过
  `m.spoken`（已交 TTS 的字节数）；静默 pacing 时不钳制（无声
  音可跟）；遗留整段路径在 speak 成功时把 `spoken` 置为整条，
  钳制对其是 no-op。插话无代码改动：唯一 `muse_tts_cancel()`
  调用点是 `turn_finish`，`s_gen` 两处拦截 + drain 循环守门，
  在途句子的字节进不来；新 turn 的 `turn_t{}` 把 `spoken` 清零。
- 5/5 已收尾（2026-10-28）：host 全集流式分支 614 项 vs 干净
  1.5c 605 项，失败 12 项、报错 7 项、跳过 10 项两边逐项相同，
  多出的 9 项正是新分句单测且全过；关开关等价性以代码核对
  （遗留路径逐行一致，只多一个遗留路径不读的 spoken 字段）。
  比对用的临时 worktree 已删，日志在 `~/workspace/tts-suite-logs/`。
