## §1 构建风味总开关：Chill / Force（唯一开关，收编所有测试设施）

背景：测试设施的开关正在变多（遥测、ptest、诊断命令、测试分区表、版本后缀），
散着管迟早漏。收敛为**一个**风味开关，两个取值：

| | **Chill**（测试版） | **Force**（正式版） |
|---|---|---|
| 遥测采样器（设计 v2） | 编入 | 不编 |
| muse_power_test | 编入 | 不编 |
| `>pmdump` 等台架命令 | 有 | 无 |
| 分区表 | 测试版（带 fat 遥测分区） | 正式版 |
| 版本显示 | 带后缀（如 `1.4c-chill`） | 纯版本号 |
| OTA | 不进正式通道 | 正常 |

实现要点：
- Kconfig 一个 choice：`MUSE_FLAVOR_CHILL / MUSE_FLAVOR_FORCE`，
  **默认 Force（失败即关闭）**——测试版靠 overlay 显式开 Chill；
  忘开 overlay 只会得到一个干净的正式构建，绝不会把测试代码漏进正式版
- 所有测试设施的编译条件统一改为挂这个开关（原 `MUSE_TELEMETRY` 等
  子开关降为开关内部细节，不再单独暴露）
- **Force 要名副其实**：Force 下若检测到任何测试设施被单独打开
  （如手工把遥测设 y），编译期 `#error` 直接失败，不许静默共存
- 发版检查随之简化为一条：`flavor == Force` + 分区表为正式版
  （遥测设计 v2 的 §6 清单里其余 grep 项保留作双保险）

## §2 闹钟优化（用户 10-23 提出；官方核查结论附后）

### 2.0 官方核查结论
- 上游 muse-gadget-sdk **无闹钟功能**（全仓零命中），此功能是本 fork 自研，
  无上游实现可抄
- 芯片层：PCF85063A 有独立星期闹钟寄存器（0x0F），但驱动 `set_alarm`
  将其屏蔽，只给每日语义。**不推荐走 0x0F**：硬件星期只能表达"每周某天"
  一种模式，且要多维护一条寄存器路径
- 采用的模型：**软件星期位掩码**（主流闹钟应用的标准模型）——
  设置层用掩码算出"下一次响铃的日期+时刻"，驱动仍用现有 `set_alarm`
  武装单次。一次代码路径覆盖全部模式

### 2.1 重复模式（核心需求：现在没法选重复）
- 存储新增 `alarm_days`（uint8 位掩码，bit0=周日 … bit6=周六）：
  - `0` = 一次性：响完自动关（`alarm_on=false` + disarm）
  - `0x7F` = 每天
  - 单 bit = 每周该天
  - `0x3E`（周一至五）= 工作日——掩码模型白送，一并提供
- 设置页 ALARM 区域加一行 DAYS，点按循环：
  `一次 → 每天 → 工作日 → 周日 → 周一 → … → 周六`
- 下一次计算：从今天起逐日找掩码命中日（最多推 7 天），
  今天命中但时刻已过则顺延；算出目标后走现有 arm 路径

### 2.2 开机对账武装（配套结构修复，来自 1.4b review）
现状的武装只靠"响铃结束后软件重设"一条路径：深睡被闹钟叫醒后中途关机
等路径走不完重设，闹钟会永久哑火（用户"感觉是一次性"的可能真因之一）。
改为：**每次开机、每次闹钟设置变更时，只要 `alarm_on` 为真，
就按 §2.1 的掩码重算下一次并武装**。响后重设保留，但降为冗余。

### 2.3 分钟步进 +10（用户提出）
- 位置：`muse_settings_ui.c:1183`，现 `+ 5 * tap_direction(e)`
- 改为 10 步进，且**越过 60 精确归 0**（不要纯取模——取模会让 55 分 +1 落到 5）：
  - 正向：`m + 10 >= 60 ? 0 : m + 10`
  - 反向：`m - 10 < 0 ? 50 : m - 10`
- 小时保持现状（+1、超 23 回 0，用户确认符合预期）

### 2.4 验收
- 一次：响后开关自动关、次日不响
- 每天/工作日/每周：各设一个近时刻实测，响后查次日武装状态正确
- 深睡叫醒后响铃中途关机 → 再开机，对账应恢复武装（2.2 的回归项）
- 分钟：50 分正向一按变 0；**55 分正向一按变 0（不是 5）**；45 分正向一按变 55；0 分反向一按变 50

## §5 已搁置：压缩 OTA（2026-10-23 评估，用户拍板：推送效果不大，不进本周期）

来源：ESPHome 2026.10 的 Compressed OTA（deflate 流式传输、约省 1/3 字节、
协商兼容新老设备、摘要覆盖解压后镜像、解压器分配失败回退明文）。

**可借鉴的是发布机制，不是它的解压器：**
- latest.json 双资产：同时挂明文 bin 与压缩包 + 各自 sha256（摘要永远对
  **最终镜像** 算，与现行做法一致）；新固件优先取压缩包，老固件不认新
  字段、照旧走明文——零破坏滚动升级
- 压缩路径任何一步失败 → 自动回退明文下载，不许把设备卡在升级半路

**官方轮子核查（乐鑫注册表）：**
- `espressif/bootloader_support_plus`（压缩 OTA 官方件）：下载 xz 压缩包
  进 OTA 分区、重启后由 **bootloader 阶段解压**，应用层仍用原 esp_ota API，
  压缩率 40–60%。⚠️ 两个门槛：① 注册表 0.3.9 的兼容表里**没有 ESP32-S3**
  （只有 32/C2/C3/C5/C6/H2），0.4.0 的 S3 支持待核实；② 它要换 bootloader，
  存量设备迁移属最高风险类变更（bootloader 无回滚）
- `espressif/esp_delta_ota`（差分 OTA 官方件）：只下版本间 patch。
  本项目只有一台设备、发版走 GitHub Releases，为每条升级路径生成 patch
  的流水线负担大于收益，不采用

**收益量级（本设备）**：固件约 2–3MB，压缩省约 1–1.5MB；家庭 WiFi 单跳、
OTA 低频，省的是几秒和少量射频电量——ESPHome 那种 15% 丢包网格
317s→74s 的场景不是本机现实。故：机制记下、组件待核（S3 支持），
实现单独成版（1.4d/1.5 候选），1.4c 不碰 OTA 路径。
若 bootloader_plus 确认不支持 S3，备选是应用层流式 inflate
（自写胶水，量级约几十行，届时再评估）。
