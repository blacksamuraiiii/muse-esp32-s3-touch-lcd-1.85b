## B1. 数学“取消金币上限”不生效——结算仍被夹在 20 枚

- **问题**：`esp32/components/muse/muse_pet.c:551`（`muse_pet_request_play_reward`）
  仍按 `MUSE_PET_ROUND_COIN_MAX`（20）夹取。数学 UI（`muse_mathpractice_ui.c:388-391`）
  已按 `MUSE_PET_ROUND_COIN_HARD_MAX`（钱包 100）算、worker（`muse_pet_model.c:406-407`）
  也已按 HARD_MAX 夹，但中间这道请求函数先把任何 >20 的数截成 20，worker 永远看不到
  20 以上。可达路径：数学 60 秒一局答对 20 题（+2/题 = 40 分）→ UI 算出 40 枚 →
  请求函数截成 20 → worker 付 20。用户定的“取消上限”在真机上仍是 20。
  host 测试没 catch 的原因：harness 只直接调 `muse_pet_model_apply`（模型），不走
  `muse_pet.c` 的请求函数（依赖 FreeRTOS/NVS，主机侧编不过）。
- **修法**：`muse_pet_request_play_reward` 的夹取改成 `MUSE_PET_ROUND_COIN_HARD_MAX`
  （一行）。其它游戏不受影响——它们的 UI 各自仍按 20（`muse_pet_round_coins` /
  各自的 cap）换算，传进来的数本来就不超过 20。在注释里写明：请求函数与 worker
  的夹取必须同为 HARD_MAX，免得下次改价又只改一边。
- **验证**：请求函数主机侧编不过，**需真机或代码复核**——数学答对 20 题后看实得
  是否为 40 枚（而不是 20）。主机侧已有 `muse_pet_round_coins_cap` 的数学路径
  断言（`tests/pet_economy_harness.c:105-107`，25 枚照付），本次不新增 host 断言，
  只在注释里钉住口径。

## B2. Test 版攒下的掷筊台账会让 Release 版判整个宠物状态非法，奖励全停且无法恢复

- **问题**：`esp32/components/muse/muse_pet_model.c:67-68`（`muse_pet_model_valid`）
  用 `MUSE_PET_JIAOBEI_DAILY_MAX`（Test 999999 / Release 9）校验 `jiaobei_count` /
  `jiaobei_streak`。`muse_pet.c:377-390` 的加载路径在 blob 版本/尺寸/valid 任一失败时
  直接 `ESP_LOGE("invalid storage; rewards disabled")`、置 `s_storage_error`、worker
  任务自删——**全部**宠物奖励停摆（喂食、摸摸、抽签、掷筊、小游戏一并停），不是只把
  掷筊计数截断。可达路径（就是用户现在的正常流程）：测试版上某天掷了 >9 次，
  NVS 里 `jiaobei_count` 已是两位数；同一块板刷回正式版，`DAILY_MAX` 变回 9，
  `valid()` 失败。恢复途径只有 Test 专属的 `>pet.reset`（正式版里只回
  `@pet unknown command`）——正式版上无法恢复，只能重刷测试版清掉整个 blob
  （丢全部金币与账本）再重刷正式版。日界滚动在 valid 检查之后，跨天也不能自愈。
- **修法**：`valid()` 里对 `jiaobei_count` / `jiaobei_streak` 改用与构建无关的固定上界。
  在 `muse_pet_model.h` 的 `MUSE_PET_JIAOBEI_DAILY_MAX` 旁新增
  `#define MUSE_PET_JIAOBEI_LEDGER_MAX 999999u`（结构合法性上界，与每日 9 次的
  策略上限无关），`valid()` 里两处改用它。每日 9 次上限仍由 `model_apply`
  强制（不动）。注释写明：valid 只校验“结构合法”，不应依赖构建期策略常量。
- **验证**：补主机测试（`tests/pet_economy_harness.c`）：构造 `jiaobei_count=50`
  的模型断言 `valid()` 为真；且当日仍按 9 次封顶（第 10 次返回 `PET_CAP`）。
  两项都要真跑过。

## B3. 翻面动画在 50ms 定时下严重混叠，换面/换镜像都不是“侧立时看不见”

- **问题**：`muse_jiaobei.c:143-154`（`muse_jiaobei_flip_angle`，线性 0→1080°/1000ms）
  × `muse_jiaobei_ui.c:289-317`（`sx = |cos(angle)| * 256`，`mirror = cos < 0`，
  50ms 定时器）。每 tick 角度步进 54°，`sx` 单帧跳变最高 206/256（79→243、1→207），
  且同一四分之一圈内先缩后胀；换镜像在宽度 150→79（约 31% 宽）时发生；换面在
  450ms tick（角度 486°、`sx=150`）发生，新面以 59% 宽度直接出现。根因是每圈只有
  约 6.7 帧，`|cos|` 在 54° 采样下必然混叠。这是三版迭代要交付的核心视觉效果，
  用户已因翻面观感否过两版，此版上真机大概率再被否。
- **修法（三选一里选第 ① 种）**：翻面改回 **1 圈/1000ms**——`MUSE_JIAOBEI_FLIP_TURNS`
  3→1。竖直中轴线 + 镜像贴图不动。② 改 20ms 定时器会牵连摇一摇采样（同一定时器），
  ③ 延到 2000ms 会让翻面拖沓，都不取。
  只改圈数不够：换面点 `5/12` 是按 3 圈算的（450°，离中点最近的侧立点）；1 圈时
  5/12 对应 150°，`sx=|cos 150°|≈222`，换面照样看得见。**换面点必须同步改到
  1/4（250ms、90°、侧立点）**：`muse_jiaobei.c` 的 `muse_jiaobei_tick` 里
  `FLIP_MS * 5u / 12u` 改成 `FLIP_MS / 4u`，注释同步改（1/4 处是第一个侧立点，
  此后半程显示新面；`scale_y` 的旧说法改成 `scale_x`，水平轴改成竖直轴）。
  1 圈时每 tick 步进 18°（每圈 20 帧），`sx` 序列每四分之一圈单调，单帧最大跳变
  约 79/256（79→0 那一跳），换镜像与换面都落在 `sx=0` 的 tick 上。
- **验证**：补主机侧断言（`tests/jiaobei_harness.c`，现有 harness 只断言角度值，
  不覆盖 UI 的 `sx` 序列）：逐 tick 由 `muse_jiaobei_flip_angle()` 算 `sx`，
  断言每四分之一圈内单调、单帧跳变 ≤ 80/256；换面发生的那个 tick 断言
  `sx ≤ 16`。新断言要真跑过。另须真机看一眼翻面观感（1 圈是否合意）。

## F1. `muse_lcd_bands_run()` 超时竞态 + 陈旧完成信号 + 栈参数悬空

- **问题**：`esp32/components/muse/boards/muse_lcd_bands.c:432-455` 结合 `:315-320`。
  调用方 A 在 `:450` 取 `s_call_done` 超时后释放 `s_call_lock` 返回，此时队列里
  A 的 call 项仍在排队；调用方 B 随后取锁成功，在 `:442` 覆写全局
  `s_call/s_call_arg` 为自己的 fn/arg；发送任务恢复后取出 A 的 call 项，执行的是
  B 的 fn（A 的 fn 永远不跑，B 的 fn 跑两次），并 `give(s_call_done)` 两次；多余的
  一次 give 留下陈旧令牌，下一个调用方的 `:450` 会立即返回，误以为自己的 fn
  已执行。另有栈上参数悬空：`muse_lcd_bands_frame()` 在 `:574` 传栈上 `&j`
  （`frame_job_t`），`board_waveshare_s3_touch_lcd_185b.c:1143/1765` 的
  `panel_sleep()` 传栈上 `&sleep`——超时返回后调用方栈帧可被复用，发送任务随后
  解引用的是已失效的栈内存（`send_panel_sleep` 读 `*(bool *)sleep`，可能把
  SLPIN/SLPOUT 读反）。触发前提是发送任务已卡 >2 秒（已劣化），正常路径不受影响。
- **修法（值语义，一次做到底）**：
  1. `band_t` 增加 `fn` / `arg` 字段，call 项自带要执行的函数与参数；发送任务执行
     该项自己的 fn/arg，不再读全局 `s_call` / `s_call_arg`（全局删掉）。错 fn
     竞态随之消失。
  2. 取锁后先排空 `s_call_done`（`xSemaphoreTake(s_call_done, 0)` 循环到取不到
     为止），丢掉上一次超时残留的陈旧令牌；此后 `:450` 的 take 只可能由本次
     call 项的 give 唤醒。
  3. 栈参数改按值携带：`muse_lcd_bands_frame` 的 `frame_job_t` 嵌进 call 项本身
     （`band_t` 里加 `frame_job_t job` 字段，发送任务把指向自己那份拷贝的指针
     传给 `send_frame`——队列按值拷项，发送任务手里的那份在 `send_frame`
     返回前一直有效）；`panel_sleep` 的 `sleep` 布尔改按值传
     （`(void *)(uintptr_t)sleep`，`send_panel_sleep` 按值读回，不再解引用
     调用方的栈）。`muse_lcd_bands_frame` 的 `fill` 回调与 `j->arg` 仍由调用方
     保证在调用期间有效（视频路径的 fill 参数生命周期不变，本次不动）。
  4. 在 `muse_lcd_bands_run` 的注释里写明：fn/arg 由队列项按值携带，超时返回后
     该项仍可能随后执行——arg 必须在调用方存活期外有效（或嵌进项里），
     栈上临时量一律不许直接传指针。
- **验证**：无现成 host harness 覆盖此文件（依赖 FreeRTOS/ESP-IDF），代码复核；
  真机验证：屏保路径（面板 sleep/wake）走一遍 + 断档日志里不应出现
  `band call:` 超时行。另确认 `band_t` 加字段后队列创建（`sizeof(band_t)`）
  与 `send_bands` 的 `!b.data` 判 call 项逻辑仍正确。

## F2. 单次 >100ms 的慢读不会立即停摇一摇，与笔记/提交 message 的说法不符

- **问题**：`esp32/components/muse/muse_jiaobei_ui.c:477-499`（`update_shake`）。
  笔记 §二.3 与提交 `7872d1b` 的 message 都写“连续 3 次失败或单次 >100ms 就本页
  停掉摇一摇”，但实现把 `err != ESP_OK || took > 100` 统一记为一次 strike，
  要连续 3 次 bad-or-slow 才停。I2C 总线卡住时，每次 strike 都在 LVGL 线程上
  阻塞至多约 1 秒，退避生效前一个 visit 最多吃 3 次、约 3 秒的冻结，而不是所述的
  1 次。
- **修法（改实现，不改文字）**：`took > MUSE_JIAOBEI_SHAKE_SLOW_MS` 时直接把
  `s_shake_fail` 置到 `MUSE_JIAOBEI_SHAKE_FAIL_MAX` 并打 WARN（单次慢读立即停，
  与笔记/提交 message 一致）；`err != ESP_OK` 的失败读仍按连续 3 次才停
  （失败读本身不阻塞，留 3 次容错）。成功读后清零的复位逻辑不动。
- **验证**：无 host harness 覆盖 UI 层，代码复核；真机验证：I2C 卡住时摇一摇
  应在一次慢读（≤1 秒冻结）后停掉，点筊不受影响。

## F5. 筊面缓存无释放、无二次建页保护

- **问题**：`esp32/components/muse/muse_jiaobei_ui.c` 全文件无 `heap_caps_free`，
  `s_cup_buf` 是静态数组；建页入口 `muse_jiaobei_ui_build()`（`muse_interact_ui.c:1991`）
  由 `muse_interact_ui_build()` 调用，`muse_ui.c:2007` 开机只调一次，故现网无泄漏。
  但若将来二次调用，会丢 160KB 旧缓冲且描述符悬空。
- **修法**：建页开头加二次建页守卫——`if (s_cup_buf[0][0][0] != NULL) return;`
  并在注释里写明：本页开机只建一次，二次调用直接返回（不重建 LVGL 对象、
  不重分配 160KB 缓冲）。PSRAM 不足时行为已核实为可降级（分配失败只藏杯，
  页面照常工作），本次不动。
- **验证**：代码复核（守卫在建页开头、任何分配与 LVGL 对象创建之前）。

## F6. sfx 任务栈 3072 是全仓音频任务里最小的，且无水位检查

- **问题**：`esp32/components/muse/muse_audio.c:632`（`SFX_TASK_STACK 3072`，
  对比 TTS 12288、词音播放 24576）。调用链（worker → `muse_audio_sfx_sync` →
  渲染 → `esp_codec_dev_write` → I2S 驱动）按估算够用，但无
  `uxTaskGetStackHighWaterMark` 检查，真机上看一眼水位再定。另
  `sfx_worker_init()`（:653-668）失败时只记一条 `ESP_LOGE`，之后所有
  `muse_audio_sfx()` 都回 `ESP_ERR_INVALID_STATE`，游戏音整机静默——PSRAM
  耗尽时才触发，概率低但无声。
- **修法**：`SFX_TASK_STACK` 3072 → **4096**（调用链估算：worker 帧 + sync
  渲染帧 + codec 写帧 + I2S 驱动帧约 2KB 出头，4096 留约一倍余量；渲染缓冲
  是静态 PSRAM，不占栈）。注释里写明：真机须用 `uxTaskGetStackHighWaterMark`
  确认水位，水位 <512 字节时再往上加。`sfx_worker_init()` 失败的 `ESP_LOGE`
  保留（启动日志里可见），再补一行注释说明失败后果（此后全部游戏音静默，
  只响于 PSRAM 耗尽时）。
- **验证**：代码复核；真机验证：跑一遍各游戏音效后看水位（`uxTaskGetStackHighWaterMark`），
  确认余量 ≥512 字节。
