## 1. 统一抗锯齿中文（用户已拍板：单套文泉驿微米黑 16px 4bpp）

app 槽 4MB，1.3 产物 3,084,288B（73.5%）。
根因：`gen_ui_font.sh` 只从源码字面量取字（255 字子集），永远覆盖不了任意会话回复。
分区口径：1.85B 板 Flash 16MB、PSRAM 8MB；构建链后加载 `devices/sdkconfig.muse`，
分区表为 `partitions_muse.csv`（ota_0/ota_1 各 4M），故 app 上限是 4MB；
`sdkconfig.defaults` 里的 `partitions.csv`（各 2M）只是通用默认值，不适用于这块板。

## 2. WiFi 断联后一直 joining（用户确认非网络问题）

已核实的确切问题（生产代码，全仓库搜过）：
- 除 bench（`muse_power_test.c`）外，没有任何地方调用 `esp_wifi_stop()` / `esp_wifi_deinit()`。
  设置里关开 WiFi 只走 `muse_wifi_apply()` → `keeper_kick(KEEP_WIFI)`，复用同一驱动实例，
  驱动一旦卡住，开关救不了。
- `power_off()`（`muse_input.c` + 板级 `power_off()`）进 `esp_deep_sleep_start()` 前不停 WiFi。
- keeper 状态映射有兜底分支（未连接、非 joining、非 away、无失败详情 → CONNECTING），
  屏上“连接中”不一定等于正在连接；但用户现确认是真 joining（keeper 在反复 join），
  故以驱动卡住 / join 挂起为主攻方向。

- [ ] 驱动真重启路径：新增 `wifi_mgr_restart()`（`esp_wifi_stop()` → `esp_wifi_start()`，
      并清 BSSID 缓存与信道提示、复位 retry/backoff、`s_sta_idle=true`，重启后重设 PS_NONE），
      经 `muse_link` 的 `muse_wifi_restart()` + ops `wifi_restart` 暴露；
      keeper 新增 `KEEP_WIFI_RESTART` 位处理。
- [ ] 设置开关关开走真重启：设置里 WiFi 由关 → 开时调 `muse_wifi_restart()`（而非仅 `apply`）；
      唤醒时的常规重连仍走 `apply`，不改。
- [ ] keeper 挂起兜底：连续 join 失败 3 次（或单次 joining 超过 `CONNECT_TIMEOUT_MS` + 裕量）
      仍未连上时，先 `wifi_mgr_restart()` 再重试，重启计数在成功后清零，不得无限重启循环
      （NOT_NEARBY 不计入；无成功时最多 3 次）。
- [ ] 睡前干净收尾：板级 `power_off()` 进深睡前先 `esp_wifi_disconnect()` + `esp_wifi_stop()`
      （失败只记日志，不阻塞关机）；浅睡 CPU 掉电前先切 modem sleep（与 2 分钟后的 nap
      断开路径对齐，不得破坏 resting voice 等待）。
- [ ] 超时清缓存：join 超时（非失败返回）时同样清 BSSID 缓存与信道提示并改全信道扫描重连，
      不只在失败返回时清（现 `wifi_mgr_connect()` 只在失败返回且 have_bssid 时清）。
- [ ] 诊断留口（不阻塞本轮）：下次复现抓串口三行 —— keeper 的 joining/looking/retrying、
      wifi_mgr 的 `station disconnected reason=`、`esp_wifi_connect` 返回值；
      并确认是长按关机深睡还是息屏 nap / 浅睡（开机日志的 reset reason + wake cause 可区分）。

## 3. Review 1：喂饭连点，字幕说谎（金币是对的）

`muse_interact_ui.c` 的 `on_feed_food` 无 pending 保护，第二 tap 会覆盖
`s_last_feed_idx` / `s_last_feed_before`，第二次反馈仍写“+10”但实际未给币。
小游戏有 SHAKE 保护、运势重复抽是 SAME、摸摸按 tap 结算，故只有喂饭有此问题。

- [ ] `on_feed_food` 加 `s_feed_pending`：请求未回之前忽略新的喂饭点击；
      反馈到达（OK / STORAGE / 其他结果）时清 pending；`muse_pet_request()` 返回 false 时不置 pending；
      另加 5 秒超时兜底，防反馈被丢后按钮永久卡死。

## 4. Review 2：消耗公告 ACK 午夜竞态（低概率，真实）

互动 tick 公告“毛毛这几天花了 X 金币”后发 `PET_DECAY_ACK`；若 worker tick 在此间
因跨日（08:00 日界）产生新公告，ACK 会把新公告静默清掉（金币已扣对、只是公告丢了）。

- [ ] ACK 带 `decay_day`：新增 `muse_pet_decay_ack(day)`（或等价带参 API），
      worker 仅当 `state.decay_day == day` 时清 `decay_notice`，否则忽略；
      UI 公告时记下当日 day 并用该 day 发 ACK；旧的无参 `PET_DECAY_ACK` 动作相应废除
      （由 `muse_pet_request()` 拒绝，全仓搜引用并改掉）。

## 5. Review 3：worker 反馈 `portMAX_DELAY` 潜在 stall

反馈只是 UI 通知、快照才是权威；现 worker 发反馈用 `portMAX_DELAY`，队列满且
LVGL tick 万一停排空时 worker 会卡住（正常运行时 tick 每帧排空、即使 tile 隐藏也排，
故目前未爆出）。

- [ ] worker 发反馈改超时发送（如 100ms），超时则丢弃并记一条日志，不得无限等待。

## 6. Review 4：Release 下串口 `pet.*` 命令仍可改金币

在 Release 里也能改金币（物理串口可及，风险不高，但不应是默认没人注意的状态）。

      为防 Release 未使用函数警告，相关辅助函数也一并门控，`pet.status` 用的保持常驻。
