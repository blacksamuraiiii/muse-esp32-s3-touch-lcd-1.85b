## 1. 三链路架构（固件 → 服务器）

三条链路共用**同一条 HTTPS 连接、同一个端点、同一个令牌**，差别只在请求参数与播放路径。

### 1.0 公共骨架

- **端点模板**（`esp32/components/muse/muse_tts.c:644-680` `tts_template_into()`）：
  `<url>[?|&]k=<key>&voice=<voice>&rate=<rate>&text={text}`；`url` 优先取设置页（裸主机自动补 `https://`），否则取构建期 `CONFIG_MUSE_TTS_URL`。
  实机生效端点（本次实机核查）：`https://<TTS 桥域名，见本机 sdkconfig.local>/`，nginx 根路径 `rewrite ^/$ /tts last`。
- **百分号编码**：`muse_tts.c:150-171` `url_encode()`，只放行 `A-Za-z0-9-_.~`，其余一律 3 字节编码；请求行缓冲 `TTS_HTTP_TX_BUF 2048`（`muse_tts.c:51`，注释记录了 512 默认值会被 180 字节中文分块撑爆 → `Out of buffer` 丢块的历史）。
- **单请求文本上限** `TTS_TEXT_CHUNK = MUSE_SENTENCE_CHUNK = 180` **字节**（`muse_sentence.h:33`）；服务端 `TTS_MAX_CHARS=180` 是**截断**不是拒绝（`tts-server/tts_server.py:123,191` `[:MAX_TEXT_LEN]`），180 字节中文只有 60 字，远不到上限。
- **一条长连接**：`s_client` 由 `ensure_client()/drop_client()`（`muse_tts.c:319-373`）管理，`keep_alive_enable=true`；空闲超 `TTS_IDLE_DROP_US = 45 s` 在**复用前**主动重建（`muse_tts.c:135,329-333`），因为桥的 nginx 300 s 就关连接而 lwIP 仍报 connected。
- **三用户一把锁**：回复 worker / prewarm 探针 / 卡片取词共用 `s_client_lock` + `s_raw_active`（`muse_tts.c:113-128,432-491`，1.5.3a B1）。卡片取词入口 `muse_tts_fetch_raw()` 遇 `s_busy || s_prewarm || s_prewarm_task || s_raw_active` **直接返回 -1 拒绝**（`muse_tts.c:444-447`）。
- **服务器侧**：`<腾讯云 VPS，IP 不入库>`（OpenCloudOS，宝塔 nginx 80/443）→ `upstream muse_tts_backend { server 127.0.0.1:5050; keepalive 16; }`（`vhost/nginx/0.muse-tts-upstream.conf`）→ Docker 容器 `muse-tts:1.6`（`tts_server.py` + waitress，`threads=8`）。nginx 侧 `proxy_buffering off`、`proxy_set_header Connection ""`、`proxy_request_buffering off`。

### 1.1 链路一：毛毛（宠物）聊天回复 TTS

1. `muse_chat_session.cpp:1044 turn_start()` → `:1049 muse_tts_new_turn()`（C4 世代作废旧回合）→ `:1084 muse_tts_prewarm()`。
2. `muse_tts_prewarm()`（`muse_tts.c:873-915`）在**模型写字的 4–7 s** 里起 `prewarm_task`（栈 `TTS_PREWARM_STACK 8192`，`muse_tts.c:137`）打**根路径**（不带 text → 不合成、不耗额度），只买 TCP+TLS，403 也算成功；日志 `prewarm: connection ready in 3109 ms`（引用出处：`notes/20261110`）。
3. 文字到句界后 `muse_tts_speak()`（首句，置 `s_reply_first`）/ `muse_tts_enqueue()`（后续句预取）→ 通知 `tts_task`（栈 `TTS_TASK_STACK 12288`，PSRAM，`muse_tts.c:58,933`）。
4. `fetch_reply()`（`muse_tts.c:736-785`）按 180 字节分块循环：首块带 `&first=1`（桥在首个逗号切断抢首音，C1）、末块带 `&last=1`（C2 末段标记 `X-TTS-Last`）。
5. 首块超时 `TTS_HTTP_FIRST_MS 3000`，收到头后恢复 `TTS_HTTP_TIMEOUT_MS 8000`；失败且**一个字节都没进解码器**才重试一次，重试前等 `TTS_RETRY_DELAY_MS 150`（`muse_tts.c:610-630`）。
6. 回调 `on_http_data` → `gate_feed()`（前 8 字节必须像 MPEG 帧同步 `0xFF` 或 `ID3`，否则整条判坏、不重试）→ 16384 字节 PSRAM ring（`TTS_RING_BYTES`，`muse_tts.c:44`）→ 主循环 `pump_tts/decode()`（minimp3）→ I2S。
7. 打断（barge-in）：`muse_tts_cancel()` bump `s_gen`、置 `s_abort`、清 ring（失败则 `s_ring_dirty` 交给 worker 先清）；`ring_send` 3 s 堵死只在**当前世代**才置 abort（`muse_tts.c:185-205`）。

### 1.2 链路二：英语单词卡发音 TTS

1. 进组 `muse_wordcards_ui_show()` → `muse_wordcards_audio_prefetch()`（`muse_wordcards_ui.c:328,878`；开始页 `begin_game()` :320-331 也调一次）。
2. **复用链路一的连接**：`muse_tts_fetch_raw()`（`muse_tts.c:432`）拿同一把锁、同一个 `s_client`，回调走 `s_raw` 分支原样收字节，不进 ring、不进解码门。
3. URL 由 `muse_tts_url_for_text()`（`muse_tts.c:702-734`）在 `{text}` 后追加 **`&word=1`**；服务端 `tts_server.py` 见 `word=1` 就**忽略 URL 的 voice/rate**，固定 `en-US-AriaNeural -10%`，优先读磁盘 `TTS_WORD_DIR=/app/word_audio`，命中直接回，未命中才合成一次并落盘。
4. 任务分工（`muse_wordcards_audio.c`）：`fetch_task` 栈 `WC_TASK_STACK 12288`（:40，PSRAM），`play_task` 栈 `WC_PLAY_STACK 24576`（:47，12 KB 曾 panic）；每词 PSRAM 槽 `MUSE_WORDCARDS_MAX_MP3_BYTES = 32768`（`muse_wordcards.h:84`）；单词超时 `WC_HTTP_TIMEOUT_MS 8000`（:39），`fetch_one()`（:264-304）**重试 1 次**，再失败标 FAILED；传输级失败（-1）**放弃整组剩余词**（:432-446）。
5. **预取内存门** `WC_MIN_INTERNAL_FOR_TLS = 4608`（:79）：内部最大空闲块 < 4608 B 就整组跳过并全标 FAILED（:375-388），门值上下各有一次实测依据（注释 :61-78：崩溃点 4 KB、正常运行 ~5 KB）。
6. 播放：50 ms tick `drain_pending_audio()`（`muse_wordcards_ui.c:342-371`）READY 即播、FETCHING 等、FAILED 给**一次**点按单取（2026-11-17 方案②）。尾静音裁剪 `WC_SPEECH_PEAK/MIN_MS/TAIL_SILENCE_MS = 300/200/200`（:57-59,786-805）。

### 1.3 链路三：英语听力（quiz）出声 TTS

**结论：听力不自建链路，完整复用链路二的取词/播放机制**（读码确认，非猜测）：

- `muse_quiz_ui.c:331/583` 调 `muse_wordcards_audio_prefetch_quiz()`；`:355` `muse_wordcards_audio_play_quiz()`；`:364` `muse_wordcards_audio_fetch_one_quiz()`；`:602-603` 离页 `stop()+prefetch_abort()`。
- 底层同一个 `fetch_task`、同一把 `s_client_lock`、同一个内存门、同一套排队（`s_fetch_wanted`），只是**独立槽池** `s_quiz_slot[MUSE_QUIZ_QUESTIONS=5]`（`muse_wordcards_audio.c:94-99`），与单词卡的 8 槽池互不覆盖（:94-97 注释）。
- URL 同样带 `&word=1`；题库池 20 词（`muse_quiz.c:28-33 k_pool`，取自词卡表的 set 0/1/6/8）。
- **首音时序**：`reset_round()` 置 `audio_pending=true`（`muse_quiz.c:129` “the first question reads itself”），50 ms tick 见 READY 就播；切题/重播各置一次标记（:177,213）。所以首音 = **进组取词任务启动 + 冷握手（若无温连接）+ 第 1 题答案词取回**。
- 60 秒局时钟只在 `PLAYING` 跑 drain（`muse_quiz_ui.c:374-379`），代际 `quiz_gen` 防过期重试在 OVER 后播出来。

### 2.3 三链路首音账（合计 = 各段相加，**推算**，分段来源见上）

| 链路 | 冷（无温连接） | 热（温连接） |

| ② 单词卡 | 握手 3.5–4.3 s + 词音取回（磁盘命中 TTFB 74–82 ms）≈ **3.6–4.4 s**；再叠加内存门/连接被占的失败重试（见 N2/N3） | 翻面即播 ≈ **20–80 ms** 取回 + 解码；实测同连接 4 词 0.40 s 起、其后 ~18 ms |

## 4. 新发现问题清单（9 条：P1 ×3、P2 ×6；均未见于上述基线文档）

### N1 — P1 · 服务器限流 60 r/m（1 请求/秒）+ burst 20，固件对 429 零处理

- **路径**：服务器 `/www/server/panel/vhost/nginx/0.muse-ratelimit.conf:2`
  （`limit_req_zone $binary_remote_addr zone=tts_per_ip:10m rate=60r/m;`）+
  `/www/server/panel/vhost/nginx/extension/<TTS 站点目录>/proxy.conf:1-2`
  （`limit_req zone=tts_per_ip burst=20 nodelay; limit_req_status 429;`）；
  固件侧 `esp32/components/muse/muse_tts.c:568-570`（`status != 200` → `drop_client`，不区分状态码）、
  `esp32/components/muse/muse_wordcards_audio.c:289-291`（非 200 → FAILED）、全仓库无 429 分支（`grep -rn "429" esp32/components/muse/` 无功能命中）。
- **机制**：`rate=60r/m` 即稳态 1 请求/秒，`burst=20 nodelay` 只给 20 个瞬时额度。一次语音回复按 180 字节分块 ≈ 6–8 个请求，单词卡进组 4–8 个，听力进组 5 个，失败重试再翻倍——**一次连续操作就可能吃掉整个 burst**，随后按 1 r/s 放行，超出即 429。固件收到 429 与收到 502 同等对待：回复侧 `fetch()` 因“payload 没打开”重试一次（150 ms 后仍会撞限流）→ 该句及之后整段转静默；卡片侧标 FAILED，且可能连带 N3 的“整组放弃”。
- **证据（实测）**：nginx access 4473 行、近 2000 行状态计数 `200×681 / 403×1313 / 400×6`，**尚无 429** → 潜在风险、未爆。
- **为何现在提**：限流是 2026-11 之后加的（`0.muse-ratelimit.conf`），基线文档全部写于它之前/未提及；固件与它的交互无人评估过。

### N2 — P1 · 点按重试的“一次性”标志在内存门判定**之前**置位，门一跳过就把唯一一次重试烧掉

- **路径**：`esp32/components/muse/muse_wordcards_audio.c:375-388`（`fetch_task()` 内的 `WC_MIN_INTERNAL_FOR_TLS` 门，跳过时把**包括被重试的那个词在内**的未 READY 词全标 FAILED）；
  `esp32/components/muse/muse_wordcards_ui.c:362-366`、`muse_quiz_ui.c:363-367`（先 `retry_failed_audio()` 置位再 `fetch_one()`）；
  `esp32/components/muse/muse_quiz.c:237-239`、`muse_wordcards.c` 对应重试函数（**置位先于取词**）。
- **机制**：重试位 `audio_pending_retried / pending_audio_retried` 在**发起**单取时就置 1；而门在 `fetch_task` **内部异步**判定。时序是：点按 → 置位 → 任务起来 → 门拒绝 → 词回 FAILED → 下一 tick 见 FAILED，但重试函数返回 false（已用过）→ `clear_pending_audio()` 静默丢标记。**结果：堆仍紧张时，2026-11-17 方案②提供的唯一补救被无声消耗，卡片回到“点了没声”。**
- **触发条件**：内部最大空闲块 < 4608 B（注释记录 Link 连上后正常值约 5 KB，**余量只有约 400 B**，LVGL 渲染一波动就可能跌破）。
- **严重度**：P1 —— 这正是用户 2026-11-17 上报症状的同一条路径，基线文档只写了“门是防崩机的、不能绕”，**没有覆盖“门会吃掉重试”这个交互**。
- **验证**：串口出现 `prefetch skipped` 的同时点卡 → 观察是否仍静默；对照修后日志应看到门失败后重试位回滚、第二次点按可再取。

### N3 — P1 · 回复进行中 / prewarm 探针期间的卡片取词被“拒绝”，却被当成“传输故障”→ 整组放弃

- **路径**：`esp32/components/muse/muse_tts.c:441-447`（`client_lock_take(0)` 失败、或 `s_busy || s_prewarm || s_prewarm_task || s_raw_active` → **返回 -1**）；
  `esp32/components/muse/muse_wordcards_audio.c:285-288`（-1 → `return -1`）+
  `:432-446`（`r < 0` 分支：**把 i 之后所有未 READY 的词一并标 FAILED 并 `break`**，注释理由是“主机不可达，剩下的也会一样失败”）。
- **机制**：**“我暂时不能借你连接”和“网络真的断了”共用同一个返回值 -1**，于是“拒绝”被升级成“整组放弃”。`s_busy` 覆盖整条回复的取音频阶段（数秒到十几秒），`s_prewarm_task` 覆盖 turn_start 后的探针期（`TTS_PREWARM_TIMEOUT_MS 6000`，实测握手 3109 ms）。窗口内进单词卡/听力页 → 整组 FAILED → 翻面静默；此时若回复仍在继续，点按单取同样被拒，而该次点按重试也已按 N2 的方式被消耗。
- **注**：`muse_tts.c:416-430` 的注释承认 “a refusal is silent”，但**没有承认返回值 -1 会触发“放弃整组”的放大效应**；`muse_wordcards_audio.c:432-438` 的注释只按“主机不可达”写的。两者组合的结果未在任何基线文档中出现。
- **严重度**：P1（整组静默 + 与“进组即玩”体验底线冲突），但有 N2 之外的兜底路径（离页重进重新预取）。

### N4 — P2 · 首请求 3000 ms 预算 < 实测冷握手 3.5–4.3 s，prewarm 一旦没落地就必然超时重试

- **路径**：`esp32/components/muse/muse_tts.c:66`（`TTS_HTTP_FIRST_MS 3000`，注释 :62-66 解释“3 秒放弃是为了快点重试”）；
  对照 `notes/20261110` 实测冷握手 **3.5–4.3 s**；prewarm 的三个早退口 `muse_tts.c:880-896`（`muse_tts_active()`、已有探针、`client_lock_take(0)` 拿不到锁——**卡片取词正持锁时必然早退**）。
- **机制**：prewarm 没落地时，首块请求在**新建连接**上跑，3 s 预算小于实测握手耗时 → 必然超时 → 150 ms 后重试（此时用 8000 ms、重新握手）→ 首音多付 ≈3.15 s + 一次完整握手。`notes/20261027:190` 记录过同型事故：“首句请求整整 8 秒收到 0 字节，重试才成功，文字到出声 15.1 秒”。
- **标注**：**推算 + 待实测**（本机无 ESP-IDF 工具链、无真机，无法确认 IDF 的 `timeout_ms` 是否覆盖 TLS 握手本身；需串口抓 `TTS request failed: … budget 2048` 与 `prewarm:` 两行的时间关系）。

### N5 — P2 · prewarm 任务栈 8192，而同样要跑 TLS 握手的另外两个任务分别要 10240 / 12288

- **路径**：`esp32/components/muse/muse_tts.c:137`（`TTS_PREWARM_STACK 8192`）vs `:1059-1061`（`SPEECH_PROBE_STACK 10240`，注释原文：“8 KB was enough on paper and not in practice”）vs `:55-58`（`TTS_TASK_STACK 12288`，注释原文：TLS 握手在该任务上跑，mbedtls 要的比 8 KB 多）。
- **机制**：`prewarm_task`（`muse_tts.c:833-871`）做的是**同一类** TCP+TLS+证书链验证，却拿最小的栈，且**从未打印过 `uxTaskGetStackHighWaterMark`**。一旦溢出是 panic（栈在 PSRAM，越界写穿相邻对象），不是优雅失败。
- **标注**：**风险推算**。现网确实跑通过（`prewarm: connection ready in 3109 ms`，引用 `notes/20261110`），但没有余量证据；两处现场笔记都说 8 KB 不够。

### N6 — P2 · nginx access log 明文记录完整查询串，等于把共享令牌写进日志

### N8 — P2 · 一次“服务端已完成、客户端 30 s 未收到”的响应悬挂（单次、未复现）

### N9 — P2 · 整组已 READY 的回组预取，仍要先等在播的词最多 6 秒

## 5. 优化建议（P0 ×2、P1 ×3、P2 ×5）

### P0-1 · 门失败不消耗点按重试（对应 N2）

- **做法**：`fetch_task()` 走内存门跳过分支时，把本次 `single` 取词对应的重试位**回滚**（词标回 FAILED 的同时清 `*_retried`），或改成“门拒绝即视为任务没启动”，让 `fetch_one()` 返回 false、由 UI 现有分支丢标记（重试位随之可下次再用）。
- **收益**：用户在堆紧张时点卡仍有第二次机会，直接消掉“点了没声”的一条复发路径；改动面小（音频层一个分支 + 逻辑层一个回滚函数）。
- **代价**：需保证回滚不产生 50 ms tick 驱动的无限重试——沿用现有“每标记一次”的语义即可，回滚只在“任务确实没取到任何字节”时发生。
- **验证**：host 层加两个用例（门拒绝 → 重试位仍为 false；门通过 → 重试位为 true）；实机串口在 `prefetch skipped` 后连点两次，第二次应发起取词。

### P0-2 · 把“连接被占”从“传输故障”里分出来，禁止整组放弃（对应 N3）

- **做法**：`muse_tts_fetch_raw()` 对“忙/探针中/锁被占”返回独立值（如 `-2`），`fetch_one()`/`fetch_task()` 对该值只标**当前词** FAILED 并结束本轮（不进入 `r < 0` 的整组放弃分支），同时让点按单取在该场景下**不消耗**重试位。
- **收益**：回复进行中打开单词卡/听力不再“整组静默”，失败被限制在一个词/一次 tick；也顺带缓解 N1 的 429 后果（同一套“非真故障不放大”逻辑）。
- **代价**：多一个返回值与两处分支；要确认不会把“真·连接被占导致的连续失败”变成逐词拖时间（可用“连续两次被拒就结束本轮”封顶）。
- **验证**：host 层桩 `muse_tts_fetch_raw` 返回 -2，断言其余词状态不变、无 `break` 放弃；实机在语音回合进行中进单词卡，翻面应“这一组失败但点按可救”，而不是全组 FAILED。

### P1-1 · 限流参数与固件 429 处理一起调（对应 N1）

- **做法**：服务器 `rate=60r/m` 提到 `300r/m`（或 `burst=20` 提到 `60`，二者取一即可），保留 `limit_req_status 429`；固件侧给 429 单独的处理——回复链路延后 1–2 s 重试一次，卡片链路把词标回 FAILED 且**不消耗**重试位（与 P0-1/P0-2 同批）。
- **收益**：消除“密集操作把 burst 打穿 → 整段静默/整组静默”的隐性故障；这是当前唯一**尚未发生但一旦发生用户完全无法自救**的链路级风险。
- **代价**：抗刷能力下降——但入口已有令牌闸门（无令牌 403，日志实测 1313 条全被挡），限流的实际价值只剩“防令牌泄露后的滥用”，放宽是安全的。
- **验证**：从 WSL 用令牌连发 40 个短请求，改前应见到 429、改后应全 200；同时观察 `/health` 与 Azure 用量无异常。

### P1-2 · 首请求超时与 prewarm 兜底对齐实测握手时长（对应 N4）

- **做法**：`TTS_HTTP_FIRST_MS` 3000 → **5000**（覆盖 3.5–4.3 s 实测握手上限）；同时给 prewarm 的三个早退口打一行日志（`prewarm skipped: reason=`），让“没预热成”在串口可见。
- **收益**：消除“必然超时 + 150 ms + 重连”的 3.15 s 纯浪费；3000 → 5000 只在**服务端真的挂了**时才让失败变慢 2 s，而那种情况本来就要重试。
- **代价**：服务端不可用时首个错误反馈慢 2 s（可接受：卡片/回复本来就有 8 s 兜底）。
- **验证**：串口抓一次“断网→恢复”的回合，确认不再出现 `TTS request failed … budget 5000` 紧接 `retrying once`；对照 `prewarm:` 行确认握手落在预算内。

### P1-3 · prewarm 栈抬到 12288 并打印高水位（对应 N5）

- **做法**：`TTS_PREWARM_STACK 8192 → 12288`（与 `TTS_TASK_STACK` 持平，PSRAM 栈代价可忽略），成功后打 `uxTaskGetStackHighWaterMark`。
- **收益**：消除“同类握手任务里唯一拿 8 KB”的不一致与 panic 风险；高水位数据让下次再不是猜。
- **代价**：PSRAM 多占 4 KB（本板 PSRAM 富余，`WC_PLAY_STACK` 已是 24576）。
- **验证**：连续 10 次冷 prewarm 看高水位余量 ≥2 KB；跑 host 全量确认无新增失败。
