# TTS 流式重做 · 1.5.3a C 流（C1–C4）

分支 `feat/1.5.3a`，基点 A 流头 `7777839`。四笔本地提交：C1 `f83b55d`、C2 `7b149e3`、C3 `d2596e2`、C4 `b24e41e`。未推、未合 main。

## 背景

1.5.2c 已有 keep-alive 连接复用（`turn_start()` 调 `muse_tts_prewarm()`，握手藏进等模型出字的 4–7 秒），实测回复首字节 2040/506/481ms（第 1/2/3 句，首句是 Azure 合成本身）。剩下两个问题：

1. `done` 分支仍整段一口说：尾巴整条当一个 unit 发，句间停顿丢了；
2. 尾巴 burst：上游按 4096 字节块往桥的队列里灌，LLM 一停顿就攒一串，桥再整串推给板子，板子 16 KB ring 满了，`ring_send` 堵满 3 秒就 abort，丢句。

用户已定：走 C2+C3，`stream=1` 不做；不做 Opus 迁移、WebSocket/SSE（relay 协议由 Muse 服务端定）。

## C1：桥侧首句在第一个逗号处切断抢首音（`f83b55d`）

- 只改桥 + 固件 3 行：固件 `fetch_reply()` 给回复的第一个 chunk 请求加 `&first=1`；桥 `split_first_sentence()` 在首个 `，`/`,` 处切，head ≥ 2 字符且 tail 非空才切（head 太短就找下一个逗号），两个 segment 先后进同一个流式响应，响应头加 `X-TTS-First-Cut: 1`。
- 缓存存拼接后音频、键仍是全文；缓存命中不切；`stream=0` 忽略 first。
- 后面的句子保留逗号停顿（切断会丢停顿，只切首句）。
- 验证（无 Azure key，本地桩）：`tts-server/test_tts_stream.py`，Azure 桩的首读延迟随文本长度增长——切分首字节 < 0.5s、整句 > 0.5s，正文仍是 head+tail 音频；4/4 通过。

## C2：尾巴走正常句路 + 末段标记 + 排空再结束（`7b149e3`）

- `muse_sentence_next_unit_final(p, len)`：下一句，或无边界时整段余下文本（`len` 非零时永不返回 0）。`start_tts_streaming` 在 `m.done` 时用它，未完成的消息仍等边界。
- `last` 参数：`muse_tts_speak(text, last)` / `muse_tts_enqueue(text, last)`；`hand_sentence` 接 `last`（`m.done && (m.spoken + unit >= buffered)`）；非流式 `start_tts` 传 true（整条消息就是自己的 last unit）。
- 桥回显：最后 unit 的最后 chunk 请求带 `&last=1`，桥在流式、缓冲式、缓存命中三路响应上都回 `X-TTS-Last: 1`；固件 `fetch_once` 读到才置 `s_last_chunk`（访问器 `muse_tts_last_chunk()`），speak/cancel 时重置。
- `decode()` 流式分支：kbps==0 静默回落分支原样不动；随后等 `xStreamBufferIsEmpty(s_out)`，`drain_us` 在 `hand_sentence` 首句分支与 `s_out` 非空时重置；余量 120ms（`TTS_DRAIN_MARGIN_US`，标记已到时），无标记时 2 秒宽限（`TTS_DRAIN_GRACE_US`）——缺标记绝不能挂住 turn（旧桥兼容）。非流式 decode 分支不动。
- 验证：句子 harness 加 final 模式（3 个新测试，15/15）；桥测试 5/5（marker 三路回显）。

## C3：桥侧 pacing，按 MP3 帧实时发送（`d2596e2`）

- `_Mp3Frames`：把字节流切成 MP3 帧，帧长与时长取自每帧自己的帧头（MPEG-1 L3：144×码率/采样率、1152 采样；MPEG-2/2.5：72×、576 采样）。**实测纠正了计划的数**：真实回复是 MPEG-2 L3、24kHz/48k，**每帧 24ms**（576 采样 @24kHz），不是计划写的 72ms（那是 16kHz 的数）；帧长 144/192 字节不等（VBR 混码率）。丢同步时往前扫恢复；尾部不完整帧只在流结束时原样放行。
- `_FramePacer`：前 2 帧直发（首音不延迟），之后一帧一间隔；上游停顿后 backlog 一齐到时重锚时钟、不 burst。
- ID3 标签在任何一个帧边界都合法（分段回复的每个 segment 开头都有一个），按 dur=0 直发不 pacing；pacing 流与缓存的字节数完全一致（C3 测试抓到过一次分段 ID3 被当垃圾丢掉、导致 pacing 体比缓存短 45 字节，已修）。
- 回滚：`TTS_PACING=0` 恢复旧 burst 行为（已进 `deploy.py` 的 env 清单与 `/health` 的 `pacing` 字段）。
- 验证（无 Azure key，本地桩，burst 进）：tag + 153 帧 @24ms，整段约 3.7 秒出完（burst 不到 0.5 秒），读间隔中位数 > 30ms，首字节 < 0.7s，正文与原文件逐字节相同；pacing 关掉又是 burst。桥测试共 11/11 通过（含 C1/C2 的 5 个）。

## C4：世代守卫（`b24e41e`）

- `muse_tts_new_turn()`（只 bump `s_gen`），`turn_start()` 开头调用：新回合开始即宣告旧回合的音频作废，fetch 各路按 generation 丢字节。speak()/cancel() 本来已按消息/打断 bump，回合边界是唯一没 bump 的地方。
- 末段标记只认当前世代的 fetch：新回合开始后才收完的旧 fetch 不能给新回合打标记。
- 另给 chat-session host harness 补了 `muse_tts_prewarm()` 与 `muse_tts_new_turn()` 两个桩（它抽 `turn_start` 切片、但不链接 `muse_tts.c`）。注意该 harness 还有更老的缺口（`types` 切片拖进了需 `conn_t` 与 Hatch session API 的函数，`silent_frames` 在 `-Werror` 下未使用），即使有 cJSON 也编不过，修通是另一个任务，不在 C4 内。

## 未验证、须真机 + 已部署的桥复测（不要当成已完成）

- **首句三组数**对照 1.5.2c 基线 2040/506/481ms：本机无 Azure key、无真机，桩测试只证明了机制（切分确实让首字节更早、pacing 确实按 24ms 出帧），没证明真机上的毫秒数。
- `decode()` 的排空+余量块：host 上没有音频任务，编不进测试，只能真机听尾巴是否完整、回合是否按时结束（尤其注意无标记的旧桥：2 秒宽限会不会让回合结束拖 2 秒）。
- C1 首切在真机上的体感：首句在逗号处断开，听感上首音早到了，但逗号停顿没了——只影响首句。
- 回滚：桥 `.env` 加 `TTS_PACING=0` 即回 burst（C1/C2/C3 都是桥侧开关可控，固件侧 C2 的 drain 等待在无标记时 2 秒宽限，不会挂住）。
- `s_task` 首次 speak 后即直接返回的问题（45 秒闲置丢连接那条路实际是死代码）仍在，不在本次范围。
