# 1.5 互动预览版设计方案

> 基线：`blacksamuraiiii/muse-esp32-s3-touch-lcd-1.85b`，HEAD `7f6db73`（notes 公开目录入库），
> `esp32/version.txt` 为 `1.4d`，上一版为 `54b58ed` 的 1.4d 测试版。
> 状态：设计方案，未实现；凡标注“待核实 / 待验证”的结论，实现时以代码与实测为准，不要照抄。
> 本目录随仓库公开：本文不含内网地址、口令、密钥、SSID。

## 0. 一句话

1.5 预览版只做一件事：把 TamaMe（`asos520-rgb/tamame-esp32`，1.75C 桌面宠物）的
**玩法模型**搬到 1.85B 上，形象继续用毛毛 v2，不上宠物 UI、启动器、换装 UI、Fish TTS。
玩法只有三项：**摸摸、喂食（只喂米饭）、今日占卜**。

“1.5 预览版”在版本号上的含义见 §7：它是 **1.5a + Test 构建**，不是 Release 1.5。

## 1. 目标与非目标

### 目标

- 待机脸点按 = 摸摸，能赚金币（每日上限内），毛毛有开心反馈。
- 设置页新增“宠物”子页，3 个操作：摸摸、喂米饭、今日占卜，外加金币 / 饱腹度 / 心情 / 今日次数的状态显示。
- 状态断电不丢：重启后金币、饥饿、心情、占卜日都在；隔夜按模型衰减；时钟回拨不补发金币。
- 对话主线、闹钟、顶栏、待机功耗无回归；1.4 定过的红线不动（见 §1.2）。

### 非目标（1.5a 明确不做，写进待办别顺手扩）

- 换装、场景、启动器展开动画、食物选择菜单、6 种食物全量 UI、三语界面。
- Fish Audio TTS、TamaMe 默认角色、TamaMe 的 1.75C 板级文件与 466×466 坐标布局。
- TamaMe 的聊天日志脱敏补丁（`muse_chat_session.cpp` 等）：与 1.4 代码容易冲突，不碰。
- IMU 手势（抬腕 / 敲击 / 翻面）复活、触摸唤醒加回：1.4 已取消 / 已删，不为宠物改回来。
- 宠物状态上云、跨设备同步、后台记忆 / 定位 / 班表自适应：TamaMe 自己也未定义为可验收功能，不宣称。

### 1.4 红线（复述，不改）

- 唤醒源只剩 BOOT（GPIO0）；IMU 的 GPIO8 与触摸的 GPIO4 唤醒线已撤。
- 息屏时 CST816S 走 auto-sleep，触摸芯片不常驻动态扫描；宠物 worker 不得为“随时可摸”而阻止浅睡。
- 发版后一周观察期只修真 bug 的口径适用于 1.4 线；1.5a 是另一条实验线，不混进 1.4 的 OTA / Release 说明。

## 2. 现状锚点（2026-10-25 实查 1.4d 代码，设计就建在这上面，不要重造）

以下每条都已在仓库代码里确认，文件路径为仓库内路径：

1. **脸与设置是两块 tile**：`esp32/components/muse/muse_ui.c` 的 `muse_ui_start()` 建
   tileview，脸在 (0,0)、设置在 (1,0)；`muse_settings_ui_build(s_settings)` 建设置页。
   脸是否可见有现成接口 `muse_ui_face_active()`（`muse_ui.h`）。
2. **摸脸已有开心通道，不用新造**：`muse_ui.c` 的 `on_canvas_clicked()`（脸画布点按）
   调 `muse_state_make_happy()`；`muse_state.c` 里 `HAPPY_SECS` 为 1.6 秒，
   `muse_state_happiness()` 在 1.6 秒内返回 1、最后 0.4 秒缓出；
   `muse_ui.c` 的 tick 里 `pose.happy = muse_state_happiness()`，再调
   `muse_pixel_render(&pose)`。毛毛渲染器（`components/muse/avatar/muse_pixel.c`，
   gitignored，构建时由 `CMakeLists.txt` 的 GLOB 捡起）已按 `happy` 画大笑嘴与飘爱心。
   结论：1.5a **不改 avatar 文件、不新增 happy 接口**，只复用这一条。
3. **设置页已有子页范式，照抄 ALARM 页**：`muse_settings_ui.c` 里
   `page_t { obj, build }`，子页在打开时建、返回时删（注释原话：只有 home 常驻，
   子页同时存在约 50 KB）；`build_home()` 用 `row()` 加行、`on_nav` 打开子页；
   `muse_settings_ui_tick()` 按 `s_current` 分发各页的 tick，`tick_alarm()` 会先判
   widget 为 NULL 再写。宠物页按同一范式：`build_pet_page` / `tick_pet` /
   `page_t PET` / home 加一行 / tick 分发加一支。
   待核实点：`drop()` 的删除列表里没有 `s_alarm`，实现前先核实这是刻意保留还是遗漏；
   宠物页按核实结论处理，若是遗漏则宠物页进 `drop()` 列表，并在进展记录里记一笔，
   **不顺手改 ALARM 页**（范围外）。
4. **设置枚举与存储是两回事**：`muse_settings.h` 的 `muse_setting_t` 到 ALARM 为止，
   没有宠物项；`muse_settings.c` 用 NVS namespace `"muse"`，setter 立即落盘并通知 listener，
   闹钟由 input task 拥有（`muse_input_alarm_sync()`）。宠物状态**不塞进这个枚举**，
   也不走这个 listener，单独一个 NVS namespace（见 §4.4），避免把宠物经济与系统设置耦合。
5. **启动顺序已定，宠物 worker 的插入点就卡在这里**：`muse_app.c` 的 `muse_app_run()`：
   板级 init → `muse_settings_init()`（内含 `nvs_flash_init()`，布局变化时会擦 NVS，
   见 §4.4）→ `muse_state_init()` → `muse_battery_init()` → `muse_time_start()`
   （RTC adopt，SNTP 等 Wi-Fi）→ Test 下 `muse_telemetry_start()` →
   `muse_ui_start()` → input 队列 → `muse_voice_start()` → mode 置 IDLE。
   宠物 worker 在 `muse_time_start()` 之后、`muse_voice_start()` 之前启动：
   时间已 adopt、NVS 已初始化、UI 与语音尚未开始，不依赖任何一方的完成。
6. **字幕是全局共享资源**：`muse_state.h` 的 `MUSE_CAPTION_MAX` 为 400，
   字幕带版本号，UI tick 按版本刷新；`muse_ui.c` 里扬声器处理有现成范式——
   只有 mode 为 IDLE 时才写提示字幕，不覆盖对话的字幕。宠物反馈的字幕遵守同一条
   （见 §5.3）。
7. **板子事实**：`boards/board_waveshare_s3_touch_lcd_185b.c` 的 `s_board`：
   360×360 圆屏（`LCD_H_RES` / `LCD_V_RES`）、`round = true`、`touch = true`、
   单键（`talk_button = "boot"`，`aux_button = NULL`）、`wake_lines_reliable = true`。
   设置页在圆屏且高度 < 466 时 `s_text_scale` 取板高（360），宠物页的文字与行高
   走这套现成缩放，不要为宠物页另写 466 坐标。
8. **构建分型是硬校验，不是约定**：`esp32/components/muse/muse_build.h` 与
   `esp32/cmake/validate_config.cmake` 会在编译期拒绝“构建类型与测试设施 / 分区表 /
   版本后缀不一致”的组合。宠物核心代码本身不分 Test / Release（见 §3.3），
   只有调试命令按此分型处理。

## 3. 架构与文件清单

### 3.1 数据流

```text
待机脸点按 ──► muse_pet_request(PET_TOUCH) ──┐
设置宠物页按钮 ──► muse_pet_request(...) ────┤
                                              ▼
                                   pet worker（独立 FreeRTOS 任务）
                                   串行结算 → NVS 落盘 → feedback 队列
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    ▼                                                   ▼
        LVGL task 的 tick_pet / muse_ui tick                   muse_state_make_happy()
        读 snapshot + feedback，刷新宠物页 / 写字幕              （仅成功反馈时，见 §5.3）
```

铁律：UI 线程只发动作、只读快照与反馈，**不直接改状态结构体**；
worker 是唯一写状态的地方；快照复制加锁，照 TamaMe 的 worker 模式，不共享裸指针。

### 3.2 新增与改动文件

| 文件 | 动作 | 说明 |
|---|---|---|
| `esp32/components/muse/muse_pet_model.h` / `muse_pet_model.c` | 新增，改编自 TamaMe | 模型本体；去掉 `muse_i18n.h` 依赖（见 §4.5），保留 Apache-2.0 文件头与 TamaMe 署名 |
| `esp32/components/muse/muse_pet.h` / `muse_pet.c` | 新增，改编自 TamaMe | worker：队列 + NVS + 衰减 + 反馈；删自起 SNTP（见 §6.1） |

不新增 Kconfig 选项：1.5a 不需要宠物开关。想要关宠物，1.5a 的办法是刷回 1.4d，
不是再加一个设置项（多一个 NVS 键、多一个 listener 分支，预览版不值）。

### 3.3 构建类型与宠物代码的关系

- 宠物模型 + worker + 宠物页：**不包在 `CONFIG_MUSE_BUILD_TEST` 里**，这样 1.5a 的代码
  不经改动就能进 Release 1.5；预览版与正式版的差别只在构建类型、分区表与版本号（§7），
  不在宠物代码本身。
- 调试命令分两档：只读的 `pet.status` 常驻；破坏性的 `pet.reset`（清 NVS）包在
  Test 内（`muse_build.h` 的惯例：测试设施在 Release 下编译期硬拒，宠物核心不算测试设施，
  但清数据命令算）。1.5a 本身就是 Test 构建，两档都可用；进 Release 前 `pet.reset` 必须
  已被编译期排除，靠构建验证，不是靠人工记得关。

## 4. 数据模型（照抄 TamaMe 的数值，不重发明；改动点只列在 §4.5）

### 4.1 状态字段（TamaMe `muse_pet_model_t`，单位：千分点，100000 = 100）

- `coins`：金币。初始 0（`memset` 后未赋值即 0），上限 1000000（防溢出，实际到不了）。
- `hunger` / `mood` / `energy`：初始 70000 / 75000 / 75000，即 70 / 75 / 75。
- `daily_pets`：当日摸摸次数；`reward_day`：金币结算日，初始 -1。
- `fortune_day` / `fortune`：占卜日与当日占卜序号，初始 -1 / 未抽。
- `last_time` / `reserved`：上次结算时间与未校准时钟下攒下的秒数（见 §6.1）。
- `sfx`：TamaMe 的音效开关字段。1.5a 不做宠物音效开关，字段保留在结构体里
  （保持与 TamaMe 的布局可比对），UI 不暴露，恒为 1。

### 4.2 衰减

- 每 36 秒一个量子，不足 36 秒不扣：频繁点按不能把衰减“刷停”。
- 每小时：饥饿 -2（2000 千分点）、心情 -1、能量 -1.5；封顶按 30 天结算，超过按 30 天算。
- 时钟回拨不补发任何东西；`last_time` 为 0（从未结算）时先记时间、不扣。

### 4.3 动作与结果（模型层保留 TamaMe 全表，UI 层只暴露三项）

| 动作 | 效果 | 结果码（UI 文案按结果码写，不要按猜测写） |
|---|---|---|
| 摸摸 `PET_TOUCH` | 心情 +3；当天前 30 次每次 +1 金币 | `PET_COIN`（加币）、`PET_CAP`（第 31 次起：只加心情，不加币）、`PET_TIME`（时钟异常日，见模型代码注释） |
| 喂米饭（模型里的 `PET_RICE`） | 成本 7 金币，饱腹 +40，心情 +8 | `PET_OK`、`PET_FULL`（饥饿 ≥100，不扣币）、`PET_POOR`（金币不够，不扣币、不加饱腹） |
| 今日占卜 `PET_FORTUNE` | 每天一次，`esp_random() % 20` | `PET_FORTUNE_NEW`（新卡）、`PET_FORTUNE_SAME`（当日已抽，显示同一张） |
| 对话完成 `PET_CONVERSATION` | 能量 +10 | `PET_OK`；是否接线见 §4.6 的决策 |

TamaMe 原食物表（模型层保留，UI 层 1.5a 只暴露米饭）：
咖啡 3/15、茶 4/20、蛋糕 5/25、鸡肉 6/35、米饭 7/40、火锅 10/60
（成本 / 饱腹度；任意一种喂食心情 +8）。
新用户第一天流程因此是：先摸摸赚币（最多 30 币）→ 再喂米饭；宠物页要把这句
话写进 note，不要让用户对着“金币不够”发懵。

### 4.4 存储

- NVS namespace 沿用 TamaMe 的 `pet_pub_stats`，key 为 `"state"` 的 blob，一次写整个
  结构体。沿用这个名字不是图省事：模型文件与 TamaMe 的 diff 最小，出问题能逐行比对。
- 奖励与消费**先落盘再公布成功**；纯衰减存盘最多 30 分钟一次（TamaMe worker 为
  30 秒一轮、60 轮一存）；不要每帧、每次 tick 写 NVS。
- 校验沿用 TamaMe 的 `muse_pet_model_valid` 思路：版本号、各项 0~100000、
  金币与当日次数上限、占卜序号 <20。**损坏的 blob 不静默重置**：worker 记错、
  奖励停用、宠物页显示“宠物数据损坏”，靠 Test 调试命令清数据后重建。
  宁可预览版停用宠物，也别悄悄清零重发币——静默重置会把“币被吞了”与“币被重置了”
  两种故障混成一种现象，无法复现。
- 注意 `muse_settings_init()` 里 `nvs_flash_init()` 在 `NO_FREE_PAGES` /
  `NEW_VERSION_FOUND` 时会擦整片 NVS：宠物数据与系统设置同在 NVS 分区里，
  这是既有行为，1.5a 不改；但进展记录里要写明“宠物数据不抗 NVS 布局变化”，
  不要在 Release 说明里承诺宠物数据永不丢。

### 4.5 相对 TamaMe 必须改的三处（也是 1.5a 改编工作的全部）

1. **去掉 `muse_i18n.h` 依赖**：TamaMe 模型用 `MUSE_KEY_s200` 一套词条查占卜卡与等级、
   用词条查食物名；本仓库没有 `muse_i18n`（那是 TamaMe overlay 的东西，不是上游 SDK）。
   改法：占卜卡、等级词、食物名全部换成 §4.5 外的静态中文表（新文件或并入模型文件），
   模型函数签名不变，只换文案来源。
2. **删 worker 自起 SNTP**：TamaMe `muse_pet.c` 里 `clock_start()` 自己起 SNTP；
   本仓库 `muse_time_start()` 已做 RTC adopt + SNTP 等 Wi-Fi（§2.5）。宠物 worker
   直接用 `time()`，不另起对时（见 §6.1）。
3. **删 1.75C 门控与 466 坐标**：TamaMe 的 `muse_pet_ui.h` / `muse_style_ui.h` /
   `muse_launcher.c` 全被 `#if CONFIG_MUSE_BOARD_WAVESHARE_S3_175C` 门控且写死
   466×466；1.5a 不移植这些文件，宠物页走 §2.3 的设置页范式，文字缩放走
   `s_text_scale`（圆屏 360），不要从 TamaMe 抄任何坐标。

### 4.6 能量字段的决策（1.5a 的唯一待定项，先给默认解）

能量只在模型里衰减、只在对话完成时恢复（+10）。1.5a 有两个可接受的解，
实现时二选一、写进进展记录，不要两个都做：

- **默认解 A（推荐）**：接对话完成回调，只加一行 `muse_pet_request(PET_CONVERSATION)`，
  不改对话逻辑、不给金币、不显示能量以外的任何东西；宠物页显示能量数值。
  前提是能找到干净的对话完成回调（语音 / 会话完成处），找不到就 fallback 到 B。
- **解 B**：1.5a 不接对话回调，宠物页**不显示能量**（字段仍在模型里衰减，
  供以后接线），避免给用户一个“只会掉、永远回不来”的数字。
  哪个解落地、回调在哪个文件哪一行，进展记录里必须写清楚，不许写“已接对话奖励”
  却无落点。

## 5. 入口与反馈

### 5.1 入口一：待机脸点按 = 摸摸（已有通道的最小改动）

- 现状：`on_canvas_clicked()` 无条件 `make_happy()`。
- 1.5a 改法：仅当 mode 为 IDLE 且 `muse_ui_face_active()` 为真时，再发
  `muse_pet_request(PET_TOUCH)`；非 IDLE（聆听 / 思考 / 说话 / 错误 / 关机）时
  不发宠物动作——点按反馈仍走现有行为，不为宠物改对话态的点按语义。
- 双通道说明（不要“优化”掉）：脸点按保持**同步** `make_happy()`（1.6 秒开心，
  手感不变），金币结果走**异步** feedback 队列（见 §5.3）。于是“第 31 次摸摸”
  也会开心、但字幕会诚实地写“今日已满 30/30”，开心是表情、金币是结算，
  两者不互相冒充。

### 5.2 入口二：设置页“宠物”子页（1.5a 的主入口）

- home 行：标题“宠物”，图标先传 NULL（`row()` 允许 NULL，ALARM 页的 Hour / Minute /
  Days 行就是这么写的）；不要为这一行去猜一个 LVGL symbol 名，查到确切存在的
  symbol 再换。
- 子页内容（全部用设置页现成构件 `button` / `info_row` / `note`，不新画 LVGL 页）：
  - 按钮：摸摸 / 喂米饭 / 今日占卜。回调只发动作，不结算、不直接改显示。
  - 状态行（`tick_pet` 刷新，widget 为 NULL 时先返回，照 `tick_alarm()` 的写法）：
    金币、今日摸摸 x/30、饱腹度（0~100 整数，千分点 /1000）、心情（同）、
    今日占卜（未抽 / 第 N 张卡名）。
  - note 行：结果反馈（见 §5.3）与新手提示（先摸摸赚币再喂米饭）。
- 子页生命周期照 §2.3 的 ALARM 范式，并先落实 §2.3 的 `drop()` 待核实点。
- 子页打开时不改 tile swipe 语义：`show()` 里 `muse_ui_set_swipe_enabled(p == s_home)`，
  子页本来就关 swipe，宠物页不例外；返回 home 靠现有 `go_back()` / 右滑，不要另加返回按钮逻辑。

### 5.3 反馈：字幕 + 开心，都有过期与守门

- LVGL task 里消费 feedback 队列（不要在 worker 里直接调 UI 函数）：
  成功（`PET_COIN` / `PET_OK` / `PET_FORTUNE_NEW`）→ `muse_state_make_happy()`；
  所有结果 → 写结果文案。
- 字幕文案按结果码一一对应，示例（实现时以结果码为准，数字取快照）：
  - 摸摸加币：`毛毛很开心 +1 金币（今日 3/30）`
  - 摸摸满额：`今日摸摸已满 30/30`
  - 喂米饭成功：`喂了米饭 -7 金币，饱腹度 +40`
  - 喂米饭失败：`已经吃饱了` / `金币不够（还差 X）`
  - 占卜新卡：`今日运势：<卡名> · <等级>`（卡名与等级取静态表）
  - 占卜重复：`今日已抽过：<卡名> · <等级>`
  - worker 未就绪 / 存储错误：`宠物未就绪` / `宠物数据损坏`（不编造数字）
- 字幕守门（照 §2.6 的扬声器范式）：
  - 只在 mode 为 IDLE 时写宠物字幕；对话进行中不写、不覆盖回复字幕。
  - 宠物字幕带过期时间（建议 3 秒，脸点按的开心是 1.6 秒，两者不绑定）：
    LVGL tick 里到期且 mode 仍为 IDLE 且字幕仍是宠物那条时，清为空串；
    期间 mode 变了（开始对话），不要清掉对话的字幕——过期清理必须先确认
    “当前字幕还是宠物字幕”，不能无条件 `set_caption("")`。
  - 宠物页内的结果 note 不受 3 秒过期限制，离开子页即随子页删除而消失。
- 音效：1.5a 不新增宠物音效。TamaMe 的本地互动音效（`muse_pet_sfx`）不移植；
  已有对话 / 提示音不动。想要“摸摸有声音”放到 1.5b 讨论，不要在 1.5a 里顺手加。

### 5.4 串口调试（不走 UI 的第二条验证路）

见 §8.3。调试命令只用于验证模型，不作为用户功能写进设置页与 Release 说明。

## 6. 时间、线程、功耗

### 6.1 时间

- 宠物 worker 直接用 `time()`；`muse_time_start()` 在 worker 启动前已跑
  （§2.5），RTC adopt 在先。
- 未校准时钟沿用 TamaMe 的 `reserved` 机制：时钟未校准时按单调计时攒秒数，
  校准后再结算衰减；时钟回拨不补发。
- **待核实（实现前必须查，不许照抄）**：TamaMe 的占卜日按
  `(now + 8*3600) / 86400` 算，隐含 `now` 为 UTC；本仓库 `muse_time_start()` /
  SNTP 配置后的 `time()` 究竟是 UTC 还是本地时区，查 `muse_rtc.c` 与 SNTP
  配置后再定公式。若本仓库时钟已是本地时区，+8 就是错 8 小时的 bug，
  占卜会在错误的时间点跨日。公式以核实结论为准，进展记录里写明查到的
  时钟语义与最终公式。

### 6.2 线程与栈

- worker 任务：照 TamaMe 的形态——独立任务、命令队列（8 项）、反馈队列（8 项）、
  30 秒一轮（队列超时即做一次衰减结算）。优先级与栈大小以 TamaMe 为起点
  （任务优先级 2、栈 4096），实现时按本仓库的任务优先级分布复核一遍，
  不要高于 input / voice 任务。
- 栈位置：TamaMe 注释原话——NVS 提交会关 cache，PSRAM 栈不安全。worker 栈
  必须落在内部 RAM（`xTaskCreate` 默认即内部 RAM，不要为省内部 RAM 而改成
  PSRAM 栈）；实现时在代码注释里写明这一条，不要只留在设计稿里。
- 队列满时 `muse_pet_request()` 返回失败（不阻塞 UI）：UI 侧把“宠物未就绪”
  写进结果 note，不要在 LVGL 回调里等 worker。

### 6.3 功耗与待机

- worker 30 秒一轮、衰减存盘 30 分钟一次，是 1.5a 的功耗上限口径：
  实现后要在电池下测一夜掉电，与 1.4d 同条件对比（见 §8.2），不要只测 USB 下。
- 宠物页、脸点按、字幕过期清理都不持有 power lock、不阻止浅睡；
  `make_happy()` 本身调 `muse_state_poke()`（保持唤醒），这是既有行为，
  宠物动作因此会推迟一次自动息屏——属于“交互了所以不睡”，不是待机回归，
  验收时按“交互后息屏计时重置”算，不要按“宠物导致不睡”算。
- Test 构建的遥测采样（FAT 写 CSV）仍在，宠物数据不写 FAT、不进遥测 CSV，
  两条写路径分开，夜测数据才可比。

## 7. 版本与发布（1.5a 的身份）

- `esp32/version.txt`：`1.4d` → `1.5a`。这是 1.4a / 1.4b / 1.4c / 1.4d 一脉的
  字母后缀即测试版约定（`esp32/cmake/project.cmake`：以字母结尾的版本即测试版，
  不再追加 `-test`；`validate_config.cmake`：Test 构建的版本必须以字母或 `-test` 结尾，
  Release 构建的版本不得以字母结尾、不得带 `-test`）。
  不要发明 `1.5-preview` / `1.5_preview` 这类新后缀：它不在仓库的版本约定里，
  OTA 与 Release 脚本对它的处理是未验证的。对外称呼写“1.5 预览版”，
  版本号写 `1.5a`，两者在 Release 说明里各归各的位置，不要混成一个字符串。
- 构建命令：照 `sdkconfig.muse-test` 注释的 Test 形态走
  `tools/muse/board.sh` 的 Test 构建链（`MUSE_BUILD=test … build lcd185b`），
  分区表用 Test 表（`partitions_muse_test.csv`，含 FAT 遥测分区）。
- 发布形态：**USB 刷入，不走 OTA 推广**。Test 表与 Release 表的分区不同，
  Test 镜像按 1.4d 的做法走 USB；`ota/latest.json` 不指向 1.5a，
  直到 1.5 正式版（Release 构建、数字版本号）再按发版流程换。
  GitHub Release 上 1.5a 标为 pre-release（与 1.4 撤回为 pre-release、1.4d 为
  测试版的做法一致），说明里写清：预览版、USB 刷入、回退办法（见 §8.2）。
- 回退：刷 1.5a 前先有 1.4d 下的整颗 Flash 备份（TamaMe 文档与本仓库 1.4 流程
  的同一要求）；宠物 NVS 与系统设置分 namespace，但同在 NVS 分区里，
  刷回 1.4d 不会自动清宠物数据——回退说明里写明这一点，不要承诺“刷回即干净”。

## 8. 验收

### 8.1 功能验收（逐项打勾，数字以实测为准）

1. 编译通过：Test 构建链、`check_sizes` 通过（1.85B 每 app 槽 4MB；
   模型 + 20 句文案体积很小，先以实编译为准，不要凭感觉说“肯定够”）。
2. 宠物页能打开、能返回 home，返回后子页不残留、不野指针（§2.3 的 `drop()` 核实点闭环）。
3. 重启后金币 / 饥饿 / 心情 / 占卜日都在，不是每次开机归零。
4. 摸摸：30 次内每次 +1 币，第 31 次不加币；跨自然日（按 §6.1 核实后的日切分）
   后计数清零；脸点按与宠物页按钮两种入口计数同一套，不各算各的。
5. 喂米饭：金币 -7、饱腹 +40（封顶 100）、心情 +8；饱了不扣币；币不够不扣币、不加饱腹。
6. 占卜：同一天两次是同一张卡；次日能抽新卡；20 张都能显示，在 360 圆屏上
   不溢出、不截断关键等级词（长句先在模拟器 / 实机上逐张过一遍）。
7. 隔夜衰减：放一夜后饥饿 / 心情 / 能量按每小时 -2 / -1 / -1.5 的量级下降，
   不是归零也不是不动（允许 36 秒量子取整的误差）。
8. 时钟回拨不补发金币；NVS blob 损坏时宠物停用、显示损坏提示、不静默重置。
9. 对话主线无回归：按住 BOOT 录音、字幕、TTS 播放、闹钟、顶栏时钟 / 电量都正常；
   宠物反馈不打断聆听 / 思考 / 说话态。
10. 宠物页打开时不影响对话：从宠物页返回脸、再按 BOOT 对话，流程正常；
    宠物页内点按不触发录音、不触发关机（`on_aux_clicked` 的关机入口不受影响）。

### 8.2 待机与回退验收

1. 电池下放一夜，掉电与 1.4d 同条件对比，写进进展记录（不要只测 USB 下；
   USB 在位会变 USB 供电，数据作废——这是测试版遥测的铁律）。
2. 刷 1.5a 前有整颗 Flash 备份；刷回 1.4d 后对话、闹钟、配对、Wi-Fi 正常；
   回退后宠物数据残留与否按 §7 如实记录。

### 8.3 调试命令（串口，`muse_input.c` 的 `console_command()` 模式）

- `>pet.status`（只读，常驻）：打印金币、饥饿、心情、能量、今日摸摸、占卜日与序号、
  worker 就绪态。格式照现有 `@power.saved` / `@status` 的一行 JSON / 键值风格，
  不要另发明一套输出格式。
- `>pet.touch` / `>pet.feed` / `>pet.fortune`（只读验证用，走同一请求队列）：
  不走 UI 的情况下验模型，输出结果码与快照。
- `>pet.reset`（破坏性，Test 内）：清宠物 NVS blob、重建初始状态。
  进 Release 前必须已被编译期排除（§3.3），不要靠“记得关”保证。
- 以上命令名在实现时以 `console_command()` 的既有命令风格复核一遍
  （`>` 前缀、整行匹配），不要与 `face=` / `chat=` / `power` 等既有命令重名。

## 9. 风险与待核实（实现前 / 实现中必须闭环，不许带进 Release 说明）

1. **时钟语义**（§6.1）：`time()` 是 UTC 还是本地时区，决定占卜日公式。未核实前
   占卜跨日行为一律写“待验证”。
2. **宠物页指针生命周期**（§2.3）：`drop()` 未列 `s_alarm` 是刻意还是遗漏。
3. **对话完成回调**（§4.6）：能量恢复接不接、回调落点在哪一行；找不到干净回调
   就走解 B，不要为能量硬插对话流程。
4. **字幕过期清理的竞态**（§5.3）：宠物字幕与对话字幕交替时，清理逻辑必须先确认
   当前字幕仍是宠物字幕；实现后要实测“宠物字幕未过期时开始对话”这一条。
5. **脸点按的事件归属**：`on_canvas_clicked` 在脸 tile 上；确认扬声器 / 电源图标
   的点按不经过它（现有 `muse_ui_face_control_at()` 是给板级 talk 判定用的，
   与 canvas 点击不是同一条路），不要把“点扬声器也算摸摸”当成特性写进去。
6. **app 体积与 RAM**：模型 + worker + 宠物页 + 20 句文案以实编译为准；
   子页 RAM 按 §2.3 的“子页同时存在约 50 KB”口径复核，不要在宠物页里常驻大图。
7. **TamaMe 本身的成熟度**：它自述为 source preview，换背景曾有原因不明的失败、
   新账号配对与长期稳定性未验证。1.5a 只取其模型层，不取其 UI 层与发布结论；
   它的“已验证”不自动成为 1.5a 的“已验证”，§8 必须在 1.85B 上重测。

## 10. 实施顺序（按这个顺序做，不要先画宠物页）

1. 模型 + 文本表 + worker 落地，串口命令先行：不接 UI 也能 `>pet.status` /
   `>pet.touch` / `>pet.feed` / `>pet.fortune` 全流程跑通，NVS 重启恢复先验。
2. 脸点按接 `PET_TOUCH`（§5.1），字幕与开心反馈闭环，确认非 IDLE 不发动作。
3. 设置宠物页（§5.2），三按钮 + 状态行 + 结果 note，`drop()` 核实点闭环。
4. 时钟语义（§6.1）与占卜跨日实测，20 张卡逐张过屏。
5. 电池夜测 + 对话 / 闹钟 / 顶栏回归，写进展记录；`pet.reset` 的 Test 门控复核。
6. 版本号 `1.5a` + Test 构建 + pre-release + USB 刷入说明，`ota/latest.json` 不动。
