## 0. 一句话

1.5 预览版只做一件事：把 TamaMe（`asos520-rgb/tamame-esp32`，1.75C 桌面宠物）的
**玩法模型**搬到 1.85B 上，形象继续用毛毛 v2，不上宠物 UI、启动器、换装 UI、Fish TTS。
玩法：脸点按摸摸 + 互动页三项（喂饭、小游戏、今日运势）。

“1.5 预览版”在版本号上的含义见 §7：它是 **1.5a + Test 构建**，不是 Release 1.5。

## 1. 目标与非目标

### 目标

- 待机脸点按 = 摸摸，能赚金币（每日上限内），毛毛有开心反馈。
- 新增顶层互动 tile（见导航修订），3 个操作：喂饭、小游戏（默认石头剪刀布）、今日运势，
  外加金币（上限 100）/ 今日摸摸给币 / 今日喂饭奖励的状态显示。摸摸不在互动页里，
  只在脸页面点脸。
- 状态断电不丢：重启后金币、喂饭日、占卜日、扣生活费日都在；跨日按 §4.2 扣生活费；
  时钟回拨不补发金币、不补扣生活费。
- 对话主线、闹钟、顶栏、待机功耗无回归；1.4 定过的红线不动（见 §1.2）。

### 非目标（1.5a 明确不做，写进待办别顺手扩）

- 换装、场景、启动器展开动画、食物选择菜单、6 种食物全量 UI、三语界面。
- Fish Audio TTS、TamaMe 默认角色、TamaMe 的 1.75C 板级文件与 466×466 坐标布局。
- TamaMe 的聊天日志脱敏补丁（`muse_chat_session.cpp` 等）：与 1.4 代码容易冲突，不碰。
- IMU 手势（抬腕 / 敲击 / 翻面）复活、触摸唤醒加回：1.4 已取消 / 已删，不为宠物改回来。
- 宠物状态上云、跨设备同步、后台记忆 / 定位 / 班表自适应：TamaMe 自己也未定义为可验收功能，不宣称。

### 1.4 红线（复述，不改）

- 唤醒源只剩 BOOT（GPIO0）；IMU 的 GPIO8 与触摸的 GPIO4 唤醒线已撤。
- 息屏时 CST816S 走 auto-sleep，触摸芯片不常驻动态扫描；宠物 worker 不得为“随时可摸”而阻止浅睡。
- 发版后一周观察期只修真 bug 的口径适用于 1.4 线；1.5a 是另一条实验线，不混进 1.4 的 OTA / Release 说明。

## 2. 现状锚点（2026-10-25 实查 1.4d 代码，设计就建在这上面，不要重造）

以下每条都已在仓库代码里确认，文件路径为仓库内路径：

1. **1.4d 是两块 tile，1.5a 改成三块**：`esp32/components/muse/muse_ui.c` 的 `muse_ui_start()` 建
   tileview，1.4d 里脸在 (0,0)、设置在 (1,0)；1.5a 改为设置 (0,0)、脸 (1,0)、互动 (2,0)，
   开机默认脸。`muse_settings_ui_build(s_settings)` 仍建设置页，互动 tile 另建。
   脸是否可见有现成接口 `muse_ui_face_active()`（`muse_ui.h`），它按 tile 指针判，
   脸移到 (1,0) 后逻辑本身不用改，但所有“脸是第 0 页”的假设都要改。
2. **摸脸已有开心通道，不用新造**：`muse_ui.c` 的 `on_canvas_clicked()`（脸画布点按）
   调 `muse_state_make_happy()`；`muse_state.c` 里 `HAPPY_SECS` 为 1.6 秒，
   `muse_state_happiness()` 在 1.6 秒内返回 1、最后 0.4 秒缓出；
   `muse_ui.c` 的 tick 里 `pose.happy = muse_state_happiness()`，再调
   `muse_pixel_render(&pose)`。毛毛渲染器（`components/muse/avatar/muse_pixel.c`，
   gitignored，构建时由 `CMakeLists.txt` 的 GLOB 捡起）已按 `happy` 画大笑嘴与飘爱心。
   结论：1.5a **不改 avatar 文件、不新增 happy 接口**，只复用这一条。
3. **设置页的构件可复用，但互动 tile 不走设置子页**：`muse_settings_ui.c` 里
   的卡片 / 按钮 / info_row / note 样式（卡片底色 `0x1a1530`、圆角 18、行高 58、
   标题色 `0xa77dff`）是互动 tile 的视觉参照，构件本身是该文件的 static 函数，
   不能直接跨文件调用——互动 tile 要么在 `muse_ui.c` 里另写一套同样式构件，
   要么抽一个新文件（见 §3.2），不要为复用去动设置页的 static 边界。
   原先“照抄 ALARM 页 `page_t` / `drop()`”的方案已被导航修订取代：
   `drop()` 未列 `s_alarm` 一事不再是互动 tile 的前置项，1.5a 里不改 ALARM 页，
   只记为设置页的遗留问题。
4. **设置枚举与存储是两回事**：`muse_settings.h` 的 `muse_setting_t` 到 ALARM 为止，
   没有宠物项；`muse_settings.c` 用 NVS namespace `"muse"`，setter 立即落盘并通知 listener，
   闹钟由 input task 拥有（`muse_input_alarm_sync()`）。宠物状态**不塞进这个枚举**，
   也不走这个 listener，单独一个 NVS namespace（见 §4.4），避免把宠物经济与系统设置耦合。
5. **启动顺序已定，宠物 worker 的插入点就卡在这里**：`muse_app.c` 的 `muse_app_run()`：
   板级 init → `muse_settings_init()`（内含 `nvs_flash_init()`，布局变化时会擦 NVS，
   见 §4.4）→ `muse_state_init()` → `muse_battery_init()` → `muse_time_start()`
   （RTC adopt，SNTP 等 Wi-Fi）→ Test 下 `muse_telemetry_start()` →
   `muse_ui_start()` → input 队列 → `muse_voice_start()` → mode 置 IDLE。
   宠物 worker 在 `muse_time_start()` 之后、`muse_voice_start()` 之前启动：
   时间已 adopt、NVS 已初始化、UI 与语音尚未开始，不依赖任何一方的完成。
6. **字幕是全局共享资源**：`muse_state.h` 的 `MUSE_CAPTION_MAX` 为 400，
   字幕带版本号，UI tick 按版本刷新；`muse_ui.c` 里扬声器处理有现成范式——
   只有 mode 为 IDLE 时才写提示字幕，不覆盖对话的字幕。宠物反馈的字幕遵守同一条
   （见 §5.3）。
7. **板子事实**：`boards/board_waveshare_s3_touch_lcd_185b.c` 的 `s_board`：
   360×360 圆屏（`LCD_H_RES` / `LCD_V_RES`）、`round = true`、`touch = true`、
   单键（`talk_button = "boot"`，`aux_button = NULL`）、`wake_lines_reliable = true`。
   设置页在圆屏且高度 < 466 时 `s_text_scale` 取板高（360），互动 tile 的文字与行高
   走同一口径，不要为互动 tile 另写 466 坐标。
8. **构建分型是硬校验，不是约定**：`esp32/components/muse/muse_build.h` 与
   `esp32/cmake/validate_config.cmake` 会在编译期拒绝“构建类型与测试设施 / 分区表 /
   版本后缀不一致”的组合。宠物核心代码本身不分 Test / Release（见 §3.3），
   只有调试命令按此分型处理。

## 3. 架构与文件清单

### 3.1 数据流

```text
待机脸点按 ──► muse_pet_request(PET_TOUCH) ──┐
互动 tile 按钮 ──► muse_pet_request(...) ────┤
                                              ▼
                                   pet worker（独立 FreeRTOS 任务）
                                   串行结算 → NVS 落盘 → feedback 队列
                                              │
                    ┌─────────────────────────┴─────────────────────────┐
                    ▼                                                   ▼
        LVGL task 的互动 tile tick / muse_ui tick              muse_state_make_happy()
        读 snapshot + feedback，刷新互动 tile / 写字幕            （仅成功反馈时，见 §5.3）
```

铁律：UI 线程只发动作、只读快照与反馈，**不直接改状态结构体**；
worker 是唯一写状态的地方；快照复制加锁，照 TamaMe 的 worker 模式，不共享裸指针。

不新增 Kconfig 选项：1.5a 不需要宠物开关。想要关宠物，1.5a 的办法是刷回 1.4d，
不是再加一个设置项（多一个 NVS 键、多一个 listener 分支，预览版不值）。

### 3.3 构建类型与宠物代码的关系

- 宠物模型 + worker + 互动 tile：**不包在 `CONFIG_MUSE_BUILD_TEST` 里**，这样 1.5a 的代码
  不经改动就能进 Release 1.5；预览版与正式版的差别只在构建类型、分区表与版本号（§7），
  不在宠物代码本身。
- 调试命令分两档：只读的 `pet.status` 常驻；破坏性的 `pet.reset`（清 NVS）包在
  Test 内（`muse_build.h` 的惯例：测试设施在 Release 下编译期硬拒，宠物核心不算测试设施，
  但清数据命令算）。1.5a 本身就是 Test 构建，两档都可用；进 Release 前 `pet.reset` 必须
  已被编译期排除，靠构建验证，不是靠人工记得关。

## 4. 数据模型（金币替代定稿：只剩金币，不再有饱腹 / 心情 / 能量）

1.5a 的模型**不是** TamaMe 模型的原样照抄：TamaMe 的饥饿 / 心情 / 能量、
每小时衰减、36 秒量子、食物表在 1.5a 里全部不用（用户 2026-10-25 点选确认
“不要饱腹、全部用金币替代”）。模型文件可以仍以 TamaMe 为改编起点，
但 1.5a 的逻辑只用下面这些字段，不要把不用了的字段也写进验收与 UI。

### 4.1 状态字段（单位：金币，整数，不用千分点）

- `coins`：金币。初始 0，持有上限 100：任何进账使金币超过 100 时截断到 100，
  多余部分直接丢掉，不要溢出、不要记账到别处。
- `daily_touch_coins`：当日摸摸给币合计，上限 50；`touch_day`：摸摸结算日，初始 -1。
- `daily_feed_coins`：当日喂饭给币合计，上限 10；`feed_day`：喂饭结算日，初始 -1。
- `fortune_day` / `fortune`：占卜日与当日占卜序号，初始 -1 / 未抽。
- `decay_day`：上次扣生活费的日，初始 -1；`decay_notice`：待显示的生活费扣款额，
  显示一次后清零（见 §4.2），不要每次 tick 都重复提示。
- 不用的 TamaMe 字段（`hunger` / `mood` / `energy` / `sfx` / `reserved` / `last_time`）
  在 1.5a 里不结算、不显示、不进验收；实现时若保留在结构体里只为比对，
  必须恒定不动，不要让它们悄悄影响金币。

### 4.2 每天自动消耗（生活费，替代原来的每小时衰减）

- 跨日扣一次：日切分与占卜同一定义（见 §6.1，核实后为准）。从 `decay_day`
  到当前日，每经过一个自然日扣 10 金币，即 `coins = max(0, coins - 10 * 经过天数)`，
  扣到 0 为止，不欠账。关机 / 长时间不开机期间经过的天数也算——日历天数，
  不是运行天数；但损失上限就是钱包本身，不会扣成负数。
- 时钟未校准时不扣、不重置当日上限：日都算不出来，硬扣就是错扣。
  校准后第一次按校准日结算，只扣从上次已记录日到校准日的部分，不补扣
  “未校准期间猜出来的天数”。
- 扣款必须明说：扣款后 `decay_notice` 置为扣款总额，下一次互动（IDLE 时）
  字幕先写 `毛毛这几天花了 X 金币`（X 为实际扣款额，1 天就是 10），
  显示一次后清零。不要静默扣——静默扣在用户眼里就是“币被吞了”，
  与 NVS 损坏、截断丢币无法区分。

### 4.3 动作与结果（UI 层只暴露三项 + 脸点按摸摸）

| 动作 | 效果 | 结果码（UI 文案按结果码写，不要按猜测写） |
|---|---|---|
| 摸摸 `PET_TOUCH`（脸点按，见 §5.1） | 每次 +5 金币，当日摸摸给币上限 50（前 10 次给币，第 11 次起只开心、不给币；钱包上限 100 截断） | `PET_COIN`（加币）、`PET_CAP`（当日摸摸给币已满 50，只开心、不给币） |
| 喂饭（UI 只写“喂饭”，不写米饭） | 不花币、反给币：每次 +10 金币，当日喂饭奖励上限 10（每天第一次才给币，第 2 次起只开心、不给币；钱包上限 100 截断） | `PET_OK`（成功；给币与否看快照的当日喂饭给币，不要另发明失败码） |
| 小游戏（新增，非 TamaMe 动作，默认石头剪刀布，动画见 §5.5） | 每次消耗 5 金币，只消耗、不考虑胜平：赢、平、输都不返币、不退款；出拳前先扣币、随机结果在点按时已定，动画只是揭晓 | `PET_OK`（已扣 5，金币余额见快照）、`PET_POOR`（金币 <5，不扣、不开局） |
| 今日运势 `PET_FORTUNE` | 每天一次，`esp_random() % 20` | `PET_FORTUNE_NEW`（新卡）、`PET_FORTUNE_SAME`（当日已抽，显示同一张） |

新用户第一天流程因此是：先在脸页面摸摸赚币（前 10 次共 50 币）→ 到互动页喂饭
（第一次 +10 币）→ 花币玩小游戏（每次 5 币）；次日跨日再扣 10 生活费。
互动 tile 的 note 要把这句话写进互动 tile 的 note，不要让用户对着“金币不够”发懵。

### 4.4 存储

- NVS namespace 沿用 TamaMe 的 `pet_pub_stats`，key 为 `"state"` 的 blob，一次写整个
  结构体。沿用这个名字不是图省事：模型文件与 TamaMe 的 diff 最小，出问题能逐行比对。
- 奖励与消费**先落盘再公布成功**；跨日扣款也是一次状态变化，落盘后再发
  扣款提示；不要每帧、每次 tick 写 NVS。
- 校验沿用 TamaMe 的 `muse_pet_model_valid` 思路：版本号、金币 0~100、
  当日摸摸给币 0~50、当日喂饭给币 0~10、占卜序号 <20。**损坏的 blob 不静默重置**：worker 记错、
  奖励停用、互动 tile 显示“互动数据损坏”，靠 Test 调试命令清数据后重建。
  宁可预览版停用宠物，也别悄悄清零重发币——静默重置会把“币被吞了”与“币被重置了”
  两种故障混成一种现象，无法复现。
- 注意 `muse_settings_init()` 里 `nvs_flash_init()` 在 `NO_FREE_PAGES` /
  `NEW_VERSION_FOUND` 时会擦整片 NVS：宠物数据与系统设置同在 NVS 分区里，
  这是既有行为，1.5a 不改；但进展记录里要写明“宠物数据不抗 NVS 布局变化”，
  不要在 Release 说明里承诺宠物数据永不丢。

### 4.5 相对 TamaMe 必须改的三处（也是 1.5a 改编工作的全部）

1. **去掉 `muse_i18n.h` 依赖**：TamaMe 模型用 `MUSE_KEY_s200` 一套词条查占卜卡与等级、
   用词条查食物名；本仓库没有 `muse_i18n`（那是 TamaMe overlay 的东西，不是上游 SDK）。
   改法：占卜卡、等级词、食物名全部换成 §4.5 外的静态中文表（新文件或并入模型文件），
   模型函数签名不变，只换文案来源。
2. **删 worker 自起 SNTP**：TamaMe `muse_pet.c` 里 `clock_start()` 自己起 SNTP；
   本仓库 `muse_time_start()` 已做 RTC adopt + SNTP 等 Wi-Fi（§2.5）。宠物 worker
   直接用 `time()`，不另起对时（见 §6.1）。
3. **删 1.75C 门控与 466 坐标**：TamaMe 的 `muse_pet_ui.h` / `muse_style_ui.h` /
   `muse_launcher.c` 全被 `#if CONFIG_MUSE_BOARD_WAVESHARE_S3_175C` 门控且写死
   466×466；1.5a 不移植这些文件，互动 tile 走 §2.3 的卡片样式、文字缩放走
   圆屏 360 口径，不要从 TamaMe 抄任何坐标。
4. **金币替代（2026-10-25 定稿，取代 TamaMe 的宠物状态层）**：不要饥饿 / 心情 /
   能量、不要每小时衰减、不要 36 秒量子、不要食物表；只剩金币、三个当日上限
   （摸摸 50、喂饭 10、钱包 100）与每天 10 的生活费。TamaMe 的喂食动画语义
   （食物移向嘴、嘴张开、开心上升、满了拒绝）只借语义（见 §5.5），不照搬其 UI 布局。

### 4.6 对话奖励（已取消，不再是待定项）

能量字段随金币替代一并取消，1.5a 不接对话完成回调、不给对话金币、
不显示能量。以前 §4.6 的“解 A / 解 B”作废，不要为能量硬插对话流程。

## 5. 入口与反馈

### 5.1 入口一：待机脸点按 = 摸摸（已有通道的最小改动）

- 现状：`on_canvas_clicked()` 无条件 `make_happy()`。
- 1.5a 改法：仅当 mode 为 IDLE 且 `muse_ui_face_active()` 为真时，再发
  `muse_pet_request(PET_TOUCH)`；非 IDLE（聆听 / 思考 / 说话 / 错误 / 关机）时
  不发宠物动作——点按反馈仍走现有行为，不为宠物改对话态的点按语义。
- 双通道说明（不要“优化”掉）：脸点按保持**同步** `make_happy()`（1.6 秒开心，
  手感不变），金币结果走**异步** feedback 队列（见 §5.3）。于是“第 11 次摸摸”
  也会开心、但字幕会诚实地写“今日摸摸奖励已满 50 金币”，开心是表情、金币是结算，
  两者不互相冒充。

### 5.2 入口二：顶层互动 tile（导航修订后的主入口，不再是设置子页）

- 三块 tile（本地修订后）：互动 (0,0)、脸 (1,0)、设置 (2,0)。开机默认脸；
  从脸去左边是互动、从互动去右边回脸；从脸去右边是设置、从设置去左边回脸。
  “左滑 / 右滑”在本文里指去往方向，不指手指拖动方向（两者相反，见导航修订）。
  不要用“第 0 页就是脸”写任何判断，一律按 tile 指针 / 三值页索引判。
- 互动 tile 内容（样式照 §2.3，标题不用 PET、不用“宠物”）：
  - 标题：“互动”。设置页标题用的 `unscii_16` 没有中文字形，互动 tile 的标题
    要走 CJK 字形路，不要把“互动”塞进 unscii 标题。
    对齐：标题与返回按钮必须同在一条中心线上。设置页返回按钮是 56×48、
    顶部 y=28、箭头在按钮内居中，所以中心线是 y=52；标题若用更大的 CJK 字号，
    不能只照抄标题顶部 y=44，要按中心线 y=52 去算顶部，否则就会出现
    “`>` 与‘互动’不在一条水平线”的问题（上一版示意图就是这么错的）。
  - 返回按钮：左上角 `<`（`LV_SYMBOL_LEFT`，与设置页一致），点按回脸
    （`muse_ui_show_face()`）。不要右上角 `>`：`>` 按 tile 方向“指向脸”虽然
    有道理，但用户已定常规左侧 `<` 为准；圆屏顶部弦宽有限，`<` 的中心约在
    x=68、仍与标题同中心线 y=52，不要把箭头贴到 x=28（会被圆边切掉）。
  - 按钮：喂饭 / 小游戏 / 今日运势。回调只发动作，不结算、不直接改显示。
    按钮文案是动态的（`button()` 的 `label_out`，tick 里按快照改文案）：
    喂饭行写“喂饭 · +10金币”，小游戏行写“小游戏 · -5金币”，
    今日运势行写“今日运势 · 未抽 / 卡名”。居中按钮文案在圆屏下沿也安全，
    左对齐的状态行在底部会被圆边切掉，所以状态不另起行、直接塞进按钮文案，
    另加两行居中状态 note（不要一行写全——一行在圆屏下沿会被圆边切掉，
    实测 16 号字一行写全已超出弦宽）：第一行“金币 x/100”，第二行
    “摸摸 y/50 · 喂饭 z/10”。
    喂饭在当日喂饭奖励已领满（z = 10）时文案变暗（`COLOR_DIM`），
    点按前就能看出今天喂饭不再给币（仍可点、仍开心，只是无币）；
    小游戏在金币 <5 时文案变暗，点按前就能看出玩不了。
    摸摸不在互动页里：脸点按是摸摸唯一入口（见 §5.1），互动页里再放摸摸
    就是重复，拿掉后空出的行给小游戏。
  - 喂饭子页（互动 tile 的子页，不是顶层 tile，底部圆点不变）：
    点“喂饭”进子页，子页里一排三个图片按钮：上游 16×16 像素食物图，
    顺序：米饭 / 蛋糕 / 咖啡，图片下方小字写食物名（见 §5.4），
    左上角 `<` 回互动页。三个食物奖励相同：当日第一次喂给 +10，
    第 2 次起只开心、不给币，选哪个不影响给币；点食物后关子页回互动页，
    字幕与金币余额变化为主反馈（脸上附带开心通道，见 §5.4）。
  - 今日运势子页（互动 tile 的子页，不是顶层 tile，底部圆点不变）：
    点“今日运势”进子页，子页一张深色大卡片（与小游戏 / 喂饭子页同风格，
    不用米色纸、不照搬上游左右分栏）：卡片内等级金色大字、正文白色
    居中 18 号，卡片下两行灰色小字（免费每天一次 / 同日再抽显示同一张），
    左上角 `<` 回互动页。免费每天一次，同日重复抽显示同一张卡，
    直接揭晓、不做翻牌与假洗牌动画（见 §5.4）。
  - 小游戏子页（互动 tile 的子页，不是顶层 tile，底部圆点不变）：
    点“小游戏”进子页，子页里三个图片按钮：Game-icons 白手图
    （见 §5.5；按钮上不写字，不要文字按钮——2026-10-25 用户定稿；
    顺序：石头 / 布 / 剪刀，全部逆时针转 90 度、手朝上），
    左上角 `<` 回互动页（与互动 tile 的返回一致）。
    点出拳前先查币：金币 <5 时提示“金币不够，先摸摸 / 喂饭”，不扣、不开局；
    金币 ≥5 时先扣 5 再随机出拳，赢、平、输只影响结果文案，
    都不返币、不退款。胜负与连胜只记本局显示（第一版不进 NVS，
    重启清零；要持久化胜负记录是后续需求，不要在 1.5a 里顺手加字段）。
    出拳、揭晓、结果三段动画见 §5.5——先扣币再动画、随机结果在点按时已定，
    动画只是揭晓，不要先动画后结算。
  - note 行：结果反馈（见 §5.3）与新手提示（先摸摸赚币再喂饭）。
- 互动 tile 常驻不删除：离开 tile 不删页，`muse_ui_set_swipe_enabled()` 的
  “子页关 swipe”逻辑不管它；tile 间滑动始终可用（除非对话态等既有条件关掉它）。
  因此结果 note 不能靠“子页删除即消失”兜底：离开互动 tile 时清掉结果 note，
  回来时 tick 按快照重填状态行，不把上一条结果当成当前结果留着。
- 底部圆点：3 个，当前 tile 对应点亮（`COLOR_ACCENT`），其余 `COLOR_DOT_OFF`。
  1.4d 的圆点逻辑是“是不是设置页”二值 + 子页时隐藏，1.5a 要改成三值页索引；
  互动 tile 上不隐藏圆点（它不是设置子页），设置子页的隐藏规则原样保留。

### 5.3 反馈：字幕 + 开心，都有过期与守门

- LVGL task 里消费 feedback 队列（不要在 worker 里直接调 UI 函数）：
  成功（`PET_COIN` / `PET_OK` / `PET_FORTUNE_NEW`）→ `muse_state_make_happy()`；
  所有结果 → 写结果文案。
- 字幕文案按结果码一一对应，示例（实现时以结果码为准，数字取快照）：
  - 摸摸加币：`毛毛很开心 +5 金币（今日摸摸 15/50）`
  - 摸摸满额：`今日摸摸奖励已满 50 金币`
  - 喂饭成功：`喂了<食物名> +10 金币`（当日奖励已领满时文案为
    `喂了<食物名>（今日奖励已领）`，不再写 +10；喂饭没有“饱了”失败，
    因为 1.5a 已无饱腹）
  - 生活费扣款（跨日后第一次互动，显示一次）：`毛毛这几天花了 X 金币`
    （X 为实际扣款额，1 天就是 10；显示后清零，不要每次 tick 重复）
  - 占卜新卡：`今日运势：<卡名> · <等级>`（卡名与等级取静态表）
  - 占卜重复：`今日已抽过：<卡名> · <等级>`
  - 小游戏币不够：`金币不够，先摸摸 / 喂饭`（不扣、不开局）
  - 小游戏结果：`你出石头，对面出剪刀，你赢了` / `你输了` / `平局，再来一局`
    （只写胜负，不写返币——第一版胜平都不返币，扣的 5 币体现在状态 note 的金币余额里）
  - worker 未就绪 / 存储错误：`宠物未就绪` / `宠物数据损坏`（不编造数字）
- 字幕守门（照 §2.6 的扬声器范式）：
  - 只在 mode 为 IDLE 时写宠物字幕；对话进行中不写、不覆盖回复字幕。
  - 宠物字幕带过期时间（建议 3 秒，脸点按的开心是 1.6 秒，两者不绑定）：
    LVGL tick 里到期且 mode 仍为 IDLE 且字幕仍是宠物那条时，清为空串；
    期间 mode 变了（开始对话），不要清掉对话的字幕——过期清理必须先确认
    “当前字幕还是宠物字幕”，不能无条件 `set_caption("")`。
  - 互动 tile 内的结果 note 不受 3 秒过期限制，但离开 tile 时要主动清掉（见 §5.2），
    不能靠子页删除兜底；回来时只显示状态行，不复活旧结果。
- 音效：1.5a 不新增宠物音效。TamaMe 的本地互动音效（`muse_pet_sfx`）不移植；
  已有对话 / 提示音不动。想要“摸摸有声音”放到 1.5b 讨论，不要在 1.5a 里顺手加。

### 5.5 小游戏动画：出拳 — 揭晓 — 结果（三段，游戏页内自洽）

先说一个关键约束：**游戏子页上看不到毛毛的脸**（脸在另一个 tile 上），
所以输赢平局的动画不能指望脸的表情，必须在游戏页自己讲清楚：
结果大字 + 颜色 + 赢的那方高亮，脸的开心只是附带通道（赢了仍调一次
`make_happy()`，用户若立刻滑回脸能看到开心，但设计不依赖它）。
同理，喂饭的开心也是附带通道，喂饭页上的主反馈是字幕与金币余额变化。
1.5a 不在游戏页里另画一个小脸画布——那要第二套 avatar 渲染与布局，
是 v2 的事，不要在 1.5a 里顺手加。

布局（游戏子页，样式照互动 tile 的卡片 / 行高 / 颜色）：
上：标题“小游戏”与金币行（居中）；中：一行三个图片按钮（每张约 100px，
卡片底色，点按即出拳；竖排文字按钮的方案作废——用户定稿为图片点击）；
下：结果区（居中，动画 / 揭晓 / 结果 / 连胜都在这里）。左上角 `<` 回互动页
（与互动 tile 的返回一致），圆点不变。选择页与结果页共用同一套手图：选择页三张并排，结果页只放
两张（你的手在左、毛毛的手在右，每张约 130px）。

三段时序（总时长约 2 秒，不要拖到 3 秒以上，玩一局的节奏比仪式感重要）：

1. **出拳动画（约 1 秒）**：点出拳已先扣 5、结果已随机定好，动画只是揭晓。
   结果区字幕依次闪“石头！剪刀！布！”，每段约 300ms；
   同时三张手图轻微抖动（x 偏移 ±4px，LVGL 动画）3 次。抖动这招抄成熟项目
   的老套路：手抖 3 次再揭晓、800ms 抖动营造悬念；现在手图有了，
   抖的就是手图本身，不用“?”占位。
   动画期间出拳按钮变暗、不可再点，防止一局没完又开一局。
   音效：1.5a 不新增（见 §5.3），只有视觉抖动。
2. **揭晓（约 0.8 秒）**：结果区两张手图同时亮出来，左边你的手、右边毛毛的手，
   赢的那张加 `COLOR_ACCENT` 边框、输的那张变暗，平局时两张都不高亮不 dim。
   手图下方一行结果字（“你赢了！”/“你输了”/“平局，再来一局”）与连胜行。
   Game-icons 白手图（2026-10-25 用户点选确认，Adafruit 精灵图与 Twemoji
   emoji 版都被否掉后定稿）：直接用 `game-icons/icons` 仓
   `john-redman/rock.svg`、`paper.svg`、`scissors.svg`
   （John Redman，CC BY 3.0，512×512 网格，单色）：拳头 / 张开的手掌 /
   V 形剪刀手，手指分缝清晰，白色在深色卡片上直接弹出，不用白底。
   实机渲染必须整体逆时针转 90 度——原图手朝右，转完手朝上出拳，
   不要横向手。选择页约 100px、结果页约 130px，平滑缩放即可
   （矢量图，不要最近邻放大）。结果页输的那张变暗把白色换成
   `COLOR_DIM` 灰（不要用不透明矩形盖，盖完就看不见了）；赢的那张
   加 `COLOR_ACCENT` 边框。实机使用时保留 Game-icons 署名（CC BY 3.0）。
   实现前要在实机上过一遍辨认度，不要直接上机。
3. **结果页（停住，等你点，不自动跳走）**：自动跳走会让人低头一看就错过结果。
   - 赢：绿字（`COLOR_OK`）“你赢了！”，赢的那方保持高亮。
   - 输：红字（`COLOR_DANGER`）“你输了”，**不要用 error 抖动**——
     那个抖动看着像系统出错了，输了只是游戏输了。
   - 平：灰字（`COLOR_DIM`）“平局，再来一局”，出拳按钮仍在下面，
     点一下就是下一局（再扣 5），不用先回互动页。
   - 结果页停留期间不阻止浅睡：点按本身会 poke 唤醒计时（既有行为），
     但结果页本身不持有 power lock；用户放着不动，自动息屏照常走。
   - 连胜与胜平负只记本局显示，不进 NVS，重启清零（见 §5.2）。

喂饭与占卜的动画（参考上游语义，不照搬布局）：
上游喂食动画的语义是食物移向嘴、嘴张开、开心上升、满了拒绝；
1.5a 借这个语义：喂饭成功 = 字幕 + 金币余额变化 + 附带开心，
奖励已领满 = 只字幕（“今日奖励已领”）、不开心，让成功与领满一眼可分。
食物图用上游 `muse_pet_art` 的 16×16 像素画：米饭（碗）/ 蛋糕（分层）/
咖啡（带蒸汽的杯子），最近邻放大到约 80px、不要平滑；
火锅 / 鸡腿 / 茶三张作废。
占卜上游就是一张文字卡，没有特殊动画；1.5a 也一样，卡片文字 + 等级
直接揭晓，不做假洗牌动画——占卜的悬念在卡本身，不在动画上。
卡片样式按 §5.2 的深色统一版（深色卡片、金色等级、白色正文 18 号），
不用米色纸。

## 6. 时间、线程、功耗

### 6.1 时间

- 宠物 worker 直接用 `time()`；`muse_time_start()` 在 worker 启动前已跑
  （§2.5），RTC adopt 在先。
- 未校准时钟不扣生活费、不重置当日上限（见 §4.2）：日都算不出来，硬扣就是错扣；
  校准后按校准日结算一次，时钟回拨不补发金币、不补扣生活费。
- **待核实（实现前必须查，不许照抄）**：TamaMe 的占卜日按
  `(now + 8*3600) / 86400` 算，隐含 `now` 为 UTC；本仓库 `muse_time_start()` /
  SNTP 配置后的 `time()` 究竟是 UTC 还是本地时区，查 `muse_rtc.c` 与 SNTP
  配置后再定公式。若本仓库时钟已是本地时区，+8 就是错 8 小时的 bug，
  占卜会在错误的时间点跨日。公式以核实结论为准，进展记录里写明查到的
  时钟语义与最终公式。

### 6.2 线程与栈

- worker 任务：照 TamaMe 的形态——独立任务、命令队列（8 项）、反馈队列（8 项）、
  30 秒一轮（队列超时即检查一次日切分，不做每小时衰减）。优先级与栈大小
  以 TamaMe 为起点（任务优先级 2、栈 4096），实现时按本仓库的任务优先级分布
  复核一遍，不要高于 input / voice 任务。
- 栈位置：TamaMe 注释原话——NVS 提交会关 cache，PSRAM 栈不安全。worker 栈
  必须落在内部 RAM（`xTaskCreate` 默认即内部 RAM，不要为省内部 RAM 而改成
  PSRAM 栈）；实现时在代码注释里写明这一条，不要只留在设计稿里。
- 队列满时 `muse_pet_request()` 返回失败（不阻塞 UI）：UI 侧把“宠物未就绪”
  写进结果 note，不要在 LVGL 回调里等 worker。

### 6.3 功耗与待机

- worker 30 秒一轮、只在状态变化时写 NVS（动作、跨日扣款、日上限重置），
  没有每小时衰减要存盘，是 1.5a 的功耗上限口径：
  实现后要在电池下测一夜掉电，与 1.4d 同条件对比（见 §8.2），不要只测 USB 下。
- 互动 tile、脸点按、字幕过期清理都不持有 power lock、不阻止浅睡；
  `make_happy()` 本身调 `muse_state_poke()`（保持唤醒），这是既有行为，
  宠物动作因此会推迟一次自动息屏——属于“交互了所以不睡”，不是待机回归，
  验收时按“交互后息屏计时重置”算，不要按“宠物导致不睡”算。
- Test 构建的遥测采样（FAT 写 CSV）仍在，宠物数据不写 FAT、不进遥测 CSV，
  两条写路径分开，夜测数据才可比。

## 7. 版本与发布（1.5a 的身份）

- `esp32/version.txt`：`1.4d` → `1.5a`。这是 1.4a / 1.4b / 1.4c / 1.4d 一脉的
  字母后缀即测试版约定（`esp32/cmake/project.cmake`：以字母结尾的版本即测试版，
  不再追加 `-test`；`validate_config.cmake`：Test 构建的版本必须以字母或 `-test` 结尾，
  Release 构建的版本不得以字母结尾、不得带 `-test`）。
  不要发明 `1.5-preview` / `1.5_preview` 这类新后缀：它不在仓库的版本约定里，
  OTA 与 Release 脚本对它的处理是未验证的。对外称呼写“1.5 预览版”，
  版本号写 `1.5a`，两者在 Release 说明里各归各的位置，不要混成一个字符串。
- 构建命令：照 `sdkconfig.muse-test` 注释的 Test 形态走
  `tools/muse/board.sh` 的 Test 构建链（`MUSE_BUILD=test … build lcd185b`），
  分区表用 Test 表（`partitions_muse_test.csv`，含 FAT 遥测分区）。
- 发布形态：**USB 刷入，不走 OTA 推广**。Test 表与 Release 表的分区不同，

  直到 1.5 正式版（Release 构建、数字版本号）再按发版流程换。

  刷回 1.4d 不会自动清宠物数据——回退说明里写明这一点，不要承诺“刷回即干净”。

## 8. 验收

### 8.1 功能验收（逐项打勾，数字以实测为准）

1. 编译通过：Test 构建链、`check_sizes` 通过（1.85B 每 app 槽 4MB；
   模型 + 20 句文案体积很小，先以实编译为准，不要凭感觉说“肯定够”）。
2. 三页导航：开机在脸；脸左滑到互动、右滑到设置；互动右滑回脸、设置左滑回脸；
   底部圆点 3 个、当前页点亮；`muse_ui_show_face()` 回到脸（不是第 0 页）。
3. 重启后金币 / 喂饭日 / 占卜日 / 扣生活费日都在，不是每次开机归零。
4. 摸摸：前 10 次每次 +5 币（当日合计 50），第 11 次起不加币、只开心；
   跨自然日（按 §6.1 核实后的日切分）后当日给币清零；摸摸只有脸点按一个入口，
   互动页里没有摸摸按钮。
5. 喂饭：第一次 +10 金币，当日奖励上限 10，第 2 次起不给币、只开心；
   金币持有上限 100，进账超 100 截断到 100；喂饭没有“饱了”失败。
6. 小游戏：金币 <5 时不开局、不扣币；金币 ≥5 时先扣 5 再出拳；
   赢、平、输都只扣 5、不返币、不退款；出拳—揭晓—结果三段动画按 §5.5 走，
   结果页停住等点按、不自动跳走；小游戏子页能进能回互动页，圆点不变。
7. 占卜：同一天两次是同一张卡；次日能抽新卡；20 张都能显示，在 360 圆屏上
   不溢出、不截断关键等级词（长句先在模拟器 / 实机上逐张过一遍）。
8. 生活费：跨日扣 10（多日按天数算，扣到 0 为止），扣款后第一次互动
   显示一次扣款额、不重复提示；时钟未校准时不扣、不重置当日上限。
9. 时钟回拨不补发金币、不补扣生活费；NVS blob 损坏时宠物停用、显示损坏提示、不静默重置。
10. 对话主线无回归：按住 BOOT 录音、字幕、TTS 播放、闹钟、顶栏时钟 / 电量都正常；
   宠物反馈不打断聆听 / 思考 / 说话态。
11. 互动 tile 打开时不影响对话：从互动 tile 滑回脸、再按 BOOT 对话，流程正常；
    互动 tile 内点按不触发录音、不触发关机（`on_aux_clicked` 的关机入口不受影响）。

## 9. 风险与待核实（实现前 / 实现中必须闭环，不许带进 Release 说明）

1. **时钟语义**（§6.1）：`time()` 是 UTC 还是本地时区，决定占卜日公式。未核实前
   占卜跨日行为一律写“待验证”。
2. **三页导航**（导航修订）：圆点从 2 个变 3 个、页索引从二值变三值、
   `muse_ui_show_face()` 目标从 (0,0) 变 (1,0)——三处要一起改，漏一处就是
   “圆点亮错页”或“回脸回到设置页”。原 `drop()` 未列 `s_alarm` 一事不再是
   互动 tile 的前置项，记为设置页遗留问题，1.5a 里不改。
3. **生活费日切分**（§4.2 / §6.1）：跨日扣款的“日”与占卜日同一定义；
   未校准时不扣、多日按天数算、扣款提示只显示一次，三条都要实测，
   不要把“扣了但没提示”当成通过。
4. **字幕过期清理的竞态**（§5.3）：宠物字幕与对话字幕交替时，清理逻辑必须先确认
   当前字幕仍是宠物字幕；实现后要实测“宠物字幕未过期时开始对话”这一条。
5. **脸点按的事件归属**：`on_canvas_clicked` 在脸 tile 上；确认扬声器 / 电源图标
   的点按不经过它（现有 `muse_ui_face_control_at()` 是给板级 talk 判定用的，
   与 canvas 点击不是同一条路），不要把“点扬声器也算摸摸”当成特性写进去。
6. **app 体积与 RAM**：模型 + worker + 互动 tile + 20 句文案以实编译为准；
   互动 tile 常驻不删除，RAM 按常驻页算，不要按设置子页“同时存在约 50 KB”的 transient 口径，也不要在互动 tile 里常驻大图。
7. **TamaMe 本身的成熟度**：它自述为 source preview，换背景曾有原因不明的失败、
   新账号配对与长期稳定性未验证。1.5a 只取其模型层，不取其 UI 层与发布结论；
   它的“已验证”不自动成为 1.5a 的“已验证”，§8 必须在 1.85B 上重测。

## 10. 实施顺序（按这个顺序做，不要先画互动 tile）
