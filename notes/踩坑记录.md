## 0. OTA 报 `failed: could not start ota task`（2026-10-18，已真机定论）

**现象**：1.1 的板子在设置页点 Update，界面直接显示 `failed: could not start ota task`，
没有下载、没有进度条。

**定位**：这句字符串全仓只有一处 —— `esp32/main/ota.c` 的 `xTaskCreate(ota_task, "ota", 16384, ...) != pdPASS`
分支。也就是说**根本没走到网络**，是任务栈没申请下来。

**根因**：16 KB 连续块要不到。这块板内部 RAM 很紧：

```
I muse: ready: free heap 29371 internal, 4097604 psram
@power.saved ... "heap":{"free":35499,"largest":26624,...}
```

静止时最大的内部块只有 26 KB；设置页开着（LVGL + 触摸 + Wi-Fi 缓冲都活着）时更低，
16 KB 连续申请就失败了。本构建 `CONFIG_SPIRAM_ALLOW_STACK_EXTERNAL_MEMORY=y`，
`pvPortMalloc` 优先内部 RAM，落不到 PSRAM 上兜底。

**还有一个更严重的隐患**：即使栈申请成功、且落在 PSRAM，OTA 写 flash 时 cache 是关的，
PSRAM 栈不可访问 → 下载到一半必崩。所以 OTA 任务的栈**必须**在内部 RAM。

**修法**
- `xTaskCreateWithCaps(ota_task, "ota", N, ctx, 5, NULL, MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT)`；
  N 从 16 KB 起，失败依次降到 12 KB / 10 KB / 8 KB（8 KB 是 mbedTLS 握手的底线）。
- 每次失败打一行内部/PSRAM 的 `free`/`largest`，下次一看就知道差多少。
- `vTaskDelete(NULL)` → `vTaskDeleteWithCaps(NULL)`（WithCaps 创建的任务必须配对删除，否则漏栈）。

**验收行**
```
I link.ota: ota start: int free 2xxxx largest 2xxxx | psram free 4xxxxxx largest 4xxxxxx
I link.ota: ota task up (16384-byte internal stack)
```
串口 `>ota` 返回 `@ota started=1 Checking...`，随后 `ota.github: manifest: version=1.3`。

**教训**：这类"一按就失败、连网络都没碰"的错误，先 grep 报错字符串定位到唯一分支，
再看那一行的资源需求；不要从网络、签名、证书方向猜。

**测试坑（同一件事）**：想用"改 latest.json 版本号"来逼出下载路径时，注意
`releases/latest/download/latest.json` 走 GitHub CDN，**改完几分钟内板子仍拉到旧内容**
（实测改完立刻查还是旧的 `version=1.2`）。要可靠地测整条链路，就发一个真版本号的新 Release。

## 0b. OTA 装完又被静默回滚（2026-10-18，真机抓到完整时间线）

**现象**：`>ota` 打 `applied 1.2 -> 1.3, rebooting`，重启后串口 `Version: 1.3`，看着一切正常；
**但过了几分钟再抓启动日志，又变回 `Loaded app from partition at offset 0x20000` / `Version: 1.2`**。
用户视角就是"我明明升级成功了，怎么又退回旧版本"。

**根因**：`esp32/main/app.c` 的 `ota_verify_task()` 把"镜像是否有效"完全押在
Home Link 控制 WebSocket（`noise_ctrl_is_connected()`）上：只有 WS 连上才
`esp_ota_mark_app_valid_cancel_rollback()`；否则等 300 s 超时直接
`esp_ota_mark_app_invalid_rollback_and_reboot()`。
这块板**没有 SDK token**（启动日志 `SDK token: (none)`，`link.vm_api` 一直
`ESP_ERR_HTTP_CONNECT`），控制 WS 永远连不上 → 300 s 后必然回滚。

**修法**：保留 WS 快速路径；新增宽限——镜像连续运行 `OTA_VERIFY_GRACE_US`(30 s) 后也标记有效。
理由：会崩的镜像活不到 30 s，那种情况 bootloader 自己就会回滚，不需要用云端通道判断镜像好坏。
宽限路径只在 `s_ota_pending_verify`（启动时读 otadata 的真值）为真时执行——从 factory 分区启动时
`esp_ota_mark_app_valid_cancel_rollback()` 返回 `ESP_FAIL`（IDF `Running firmware is factory`
分支），无条件调用会让每次普通开机多打一条错误日志。

**验收行**
```
I link.ota: applied 1.2 -> 1.3, rebooting
I app: running a PENDING_VERIFY OTA image; awaiting health check
I app: OTA image validated after 30 s without the control WS (this build runs without it)
```
之后静置 5 分钟以上再手动复位，启动日志仍是 `Version: 1.3`（分区 0x420000），不回退。

## 0c. 这块板跑 OTA 时内部 RAM 已经很紧（2026-10-18 实测数字）

`>ota` 那一刻的实测（1.2，UI 起着）：

```
I link.ota: ota start: int free 18315 largest 8704 | psram free 4095040 largest 4063232
W link.ota: no 16384-byte internal stack for the ota task
W link.ota: no 12288-byte internal stack for the ota task
W link.ota: no 10240-byte internal stack for the ota task
I link.ota: ota task up (8192-byte internal stack)
```

**PSRAM 有 4 MB 空闲，内部最大块只剩 8.7 KB**——这就是原来 16 KB 必然失败的原因。
结论：**这块板上凡是要写 flash / 做 TLS 握手的任务，栈只能从内部 RAM 申请，并且不能假设要得到**。
8 KB 栈跑通了完整下载（3 MB）+ 验签 + 安装，说明 8 KB 是够用的底线，但没有余量：
以后新增 OTA 相关功能前先看这行日志。

## 0e. 国内网络直连 GitHub CDN 不稳，本机 curl 能通不代表板子能通（2026-10-18）

**现象**：同一时刻本机 `curl` 拉 Release 资产一切正常（200），板子上
`esp-tls: select() timeout` → `manifest fetch failed: ESP_ERR_HTTP_CONNECT`。
反复几次后又能通， fluctuate。

**根因**：本机 curl 走的是 HTTP 代理（`HTTP/1.1 200 Connection Established` 那行就是代理隧道），
板子直连。国内直连 `objects.githubusercontent.com` 时通时断是常态。

**结论**：板端 OTA 失败不要只看本机能不能下载，要看板子那三行 `esp-tls`。
测试 OTA 时要给足重试窗口，别把网络抖动当固件 bug。

## 1. 敲击亮屏过一段时间后永久失效（2026-10-18）

**现象**
- 刚刷完/刚重启时敲击正常（`muse_input: waking (tap)`）。
- 睡眠 2 分钟后敲击 0/3 唤醒；再往后按键亮屏→息屏→敲击也失效（永久死亡）。
- 故障现场：`STATUSINT=0x00 STATUS1=0x00 TAP_STATUS=0x31`，加速度计仍在正常采样（Z≈0.90 g）。

**根因**（三条独立机制，都会让 tap 引擎停摆）
1. **I2C 事务被 light sleep 截断**：`CONFIG_PM_ENABLE` + 自动 light sleep 打开后，任何任务在任何
   时刻都可能被停钟。QMI8658 会把半截写入解析成寄存器写，`CTRL8.Tap_EN` 被改写 → 引擎关掉，
   而 `CTRL7/CTRL2`（加速度计）不受影响，所以"芯片还在跑但检测不到敲击"。
   睡眠时 200 ms 一次进出 light sleep，两分钟就是 600 次，撞上一次的概率接近 1。
2. **STATUS1 锁存没人清**：`bit1` 是读清位。亮屏时敲一下，没人读 → 位一直置着，引擎不再报新事件；
   下次睡下配了 HIGH 电平唤醒，电平早已满足，等于没配。
3. **引擎状态机自锁**：配置寄存器全对，引擎就是不检测（无任何可读痕迹）。这一条只能靠定期重臂兜。

**修法**（`muse_imu_tap.c` / `muse_input.c`）
- 每个 I2C 事务持 `ESP_PM_NO_LIGHT_SLEEP` 锁（`esp_pm_lock_acquire/release`），事务期间不睡。
- `STATUS1` 每 200 ms 读一次，**不管亮屏还是息屏**；值只在睡着时用来唤醒（读即清锁存）。
- 1 Hz 回读 `CTRL7/CTRL8` 与 init 写入值比对，漂了就重跑 `muse_imu_tap_init()`（10 s 内不重复，
  防循环）；每 60 s 再比一次 `CAL1..CAL4`。
- 睡着时每 60 s 做一次完整重臂（停传感器 → 重写两组参数 → 重开），覆盖第 3 条。
  间隔取 60 s 而不是 10 min：现场故障是睡下两分钟内就死，10 min 的定时器等不到。
- 新增 `>imu` / `>imu.check` / `>imu.rearm` 串口命令，一条 WARN 打印全部寄存器与期望值。

**验收行**
- 修好后日志里 `tap engine on: accel 500 Hz, INT1 -> GPIO8 (CTRL7=0x21 CTRL8=0xc1)`。
- 漂移自愈时出现 `config drift: CTRL1=... CTRL8=0x..(want 0xc1) ...` + `tap re-initialised (#1)`。
- `tap_cycles.py` 跑 3 轮（每轮等自动息屏 120 s → 敲击）必须 3/3 出现 `waking (tap)`。
- 长稳：睡眠 10 分钟后敲击仍能唤醒。

## 2. TTS 首音慢（2026-10-18）

**现象**：板子从说话到出声 ~3.1 s（串口 `TTS got N bytes (first byte 3107 ms)`）。

**根因**：服务端每个请求都重新跟 Azure 建 TLS 连接。实测（本机 → eastasia 直连）：

| 场景 | 首音 |
|---|---|
| 冷连接，60 字 | 1.20–1.39 s |
| 同一连接复用，60 字 | **0.45–0.53 s** |
| 冷连接，5 字 | 1.17–1.26 s |
| `style=friendly` 开/关（60 字） | 1.43 / 1.29 s |
| 16k/32k vs 24k/48k | 无差别（1.39 / 1.43 s） |
| 去掉标点 `<break>` | 无差别 |

结论：**首音几乎不随文本长度变化**，所以"把首句切出来先合成"没用；连接复用是唯一大杠杆。

**修法**（`tts-server/tts_server.py`）
- Azure 连接改为**全局 LIFO 连接池**（`TTS_AZURE_POOL`，默认 6），读完整个 body 才归还；
  半读的连接直接丢弃，不污染下一次。池化连接失效时自动重连一次。
- 启动时 `_prewarm()` 合成一个"嗯"，把首请求的握手也省掉（1.84 s → 0.58 s）。
- `STREAM_HEAD_BYTES` 1024 → 512，`waitress send_bytes` 1024 → 512（`TTS_STREAM_HEAD` / `TTS_SEND_BYTES`）。
- 固件侧**不需要改**：`muse_tts.c` 已经把音频边收边送，`MP3_BUF` 有 512 KB，
  下一段请求在当前段读完就发出，不会因为 ring 满而卡住。

**踩坑**：第一版用 `threading.local()` 存连接，**完全没效果**（还是 1.3 s/次）——
流式 worker 是每个请求新 `threading.Thread` 起的，线程本地变量永远是空的。必须用显式池。

**验收行**
- 服务端日志 `first bytes after 0.4x s`（原来 1.2–2.2 s）；`/health` 里 `azure_pool_idle >= 1`。
- 板端 `first byte` 应落在 1.5 s 上下；冷启动第一次仍会慢 0.5 s 左右。

## 3. 电量恒显 100%：读错寄存器（2026-10-18，已真机定论）

**现象**：`read_power()` 读到的电量永远 100%。

**先入为主的错误判断**：一开始按"BQ27220 出厂 Data Flash 没按电芯配过、SoC 天然 100%"来解释，
还加了电压兜底。**这是错的** —— 真机 `>batt` 一打印就推翻了。

**根因**：**寄存器地址读错了**。代码读 `0x1C` 当 SoC，而 `0x1C` 是 **StandbyTimeToEmpty**（分钟）。
现场读到 1947，被 `soc <= 100 ? soc : 100` 夹成 100 → 永远满电。
SoC 在 **`0x2C`**（TRM Table 2-1；与 esp-iot-solution 的 `bq27220_reg.h` 一致）。

真机 `>batt` 原始值（1.2，插 USB 充电中）：

| 寄存器 | 值 | 含义 |
|---|---|---|
| 0x08 | 4134 | Voltage 4134 mV |
| 0x0C | 474 | Current +474 mA（正=充电） |
| 0x10 | 292 | RemainingCapacity 292 mAh |
| 0x12 | 500 | FullChargeCapacity 500 mAh |
| 0x18 | 26 | TimeToFull 26 min（正在充） |
| 0x1C | 1947 | **StandbyTimeToEmpty** ← 原来被当成 SoC |
| 0x28 | 3068 | InternalTemperature 306.8 K = 33.7 ℃ |
| 0x2A | 2 | CycleCount 2（新机） |
| **0x2C** | **59** | **StateOfCharge 59%** |
| 0x2E | 100 | StateOfHealth 100% |

交叉验证：RC/FCC = 292/500 = **58.4%**，与 SoC 59% 吻合；SoH 100%、CycleCount 2 也符合新机。
说明电量计**本来就是配好的**，根本不需要写 Data Flash。

**修法**：SoC 改读 `0x2C`；越界（>100）才回落到电压估算。`charging` 用 BatteryStatus(0x0A) bit0
（DSG，1=放电）取反。`>batt` 按 TRM 名称打印 18 个标准命令 + DesignCapacity(0x3C)。

**教训**：**先 dump 再推理**。任何一个"恒为某个值"的传感器读数，先怀疑地址/单位/缩放，
不要急着给它编一个物理原因。`0x1C` 读出 1947 这种明显不像百分比的值，本身就是最强的线索。

**验收行**
- `>batt` 里 `0x2c StateOfCharge 59 %`，`0x10/0x12` 与 SoC 自洽。
- 界面电量不再是 100%，且放电时会下降。

## 4. v1.1 tag 指错提交（2026-10-18）

**现象**：`git ls-remote --tags` 显示 `v1.1 -> ca38241`（1.1 之前的旧提交），
真正 1.1 代码在 `7a1dd26`。

**影响**：`git describe` 版本号错；OTA 的版本门禁若读 tag 会误判。

**修法**：`git tag -f v1.1 7a1dd26 && git push origin refs/tags/v1.1 --force`。
用**强制更新**而不是删除重建：GitHub Release 是按 tag 名关联的，强制更新后 Release 自动指向新提交，
删掉重建反而要手工重新关联资产。

**验收行**：`git rev-parse v1.1` == `7a1dd265bd88f9c9f42df335aa9982e891e26e1c`。

**同类复发（同日，v1.2）**：先建 Release 再推代码，GitHub 就把 tag 打在"当时 main 的 HEAD"上
（`7a1dd26`），而 bin 是新代码 → tag 与镜像不一致。已改指 `6f8eef4`。
根治：`ota/publish_github.sh` 现在**先** `git tag -f $tag HEAD && git push -f origin refs/tags/$tag`，
再建 Release；工作区脏时打 warning（tag 指向 HEAD，镜像可能对不上）。

## 8. LVGL 绘制缓冲放 PSRAM 导致 SPI DMA 饿死（2026-10-15）

**现象**：`DMA TX underflow` / `recycle spi transactions failed` / `Draw bitmap failed`，屏不亮。

**根因**：ESP32-S3 上 SPI DMA 从 PSRAM 取数供不上 QSPI 的消耗。

**修法**：分带渲染（`muse_lcd_bands_run`）+ 内部 RAM 双缓冲，绘制缓冲不放 PSRAM。

**验收行**：上述三行日志消失，`backlight 100%`。
