# 1.5.2c 收口：单词练习上线 + TTS 低时延（20261110）

> 本版两件事：**单词练习**（第 8 款小游戏）上线，以及**把「每次请求都重新握手」这个成本
> 从语音链路上拿掉**。证据全部来自串口实测与公网 curl，数字在下面各节里。

## 一句话根因

板子上**新建一条 HTTPS 连接要 3.5–4.3 秒**（ESP32-S3 跑 mbedTLS，验完整证书链 + DNS），
而 muse-tts 服务器在**同一连接内应答只要 18 毫秒**。原来的代码每条请求都是
`esp_http_client_init() → perform() → cleanup()`，所以：

- 回复语音按句请求 → 句句付一次握手，首音 2–4 秒里大头是重复握手；
- 单词卡片一组 4 个词 → 4 次握手，一组取音 16 秒。

密码学本身不是瓶颈：ESP32-S3@240 MHz 实测 RSA-2048 验签约 39 ms、ECDSA P-256 约 66 ms。
所以「复用连接」远比「换算法 / 缩证书链」划算，后者基本白费劲。

## 改了什么

### 固件

| 文件 | 改动 |
|---|---|
| `esp32/components/muse/muse_wordcards_audio.c` | 取音改**一条 keep-alive 连接**跨词复用（`ensure_client` / `drop_client`，只换 URL）；出错、被中止、状态非 200 时丢弃连接并重试一次。播放线程栈 12 KB → **24576**（原值会 panic：`A stack overflow in task muse_wc_play`）。加播放开始/结束 + 剩余栈日志。 |
| `esp32/components/muse/muse_tts.c` | 回复请求同样改 keep-alive 复用；新增 `muse_tts_prewarm()`：只做 TCP+TLS（打根路径，403 也算成功），不合成、不耗额度；空闲超 45 s 的连接在预热时主动换新。 |
| `esp32/components/muse/muse_chat_session.cpp` | `turn_start()` 里调 `muse_tts_prewarm()`，把握手藏进「等模型出字」的 4–7 秒。 |
| `esp32/components/muse/muse_wordcards_ui.c` | 进组即玩（去掉开始页/暂停页、长按不再暂停）、左上角返回按钮常驻；HUD 两处 `%d` 传 `uint32_t` 改 `%lu`（`-Werror=format`）。 |

### 服务端（muse-tts 1.6 + nginx）

- `tts-server/tts_server.py`：`word=1` 分支 + 磁盘缓存（`TTS_WORD_DIR`）、SSML 语言跟随音色、
  `/health` 增单词缓存字段。详见 `wordcards-tts-server.md`。
- nginx：`extension/<TTS 站点>/proxy.conf` 加 `proxy_set_header Connection ""`；
  新增 `vhost/nginx/0.muse-tts-upstream.conf`（`upstream muse_tts_backend { server 127.0.0.1:5050; keepalive 16; }`），
  `proxy_pass` 指向该 upstream。upstream 块必须在 http{} 作用域，所以单独放一个文件。

## 实测

| 场景 | 改前 | 改后 |
|---|---|---|
| 板子单条 HTTPS 请求 | 3.5–4.3 s（每次新建连接） | 同一连接内服务器应答 18 ms |
| 单词卡片一组 4 词 | 16 s（apple 123.29 s / banana 128.26 s / cherry 173.24 s / peach 176.71 s 时间戳差） | 「快多了」（用户实机） |
| 单词播放栈峰值 | 12 KB 溢出 panic | 24576 分配，播放后余 7.1 KB ⇒ 峰值约 17.4 KB |
| 回复语音预热 | 无 | `prewarm: connection ready in 3109 ms`（在等模型时完成） |
| 回复语音首字节 | 每句握手 3.5–4.3 s + 合成 | **2040 / 506 / 481 ms**（第 1/2/3 句，用户实机「体验很高」） |
| 公网取词（WSL 同连接 4 词） | — | 首词 0.40 s（含握手），其后 0.019 / 0.017 / 0.017 s |

## 调研结论（同类项目怎么做的）

- **xiaozhi-esp32**（`78/xiaozhi-esp32`，以及 Espressif 官方 `esp_xiaozhi` 组件）：
  唤醒时建**一条 WebSocket**，整个会话的 JSON 控制与 Opus 音频帧都走它，结束才关。
  服务端实测 ASR→TTS 首帧 975–1394 ms。即「一条流式长连接」是这个品类的通行做法。
- **TLS session resumption（session ticket）**：IDF v6.0.x 有已知 bug（issue #18919，TLS 1.3 下
  `save_client_session` 从不生效，SAVE 早于 NewSessionTicket），官方 fix 仍在评审。
  它只是「重连变快」，不能替代「不重连」。
- **nginx**：`proxy_buffering off` 是流式首音的前提（我们的 proxy.conf 本来就是 off）；
  老版本 nginx 要显式 `proxy_http_version 1.1` + `Connection ""` 才能用 upstream keep-alive。

## 没做 / 待确认

- **合并分块**：回复仍按 ~180 字节切块、每块一次请求（现在只付 RTT 与合成，不再付握手）。
  合并成整段 `stream=1` 能再抹平句间空隙，首句首音不变。未做。
- **第一句那 2040 ms** 是 Azure 合成本身，压缩空间只能在「首句更短」或「换更快档位」。
- **卡片页偶发卡顿**：怀疑与单词播放后从未 `muse_audio_power(false)`（声音通路一直开着）有关，
  未取证。用户 2026-11-10 表示先不管。
- **`systemctl is-active nginx` 显示 failed** 是宝塔不走 systemd 的缘故；判据用
  `/etc/init.d/nginx status`（already running）与端口监听。

## 复盘要点

1. 先量再改：一句 `curl -w` 的 ttfb 与串口时间戳差，就把「服务器慢」和「板子握手慢」分开了。
2. 新分支第一次上目标构建才算数：host 测试不编译 ESP-IDF-only 文件，`-Werror` 与栈溢出都是
   上机才暴露的。
3. 栈大小按高水位定，不按经验猜（本版 7.1 KB 余量即证据）。
